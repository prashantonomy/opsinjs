## Status

**Accepted, not yet implemented.** 2026-09-02. The decision is binding; the
generator that implements it has not been written. What resolves today is
described under [What exists today](#what-exists-today).

## Context

The catalogue contains two kinds of row. Twenty-four ids have specifications and
pages. Around thirty-five more are `considered`: names we have reserved, with no
specification and no commitment, so that the system has an answer to "do you have
a Tooltip" that is not silence.

The question is what happens when somebody asks for one. And "somebody" is
increasingly a program: an assistant asked to build a health screen guesses a
documentation URL from a component name, fetches it, and behaves according to what
comes back.

**A 404 is the worst possible answer**, because it is indistinguishable from a
typo, a moved page and a site outage. Faced with one, a code-generating assistant
does not stop — it invents a plausible API and writes code against a component
that does not exist. That is the specific failure this whole documentation
architecture is built to eliminate, and it is worse here than elsewhere: the
invented component will be rendering somebody's blood pressure.

But the opposite is also a trap. Giving every considered name a full page would
add thirty-five entries to a sidebar that already describes a system with no
components in it, which is the empty-cathedral problem — a documentation site
whose size is an accurate measure of nothing.

## Decision

**A generated stub page per considered id, at the guessable URL, excluded from the
navigation tree.**

- `scripts/build-registry.mts` writes one MDX file per `considered` catalogue row
  into the components directory, so the URL is
  `docs/components/<id>` — the same shape as a real component page, guessable from
  the name alone.
- The page states, in three short paragraphs and one machine-readable marker: what
  the name refers to, that it is not built and has no specification, and what to
  use instead. It carries `status: considered` and the not-implemented marker, and
  it is deliberately *not* written in the shape of a specification — a considered
  page that looks like a `planned` page is a lie with extra steps.
- **It is excluded from the sidebar.** The components group lists its pages
  explicitly, and a page not listed is absent from the navigation tree while
  remaining a real, resolvable route.
- **It is included in search, in the `.md` twins and in `/r/index.json`**, because
  those are the surfaces where a definitive negative answer is worth having.
- **It is omitted from the sitemap.** Publishing thirty-five thin pages to search
  engines serves nobody; the machine-readable surfaces already carry the answer for
  the audience that needs it.

We did *not* adopt a catch-all route.

## Consequences

- **Every catalogue id resolves**, and `assert-ia.mts` enforces it in both
  directions: a considered row with no resolving URL fails the build, and a stub
  page with no catalogue row fails it too.
- **An obligation on the components group's `meta.json`:** it must list its pages
  explicitly and must not use the rest token, or thirty-five stubs appear in the
  sidebar overnight. This is a real coupling and it is written here because that is
  the only place it can be found later.
- **A second status gate.** `<PageTemplate>` must accept `considered` and require
  a much smaller section set than `planned` — the notice, the alternative, and
  nothing else.
- **Generated pages in an authored directory.** The components directory will
  contain both hand-written specifications and generated stubs; the generated ones
  carry the marker comment and are covered by the drift check, per
  [ADR 0006](0006-generated-not-authored.mdx).
- **Thin content, deliberately.** These pages are short and repetitive by design.
  The alternative — padding them into something that reads as substantial — is how
  you end up with a documentation site that cannot be trusted about anything.

## What exists today

Until the generator is written, a considered id resolves through two surfaces and
not at a guessable page URL:

- The [catalogue](../../reference/generated/catalogue.mdx), which lists every id,
  shipped and considered, with its status and aliases.
- `/r/index.json`, which carries the same rows for programs.

The [components overview](../../components/index.mdx) also lists considered rows
in its status matrix. **Guessing `docs/components/tooltip` still returns a 404
today**, which is precisely the gap this record exists to close, and it is listed
as such on the [roadmap](../roadmap.mdx).

## Alternatives considered

**A catch-all route under the components path**, returning a machine-readable
"considered, not implemented" answer. Rejected, though it was close. It bypasses
the content pipeline entirely: no `.md` twin without writing one by hand, no
search index entry, no `llms.txt` presence, and a second rendering path for
component pages that would drift from the first. A generated MDX file gets all of
that for free because it is an ordinary page.

**One page listing every considered id, with anchors.** Rejected: an anchor is not
a guessable URL, and a program fetching it to ask about one name receives
thirty-four irrelevant answers alongside the one it wanted.

**Doing nothing — let them 404.** Rejected. It is the failure described at the top
of this record, and it is the reason the specification pages exist at all.

**Full specification pages for every considered id.** Rejected: a specification is
expensive and reviewable, and writing thirty-five of them for names nobody has
committed to would devalue the ones that are real. See
[Proposals](../proposals.mdx) for the ladder a name climbs before it earns one.

## Revisiting this

Revisit if the considered roster grows past the point where generated stubs are
noise in the repository — at which point the answer is probably a smaller roster,
not a different mechanism.
