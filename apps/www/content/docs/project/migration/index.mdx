## There are no migration guides yet

There has been one release and there is nothing to migrate from. This node exists
because the [versioning policy](../versioning-policy.mdx) promises a guide for any
change too large for a changelog entry, and a promise needs an address before the
first time it is kept.

## When a change gets a guide

A [changelog entry](../changelog/index.mdx) covers a breaking change you can act
on in a paragraph: a renamed prop, a moved import, a removed token with an obvious
replacement.

A migration guide is written when the change needs more than that. In practice
that means one of four things:

- **The DOM changed**, so somebody's stylesheets and end-to-end selectors have to
  change with it.
- **A `data-*` attribute or a CSS custom property was renamed**, which reaches
  code the [versioning policy](../versioning-policy.mdx) covers but that no type
  checker will catch for you.
- **A clinical contract changed**, altering what a component asserts, or what it
  must never be read as. That is not a code change at all for most readers; it
  is a reason to re-run a safety review.
- **The upgrade cannot be done in one step**, and the intermediate state has to be
  described so that a large codebase can move gradually.

## What a guide will contain

The version it moves from and to. What breaks, in the order you will hit it. The
mechanical changes, as diffs. The changes that need a judgement, marked as such
and never presented as mechanical. A way to verify you are finished. And because
this system is distributed as source you own, what to do if you have already
modified the component being migrated, which is the case the usual upgrade guide
forgets.

## Until then

[Upgrades and diffs](../../registry/upgrades-and-diffs.mdx) covers the ordinary
case: taking a newer version of a component whose source lives in your repository,
using a dry run and a three-way merge rather than an overwrite.
