## The board

Every proposed component is a row in the catalogue with a status, so the board is
not a separate list that drifts from reality. It is the same data the rest of
the site reads.

<StatusMatrix />

Rows marked `considered` are proposals that have been accepted as *names*: we
agree the problem is real and have reserved the id. They carry no specification
and no commitment. Rows marked `planned` have a written specification and are on
the [roadmap](./roadmap.mdx). There are none in the catalogue today, because
every proposal that reached that rung has since been built and now reads `alpha`
or `beta`. The rung is still there and a new proposal still passes through it.

## The maturity ladder

A proposal climbs five rungs, and each rung is a claim somebody has to be willing
to make in public. The ladder deliberately maps onto the
[release phases](./release-phases.mdx), so that a proposal does not have a
vocabulary of its own that has to be translated later.

| Rung | Status | What has to be true |
| --- | --- | --- |
| **Proposed** | Not yet triaged | Someone has described a real screen they could not build |
| **Considered** | `considered` | The problem is agreed and a name is reserved |
| **Specified** | `planned` | A full specification exists and has been reviewed |
| **Built** | `alpha` / `beta` | It is implemented, it renders, and it has an example |
| **Adopted** | `stable` | It meets the accessibility bar and has shipped in a product |

### Proposed

Anyone can propose. What makes a proposal answerable is a description of the
screen, not of the component: what a person is looking at, what they have to
decide, and what went wrong when you built it out of the existing parts.

The commonest outcome at this rung is not rejection. It is being told which
existing component or pattern already does the job, which is a good outcome and
takes ten minutes rather than three months.

### Considered

To be reserved as a name, a proposal has to answer three questions.

**Is it distinct?** Name the closest existing component and say what it cannot
do. "Like `Callout` but for warnings" is not distinct; the status axis already
carries urgency.

**Is it health-shaped?** opsinjs is not a general-purpose component library.
There are excellent ones already, and the reason to add something here is that it
carries a clinical meaning, a safety obligation or a plain-language contract that
a general component would get wrong.

**Would it be needed twice?** One screen in one product is a good local component.
Two unrelated products needing the same thing is a system component.

### Specified

This is the expensive rung and the one that decides most proposals. A
specification is a full component page at `status: planned`, and the
[documentation templates](../handbook/contributing/documentation-templates.mdx)
give you the exact shape. It must contain:

- **Intent** in one sentence, written for the person using the app rather than
  the developer building it.
- **When not to use it**, with every entry naming the alternative. A component
  that cannot say what it is not is not yet understood.
- **The clinical contract**, for anything in a `health-*` category: what it
  asserts about someone's health, what it must never be read as, which colour
  axis it may use, and who owns the thresholds it displays.
- **A proposed anatomy and API**, explicitly marked as a specification.
- **The accessibility bar it must clear**, covering keyboard behaviour, the
  announcement contract, target sizes, and how it survives grayscale.

A specification that survives review is a decision, and it is reviewed by whoever
the [freshness rules](./docs-freshness.mdx) name for its kind: design and
engineering always, clinical for anything in a health category.

### Built and Adopted

The remaining rungs are the release phases and are defined there. The one worth
repeating: **`stable` requires that it has shipped in a real product**. A
component that is perfect and unused is a hypothesis.

## What gets declined, and why

- **A rename of something that exists.** Confusion about which component to use
  is usually a documentation defect; the fix is the when-not-to-use list.
- **A general-purpose primitive** that a dozen mature libraries already ship
  better. The [considered rung](../reference/generated/catalogue.mdx) exists to
  hold these, reserved so the question has an answer, not so it has a component;
  the roster is empty today because every name that reached it has since been
  built.
- **Anything requiring a clinical judgement from the library.** Thresholds,
  reference ranges and what a number means for a person belong to the product.
  A proposal that needs opsinjs to decide when a value is dangerous is asking the
  presentation layer to practise medicine.
- **A component justified only by a screenshot of another product.** Say what the
  person reading the screen has to decide, and the proposal usually improves.

## How to actually open one
