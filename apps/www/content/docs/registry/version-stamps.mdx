## Overview

The fork problem is the unavoidable consequence of distributing code by copying
it. A month after installation, your `result-card.tsx` and the registry's
`result-card.tsx` are two different files with one name, and nothing in your
repository knows that.

The smallest thing that helps is a comment.

```tsx
// @opsinjs result-card 0.4.2
```

One line at the top of every emitted file, naming the registry, the item and the
version it came from. It costs nothing, survives copy and paste, is visible in a
code review, and turns three otherwise unanswerable questions into lookups.

Nothing emits it yet. `/r/<name>.json` serves each file exactly as it appears in
`registry/bases/base/` and `lib/`, so every file installed from opsinjs today
arrives unstamped, and the rest of this page is the specification rather than a
description of what you will find in your repository.

## The three questions it answers

**What is this?** A developer who has never heard of opsinjs opens a file in a
health app and can find out where it came from in five seconds, without a
package manifest, a lockfile or an internal wiki page.

**What have I changed?** Fetch that exact version from the registry and diff. Any
difference is a local change. It is either deliberate or accidental, and both
are worth knowing about.

**What has changed upstream?** Compare the stamped version against the current
one. This is the "what changed since your version" report, and it is only
possible because the file remembers where it started.

## Where the stamp goes

At the very top, before imports, in a comment appropriate to the file type.

```tsx title="components/ui/result-card.tsx"
// @opsinjs result-card 0.4.2
// Copied source. Edit freely, but read the upgrade notes before taking an update.

import { cn } from "@/lib/utils"
```

```css title="app/opsinjs-theme.css"
/* @opsinjs opsinjs-default 0.4.2 */
```

Three rules:

- **Every emitted file**, not just the main one. A component that installs three
  files would stamp three, because they are upgraded independently.
- **Never rewritten by anything but an install.** A formatter that moves it, or
  a codemod that drops it, has destroyed the only provenance the file has.
- **Kept even when you edit heavily.** A stamp on a heavily modified file is more
  valuable than one on an untouched file, not less: it is the base of the
  three-way merge described in
  [Upgrades and diffs](./upgrades-and-diffs.mdx).

The tool that reads stamps across a project and reports what has moved upstream
is specified and not built. The intended shape:

```bash
# PROPOSED. Not implemented.
npx @opsinjs/cli stamps --report
```

```txt
result-card   0.4.2 → 0.6.0   2 changes, 1 marked SAFETY
status-pill   0.4.2 → 0.4.2   up to date
value         0.3.0 → 0.6.0   4 changes
```

The `SAFETY` marker is the part worth arguing about now. A change to a clinical
default, a threshold behaviour or a screen-reader announcement is not the same
kind of change as a refactor, and a report that lists them identically will get
skimmed. Marking them differently is cheap; noticing them late is not.

Until the stamp and the tool both exist, the manual form works: keep your own
note of what you installed and when, read the
[changelog](../project/changelog/index.mdx), run `add --diff`.

## Why not a lockfile

A lockfile is the obvious alternative. It is one manifest listing every installed
item and its version, and it is worse here for two reasons.

It **drifts from reality.** The file is the artefact; the manifest is a claim
about it. Somebody copies a component into a second directory, or hand-edits
one, and the manifest still says what it always said. A stamp travels with the
file because it is *in* the file.

It **assumes one project.** Copied code moves: into a monorepo package, into a
prototype, into a different company after an acquisition. The comment survives
all of that. A manifest at a repository root survives none of it.

A manifest is a reasonable *addition*. It is not a substitute.

## Verify it worked

<Steps>

### Every installed file is stamped

```bash
grep -rL "@opsinjs" components/ui/
```

Today that command lists everything you installed, because nothing emits a
stamp. Once the build does, a file it still lists was installed by something
that stripped the stamp, or was copied by hand.

### The stamp is accurate

Fetch the stamped version from the registry and diff. Differences should be
changes you recognise. Unrecognised differences mean the stamp is wrong, which
is worse than no stamp at all. It is a provenance claim that is false.

### Your tooling preserves it

Run your formatter and your linter with `--fix` over a stamped file and confirm
the comment survives. Some header-comment rules will remove it.

</Steps>

## Troubleshooting

**A file has no stamp.** Expected for everything installed so far: the registry
emits none. Diff against the current upstream, record what you took and when,
and add the stamp by hand once versions exist. An approximate stamp with a note
is better than none.

**Two files claim different versions of the same item.** Two installs at
different times. Bring them to the same version before you next upgrade, or you
will merge two divergent bases.

**A formatter keeps deleting it.** Add an exception for the first comment block
in installed files, or move installed code into a directory your formatter does
not rewrite.

**The stamp says a version the registry does not serve.** Historical items are
required for three-way merges. If one is missing, that is a registry bug worth
reporting, not a reason to stop stamping.
