## How this is generated

**Source:** `registry/catalogue.ts` — the single declaration of the id namespace.
**Script:** `scripts/build-registry.mts` writes `lib/generated/catalogue.json`;
`scripts/build-reference.mts` renders this page. **Command:** `pnpm run generate`.

This is the answer to "does opsinjs have one of these". It is deliberately the
most boring page on the site and the one most worth trusting: every id the system
will ever resolve appears here, including the ones with no implementation and no
page, and nothing appears here that is not declared in the catalogue file.

**Six columns.** *Id* is the kebab-case name used in a URL, a registry item and a
CLI command. *Name* is the PascalCase name used in prose and in code. *Category*
groups it, and a category beginning `health-` carries extra obligations — a
clinical contract section and at least one governing doctrine page. *Status* is
one of the six [release phases](../../project/release-phases.mdx). *Aliases* are
the search synonyms, which is how "lab result" and "blood pressure" find their
way to the right row. *Page* links to the specification, where one exists.

**Considered rows are the important ones.** A row with `status: considered` is a
name we have reserved, with no specification and no implementation. It exists so
that asking about it returns a definite negative and a pointer at the alternative
rather than a 404 that invites a program to invent an API.
[ADR 0008](../../project/decisions/0008-considered-components-resolve.mdx)
records exactly how those ids resolve and why the answer is not a catch-all route.

**What is deliberately excluded.** Parts of compound components are not catalogue
entries — a dialog's panel is documented on the dialog page, not as its own id.
Examples and screens have their own registry types and are listed with the
registry, not here.

## Considered

| Component | Category | Why it is not on the roster | Reach for instead |
| --- | --- | --- | --- |
| `questionnaire` | health-input | Validated instruments are licensed, scored and interpreted by their publishers, and a component that renders one invites a product to alter its wording or its scoring. That is a clinical-safety problem no amount of API design fixes. | field, log-sheet |
| `symptom-picker` | health-input | A symptom picker is one step from a symptom checker, and a symptom checker is a regulated device in most of the markets this system targets. The controlled vocabulary is also product-specific and cannot be shipped in a design system. | field, log-sheet |
| `dose-tracker` | health-input | Dose data drives dosing decisions. A component that displays a missed dose is one product decision away from implying what to do about it, which is prescribing. | log-sheet, care-card |
| `body-map` | health-input | A body diagram must represent a range of bodies, ages, skin tones and disabilities, or it tells some readers they are not the intended user. Doing that properly is an illustration commission, not a component. | field |
| `goal-ring` | health-data-display | Goal rings are strongly associated with one platform's fitness product, and the pattern rewards streaks — which is the wrong incentive for a reader managing a condition rather than training for one. | score-dial, metric-tile |
| `timeline-entry` | health-data-display | A timeline is a layout, and every product's timeline holds different things. Shipping one would ship a data model with it. | card, relative-time |
| `scale-input` | health-input | The anchors and the number of points on a rating scale are what make it comparable over time, and they belong to whichever instrument the product is using. | field, radio-group |
| `source-citation` | health-communication | Strongly wanted and likely to be promoted. Held back only because provenance is currently doctrine rather than a component, and shipping the box before the rules would encourage products to cite whatever is to hand. | disclaimer-note, callout |
| `range-legend` | health-data-display | A legend that can be separated from its chart is a legend that will be. The bands are documented inside RangeBar instead. | range-bar |
| `toast` | feedback | A message that removes itself is the wrong shape for anything about someone's health: the reader who most needs it is the one most likely to miss it. Kept on the roster because products use toasts for save confirmations, which is legitimate. | alert-banner, callout |
| `tooltip` | overlay | There is no hover on a phone, and this is a phone-first system. Anything important enough for a tooltip is important enough to be on the screen. | term, field |
| `popover` | overlay | Base UI's popover is complete and unopinionated, and opsinjs has nothing to add to it beyond tokens. | sheet, dialog |
| `tabs` | navigation | Delegated to Base UI unchanged. Documented in the handbook rather than re-wrapped. | segmented-control |
| `accordion` | navigation | Delegated to Base UI unchanged. Note that hiding a safety message inside a collapsed section is a defect regardless of the component used. | card |
| `select` | actions-and-forms | Delegated to Base UI. opsinjs adds guidance — for short lists a radio group is easier for the reader — rather than a component. | field, radio-group |
| `combobox` | actions-and-forms | Delegated to Base UI. The hard part in a health product is the vocabulary being searched, not the widget. | field |
| `switch` | actions-and-forms | Delegated to Base UI. A switch must never be used for consent — consent is a decision with a record, not a setting. | consent-sheet, checkbox |
| `checkbox` | actions-and-forms | Delegated to Base UI. | field |
| `radio-group` | actions-and-forms | Delegated to Base UI. Preferred over Select for anything under about seven options. | field |
| `slider` | actions-and-forms | Delegated to Base UI, and discouraged for entering a measurement: a slider cannot express precision, and a reading typed in is a reading the person meant. | reading-input, number-field |
| `number-field` | actions-and-forms | Delegated to Base UI. ReadingInput is the health-aware wrapper, and it is on the shipped roster. | reading-input |
| `textarea` | actions-and-forms | A native element that needs tokens, not a component. | field |
| `progress` | feedback | Delegated to Base UI. Never use it to show a health value: a progress bar implies a target, and most readings do not have one. | range-bar, score-dial |
| `spinner` | feedback | Skeletons are preferred throughout: a skeleton says what is arriving, and a spinner says only that something is. | skeleton |
| `badge` | data-display | Kept off the shipped roster deliberately: a generic badge next to a StatusPill is exactly how the two colour axes get mixed. If you need a badge to carry a health meaning, you need a StatusPill. | status-pill |
| `divider` | layout | A border and a spacing token. Documented in Foundations rather than shipped. | card |
| `scroll-area` | layout | Delegated to Base UI. Custom scrollbars are also a frequent cause of unreachable content at 200% text. | card |
| `tab-bar` | navigation | Application navigation is a product decision, not a design-system one. The material rung, the safe-area handling and the touch-target floor it needs are all documented. | surface |
| `segmented-control` | navigation | Likely to be promoted — it is the right control for switching a chart between day, week and month. Held back until TrendSparkline exists to use it. | tabs, button |
| `stepper` | navigation | The pattern that matters is one question per page, and that is documented in Patterns. A stepper component tends to encourage the opposite. | field |
| `menu` | overlay | Delegated to Base UI. Hiding a destructive or a safety-relevant action in an overflow menu is a defect whatever renders it. | sheet, button |
| `icon-button` | actions-and-forms | A variant of Button rather than a component, and one that needs a visible label far more often than products assume. | button |
| `link` | actions-and-forms | An element with tokens and a routing decision the product owns. What opsinjs adds is guidance about link text, and that belongs in Content and language. | button |
| `avatar` | utility | Straightforward to build and full of representation decisions — default imagery, initials for names that do not have them, and what a clinician's avatar implies about who wrote a message. | card |
| `table` | data-display | Every chart in this system ships a table twin, so a table is a requirement rather than an option — but a responsive, accessible table is a project of its own and would be the largest component here by an order of magnitude. | card, metric-tile |
| `visually-hidden` | utility | Four lines of CSS that every component here uses internally, shipped as a utility class rather than as a component so that it works outside React too. | field |
