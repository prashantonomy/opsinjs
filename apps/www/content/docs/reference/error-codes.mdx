Every warning opsinjs emits in development carries a stable code, a sentence saying what to do instead, and a link to the page that explains the rule. `warnOnce()` ships in `lib/opsinjs.ts`, which `shadcn add` copies into your project with the components. Several built components call it, and the remaining codes are allocated with no caller yet. Message wording, severity and which component raises which code may change while the components are unreviewed. The code a message carries does not.

## How the codes work

- **Flat and permanent.** Codes run from `OPSIN-0001` in allocation order, and the digits carry no meaning. A code is never reused, renumbered or removed. Adding a code is not a breaking change.
- **One code, one page.** Each code links the page that explains its rule.
- **Once per session.** A warning fires once per code and message, not once per render. The message includes the values the component passed, so two components making the same mistake print two warnings, and the second render in Strict Mode prints nothing.
- **Development only.** No warning throws. A production build strips them when your bundler applies the `NODE_ENV` guard, and where `process` is undefined the channel stays silent. Validate anything you need at runtime in your own code.
- **One source.** `tokens/errors.json` is the only place a code is authored. `scripts/build-tokens.mts` writes it into `lib/opsinjs.ts`, `lib/generated/tokens.ts` and the table below, and the next `pnpm run generate` undoes an edit to any of them.

## Handling a warning

- Treat a `safety` code as an error. The screen looks right and tells a reader the wrong thing about their own health.
- Search and parse by code, never by message text. Messages get clearer between versions, and codes do not change.
- Never work around a warning you have not read.
- Turn warnings into failures in CI if you want them enforced.
- Do not silence the console to hide them, because that silences React's hydration warnings too.
- A warning raised during server rendering appears in the server log, not the browser console.
- A message with a `{brace}` still in it is a second bug, because the component did not supply that value.
- Report a warning that fires when it should not.

## The codes

{/* opsinjs:errors:begin. Everything below is replaced by scripts/build-tokens.mts from tokens/errors.json */}

A warning is one `console.warn` call, and it looks like this. The braces are
filled from what the component passed; this is the template as authored, so
what you see below is what the code emits and not a paraphrase of it.

```text
[opsinjs] OPSIN-0001 (safety): <{component}> received both `category="{category}"` and `status="{status}"`. A surface carries one axis. Set the category on the surface and render the status as a StatusPill inside it.
  → https://opsinjs.pensievelabs.org/health/two-colour-axes
```

### Severities

3 classes, and they are a statement about consequence rather than about
how noisy the warning is.

| Severity | Codes | What it means |
| --- | --- | --- |
| `safety` | 8 | A defect that can mislead a reader about their own health. Treat as a bug, not as a lint warning. |
| `correctness` | 9 | The component will render something, but not what the author meant. |
| `hygiene` | 4 | Works today, will not survive an upgrade. |

21 codes, in allocation order. "Values in the message" names the
`{braced}` spans a component has to supply; a missing one is reported in the
warning itself rather than swallowed.
