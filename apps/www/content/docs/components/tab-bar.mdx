TabBar is the persistent bar of top-level destinations at the foot of a phone screen. It
moves the reader between whole sections of an app, one of which is current at any moment,
and it is reachable by the thumb on the small mobile surface a bottom bar belongs to.

It is presentational, and application navigation is the product's decision. The bar
reports which destination the reader chose through `onValueChange` and shows the
product's answer back through `value`, so what a choice actually does, and whether it
changes the address bar, stays with the app that renders it. That split is the whole
reason a design system can ship a bar at all without shipping a router.

## Preview

A four-destination bar with one destination current. The thing worth checking is that
the current destination is marked without a colour doing the work, so read it in
greyscale: the current item carries a heavier label, a short indicator bar along its top
edge and a lift from the muted ink to the foreground ink, and underneath all three it
carries `aria-current="page"`. Check too that every destination is at least a 44pt
target on both axes.

The exclusion that matters most is the first, and it is a question about what the choice
moves the reader between. TabBar moves between whole destinations, each its own screen
with its own address. [Tabs](./tabs.mdx) switch between views that occupy the same space
within a single screen, and [SegmentedControl](./segmented-control.mdx) sets one
parameter of a view that stays put. If the choice stays inside one screen, it is not a
tab bar.

The second thing to hold firm is the count. Two to five destinations is the range a
persistent bar can carry and still be read at a glance, and the bar warns in development
outside it rather than growing an overflow. This is not only a layout preference. A
safety relevant action, such as reporting a severe reading or reaching help, must never
be hidden behind a "More" tab or any overflow the bar could sprout, because an action a
reader cannot see is an action they cannot take in the moment they need it. If the
sections outgrow five, the fix is the app's information architecture, not a longer bar.

The parts are identified by `data-slot` and are styleable from outside; none is an
export, and there is no way to render a destination without the bar. The current
destination is marked three ways so that none is load-bearing alone: `aria-current="page"`
for assistive technology, a heavier label and an ink lift for a sighted reader, and a
short indicator bar along the top edge for greyscale and for a reader stylesheet that
strips fills. That indicator is a decorative `aria-hidden` span drawn in the foreground
ink; it deliberately has no `data-slot`, because the closed set is `tab-bar`,
`tab-bar-item`, `tab-bar-item-icon` and `tab-bar-item-label`, and this bar does not mint
a fifth.

## Content guidelines

Keep the labels short, parallel and in sentence case: one noun each, naming the section
rather than instructing the reader, so the bar reads as one set of peers. Pair each with
an icon that reinforces the word rather than replacing it, because an icon alone leaves
a reader guessing and a label alone in a cramped bar is easy to miss. Do not change a
destination's wording between screens, because a reader who learnt that this bar has
"Trends" should not meet "Charts" meaning the same section elsewhere.

Hold the bar to the destinations a reader needs constantly, and keep any safety
relevant action out on a surface where it is always visible rather than folded into the
bar or an overflow it might grow. Order the destinations the way the reader moves
through the app, with the home or default section first, and do not reorder them
between visits, because a bar whose stops move is a bar nobody can build muscle memory
for.

## Accessibility

The bar is a navigation landmark: it renders a `<nav>` with an accessible name from
`label`, so a screen-reader user can jump to it and hear what it navigates before its
destinations. `label` is required, because a nav with no name is one of several unnamed
landmarks a reader has to tell apart by trial. A missing or empty `label` raises a
development warning rather than rendering an unnamed landmark.

Each destination is its own tab stop, which is the opposite of
[SegmentedControl](./segmented-control.mdx). A segmented control is a radiogroup and one
tab stop, because its options set one parameter and a reader arrows between them. A tab
bar is navigation, where every destination is a peer a reader should be able to reach
directly, so Tab steps through them and the current one carries `aria-current="page"`.
That attribute, not any pixel, is what tells assistive technology which section the
reader is in.

The current state is carried three ways so none stands alone: `aria-current="page"` for
assistive technology, a heavier label and a lift from the muted ink to the foreground
ink for a sighted reader, and a short indicator bar for greyscale and for a reader
stylesheet that strips fills. Each destination floors its target at
`--opsin-target-minimum` in rem on both axes, so a 44pt region survives and grows with
the reader's text size rather than pinning at a device pixel, and the focus ring is
carried in the item's own class list rather than left to the product stylesheet. What is
not yet checked is listed rather than left out, and it matches the open questions at the
top of this page: no contrast pair has been measured for the current treatment against
the overlay material; nobody has listened to the bar in a screen reader; the safe-area
padding has not been tested on a notched device; and there is no `forced-colors` or
`prefers-contrast: more` rule.

## API reference

<PropsTable name="TabBarProps" />

`value` makes this a controlled component with no internal selection state: the caller
stores the current destination's key and passes it back, and a `value` that matches no
item renders the bar with nothing current and raises a development warning.
`onValueChange` is optional, because a bar built from links can leave navigation to the
`href` alone, but a bar built from buttons needs it to report the reader's choice.
`label` is required because a navigation landmark with no accessible name is a defect
the type system cannot otherwise prevent.

<RelatedComponents name="tab-bar" />

**Easily confused with**

- [Tabs](./tabs.mdx) switch between views that occupy the same space inside one screen.
  TabBar moves between whole top-level destinations. If the choice stays inside one
  screen, it is tabs.
- [SegmentedControl](./segmented-control.mdx) sets one parameter of a single view rather
  than navigating. If nothing moves the reader to another section, it is a segmented
  control.
- [Menu](./menu.mdx) is a list of actions opened from a button. TabBar's destinations
  are always visible, which is the point of a persistent bar, so a set of stops a reader
  has to open a control to see is a menu, not a tab bar.

**Used by**

- No pattern, recipe or screen composes it yet. It is built to sit at the foot of an app
  shell, and assembling that shell is a product's to make rather than something the
  corpus ships today.
