Switch is a labelled on-or-off control that takes effect the moment it is flipped. Its home is a single setting a reader turns on or off and sees the result of straight away, and the case it was built for is a preference in a settings list, a "Larger text" toggle that changes the text the instant the thumb slides across.

The design decision that shapes the whole component is that it commits on the flip rather than on a later submit. A switch is not a form value gathered until the reader presses a button: the setting it names is different as soon as the reader moves it, which is why it is controlled only, with the caller holding the boolean, applying the effect, and passing the new value straight back. A value that is proposed and submitted later is a checkbox, and the difference decides which component you reach for.

It renders no icon and composes no other component.

<WhenToUse
  use={[

  avoid={[

    { case: "The value is proposed now and submitted later with a form, rather than taking effect the moment it changes.", instead: "checkbox" },

The exclusion that matters is the first, and it is the reason this component was kept off the roster for so long. A switch is a setting, and a setting carries no record: it says what the state is now, not who chose it or when, and it is flipped back with a single press. Consent needs all of that, so the moment a toggle would stand for the reader agreeing to a thing, it belongs in a [ConsentSheet](./consent-sheet.mdx), which keeps the decision and the record together. A switch that records consent loses both.

The second exclusion keeps a switch apart from a checkbox, and the test is when the change takes effect. A switch commits on the flip, so the setting is different before the reader does anything else. A [Checkbox](./checkbox.mdx) inside a form proposes a value that the form gathers and submits on the reader's command, so nothing happens until they press submit. If the reader expects to review and submit, it is a checkbox; if the effect is immediate, it is this control.

The parts above are identified by `data-slot` and are styleable from outside; none of them is an export, and there is no way to render the track without the row. Base UI's Switch also renders a visually hidden `<input>` beside the track, which carries a form value when the switch is given a `name`. This component passes no `name`, so that input submits nothing; it is out of the tab order and changes nothing a reader meets, and it is named here rather than left for someone to find in the DOM.

There is no `Switch.Indicator` and no icon slot. The on state is the track's fill and the thumb's position, not a separate mark, and adding a tick beside the thumb would be a second carrier for a state the fill and `aria-checked` already carry.

## Content guidelines

Name the setting the switch turns on, not its state and not an instruction. "Larger text" reads at a glance and stays true whichever way the switch is flipped, while "On" says nothing about what is on and "Turn on larger text" reads as a button rather than a setting. Keep the label to a few words in sentence case, and let it carry no terminal punctuation.

Use the helper line for what the setting does, not to repeat the label. A line such as "Increases the text size across the app" earns its place; a line that says "Makes the text larger" beside a "Larger text" label is noise. Never write a clinical reading, a threshold or a unit into a switch or its helper, because a switch sets a preference and asserts nothing about a measurement.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The switch draws only the neutral chrome roles and the bridged primary fill, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size, no banned word.** The label is the `body` step and the helper line the `footnote` step rather than pixel sizes, so a reader who has turned their text size up gets a larger row, and no reading-facing copy or identifier reaches for a word the glossary bans.

**Argued, and true of the implementation, but not yet measured:**

- **The whole row is the target.** The root is a label element, so the words and the track are one pressable region, and the row floors its height at `--opsin-target-minimum` in rem. That it clears 44 by 44 in a real browser is the layout half of the check, which has not been run for this component.
- **The state has two carriers and survives greyscale.** `aria-checked` reflects the caller's boolean, the thumb sits left for off and right for on, and a hairline keeps the thumb legible when the fill is stripped, so the state is never told by colour alone. This is true of the code and has not been heard in a screen reader.
- **At 200% text the row grows with the text.** The label and helper are type steps and the gaps are space tokens, so the whole row scales rather than clipping.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the card thumb against the primary fill in the on state and against the muted fill in the off state, and the hairline around the thumb and the track. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the switch draws under `forced-colors: active` and `prefers-contrast: more`, where the fills are replaced by the platform's own pair, and how the thumb travels under a right-to-left layout, where it should slide the other way. And `prefers-reduced-motion` is not honoured: the thumb's slide and the track's fade run whether or not the reader has asked for less motion.

## API reference

<PropsTable name="SwitchProps" />

`checked` and `onCheckedChange` make this a controlled component with no internal state: the caller holds the boolean, applies the effect the moment the switch is flipped, and passes the new value straight back. `label` is required because a switch with no accessible name is a defect the type system cannot otherwise prevent, and a missing or empty label raises a development warning rather than rendering an unnamed control. `description` is an optional helper line read as the control's description rather than as part of its name, and `disabled` keeps the switch visible and labelled while refusing focus and every key.

**Easily confused with**

- [Checkbox](./checkbox.mdx) proposes a value that a form gathers and submits on the reader's command. A switch commits on the flip. If the reader expects to review and submit, it is a checkbox.
- [ConsentSheet](./consent-sheet.mdx) records a decision with a who and a when. A switch is a setting with no record, flipped back as easily as it is set, so a toggle that would stand for consent is a consent sheet instead.
- [SegmentedControl](./segmented-control.mdx) chooses one of a small set of mutually exclusive options. A switch is the two-state case where the choice is on or off and the label names the setting rather than the options.

**Used by**

- No pattern, recipe or screen composes it yet. It is a neutral control a product drops into its own settings list and wires to its own preference state.
