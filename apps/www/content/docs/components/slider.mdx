Slider sets a single coarse value by dragging a thumb along a track. Its home is a rough, non-clinical preference, such as a brightness level or a fuzzy nought to a hundred sense of "how much", where the exact number does not matter and the gesture of sliding towards more or less is the whole interaction.

The rule that shapes the component is the one thing it must never do. A slider cannot express precision, because the thumb lands on whatever pixel the finger left it on, snapped to a step the control chose. A measurement is a number the person meant, so a reading is typed rather than dragged: use [ReadingInput](./reading-input.mdx) for a measurement with clinical semantics and [NumberField](./number-field.mdx) for a precise quantity with none. This control is for a preference, and the pages below say so more than once on purpose.

The control is built on Base UI's Slider primitive, which is where the drag tracking, the roving value, the keyboard stepping and the hidden range input for assistive technology all come from, so installing it pulls in `@base-ui/react`. It renders no icon and composes no other opsinjs component.

## Usage

```tsx
import { Slider } from "@/components/ui/slider"
```

```tsx
<Slider
  label="Screen brightness"
  value={brightness}
  onValueChange={setBrightness}
/>
```

The exclusion that matters is the first, and it is the reason a slider is discouraged so firmly on a health surface. A slider cannot express precision: it has no way for the reader to say "one hundred and eighteen" rather than "about a hundred and twenty", so a reading dragged onto a track is a reading nobody quite meant. A measurement is a number the person meant, so it is typed into a [ReadingInput](./reading-input.mdx), which owns the unit, the parsing and the plausibility checks a reading needs. The moment a value has a clinical meaning, this is the wrong control, and the type system cannot make that call for you because a brightness and a heart rate are both numbers.

The second exclusion keeps a slider from standing in for a precise field. A count of servings or an exact amount the reader has in mind is a [NumberField](./number-field.mdx), where the digits are typed and stay exactly as entered. A slider is for the value nobody needs to the unit, and reaching for one where the digits matter hands the reader a control that cannot hit them.

The parts above are identified by `data-slot` and are styleable from outside; none of them is an export, and there is no way to render a thumb without the group. The label and the value sit in a header row above the control, and that row is a plain layout wrapper with no slot of its own, because it carries no state a caller would need to reach. There is deliberately a single thumb and no range form: this control is for one coarse preference, and a two-thumb range is a different component with a different keyboard contract.

## Content guidelines

Name the preference the slider sets, not the act of sliding: "Screen brightness" reads better than "Drag to set brightness", because the label is the control's accessible name and a screen-reader user hears it before the value. Keep the label to the thing being adjusted so the readout beside it is understood as that thing's amount.

Do not put a unit or a clinical figure in the readout. A slider shows a rough position, so a value with a unit invites the reader to treat it as a measurement, which is exactly what this control cannot deliver. When a number needs a unit or has to be exact, the readout belongs to a [ReadingInput](./reading-input.mdx) or a [NumberField](./number-field.mdx), not to a slider.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The control draws only the neutral chrome roles and the bridged `primary` fill, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size, no oversized radius.** The label and the readout are the `subheadline` semantic step rather than a pixel size, and the track, knob and thumb use the token radii, so a reader who has turned their text size up gets a larger control instead of a pinned one.
- **A 44px target on the thumb.** The thumb's hit area is floored at `--opsin-target-minimum` on both axes, in rem, so the pressable region is a comfortable target that grows with the reader's text size even though the visible knob is smaller.

**Argued, and true of the implementation, but not yet measured:**

- **The label names the control for assistive technology.** Base UI wires the visible `Slider.Label` to the thumb's hidden range input through its field context, so the input announces the name, and a missing or empty `label` raises a development warning rather than rendering an unnamed control.
- **The focus ring is carried by the component.** The ring is in the thumb's own classes, keyed off the nested input's `:focus-visible`, so a project installed without the product stylesheet still gets a visible ring on the knob rather than nothing.
- **The value has a text form.** The `Slider.Value` readout mirrors the thumb's value as text beside the label, so the current position is visible to a sighted reader and not only carried by the thumb's place on the track.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the card knob against the primary fill and the muted track, the primary fill against the muted track, and the focus ring against all three. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the control draws under `forced-colors: active`, where the knob, the fill and the track are all replaced by the platform's own pair, and whether a screen reader speaks a useful value phrase rather than a bare figure. None of this has been put in front of a machine or a screen-reader user.

## API reference

<PropsTable name="SliderProps" />

`value` and `onValueChange` make this a controlled component with no value of its own: the caller stores the number and passes it back. `label` is required because a control with no accessible name is a defect the type system cannot otherwise prevent, and a missing one raises a development warning. `min`, `max` and `step` set the range and the granularity, and a coarser `step` is the honest choice for a preference nobody needs to the unit. `disabled` still shows the value and keeps it readable rather than fading it out of contrast.
