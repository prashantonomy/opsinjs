A disclaimer that appears everywhere is read nowhere, and a disclaimer that appears nowhere
is a liability. This component exists so the placement decision is made once, in the system,
rather than twenty times by twenty different people under deadline. What it does not do is
supply the words, and that refusal is the larger half of the component.

Repetition is the failure mode this component exists to prevent. One note per surface, placed
by the rule, and never repeated beside every individual result: a screen that seems to need
four notes is a screen showing four things that each need explaining, and four identical
notes will explain none of them. The component does not enforce that, because it renders
where it is put and cannot see a second copy of itself. The rule therefore lives in review,
and the example below is what it looks like when it is kept.

## Clinical meaning

**What it asserts.** That this product provides information rather than clinical assessment,
that it does not replace advice from a clinician, and that it is not a medical device. The
third of those is asserted where it is relevant. It asserts those things in the product's own
words. The component supplies the position, the type size, the ink and the boundary, and not
one syllable of the content.

**What it must never be read as.** A waiver, an excuse, or a substitute for designing safely.
A disclaimer does not make an unsafe screen safe, and no regulator, and no reader, has ever
been persuaded otherwise. It also must never be read as *this number is unreliable*: the
note is about the product's role, not about the quality of the measurement.

**Which colour axis it may use.** Neither, and this is the one component where the two-axis
rule is answered by absence rather than by a choice. There is no `status` prop and no
`category` prop, the root carries neither `data-status` nor `data-category`, and there is no
fill of any kind. Status colour on a standing disclaimer is a permanent false alarm, because
it says the same level on every screen, from first launch to last, about nothing in
particular. Category colour makes a legal statement look like a topic. See
[The two colour axes](../health/two-colour-axes.mdx).

**Where it goes.** Below the content it qualifies, above the surface's footer, once per
surface. Never above the result. A reader who came to see a number should see the number
first. Never in a collapsed section, and never in a modal the reader must dismiss before
they can read the thing they came for. `placement` is the prop that says which of the two
positions this note is in; it changes the space above the note and nothing else, because a
placement that also changed the treatment would be a second way to make the note louder.

**Who owns the words.** The consuming product, in consultation with whoever is accountable
for it. opsinjs does not ship legal text, and nothing on this page is legal advice.
[Regulatory context](../health/regulatory-context.mdx) sets out what DCB0129, DCB0160, the
EU MDR and FDA SaMD expectations ask of the *consuming* product. The design system confers
no status of any kind. The implementation is written so that this cannot be got round by
accident: there is no default string, no placeholder, no vetted variant and no translation
key with a fallback, and a note rendered with nothing in it prints an admission that nothing
was supplied.

<SafetyCallout severity="attention" evidence="opinion">
If a product finds itself relying on this component to make a screen acceptable, the screen
is the problem. Fix the screen. The note exists to set expectations honestly, not to
transfer risk onto the reader.
</SafetyCallout>

That is the whole component, deliberately: every part that could be added is a part that
could be used to make the note louder. The parts are identified by `data-slot` and are
styleable from outside; none of them is an export, and there is no way to render one without
the root. The one part the specification did not name is `DisclaimerNote.Version`, and it
exists because `textVersion` had to go somewhere a person could read it. The
[API reference](#api-reference) has the reasoning.

There is no `DisclaimerNote.Heading`, no `DisclaimerNote.Actions` and no dismiss control. A
note with a heading is a section; a note with an action is asking the reader to do something,
and an instruction with somebody behind it is a [CareCard](./care-card.mdx).

The placement rule is the component. The example shows three rows and one note underneath all

### When nobody wrote the words

Legal copy arrives from a content service, a translation table or a flag saying whether the
current wording has been reviewed, and every one of those can return nothing without anybody
noticing. The note prints an admission rather than rendering empty, because an empty one
passes review, passes every gate in this repository, and reaches a reader as a surface whose
standing statement has silently gone missing. [EmptyState](./empty-state.mdx) refuses in the
same shape and for the same reason.

The boundary is worth stating, because it is narrower than that promise sounds. The note
detects missing *words*: `undefined`, `false` from an `&&` branch, `0` from the same branch on
an empty collection, an empty array, a whitespace-only string and a body that is nothing but a
number are all read as none supplied. A caller who wraps the copy in an element is taken at
their word, and an empty `copy.text` inside `<strong>{copy.text}</strong>` still renders an
empty note with no admission and no development warning. Printing *this app has not added its
notice about what it can and cannot do* over somebody's own markup would be a false accusation
on their screen, so the component does not;
the cost is that this one route stays open, and it is stated here rather than left for a
reader to find.

## States

The note itself is not interactive. It is a server component with no state, no hook, no
event handler and no dismiss control, so it has no hover, pressed or disabled state of its
own. The one focusable part is the link, present only when `more` is supplied, and its
states are decided by [Link](./link.mdx): a focus ring and a one-pixel press. Hover adds
nothing, because the underline is the rest state and there is no quieter state for hover to
lift from, and the disabled, selected and loading states do not apply, because a note's link
is never turned off, chosen or pending.

The five canonical [data states](../foundations/data-states.mdx) mostly do not apply here,
because this component carries no reading. It is a standing statement about what the product
is, not a display of a measurement, so it holds no value to be in error, loading, partial or
stale about. The one state it does own is the absence of its words, and it makes that absence
visible rather than rendering empty.

| Data state | What DisclaimerNote renders |
| --- | --- |
| Error | No error state of its own. The component fetches nothing and holds no reading. Copy that fails to arrive upstream reaches the note as no words, which it handles as the empty row below rather than as an error. |
| Loading | No skeleton and no spinner. It renders synchronously with whatever children arrive, and a surface still loading its copy passes no words, which is again the empty row below. |
| Empty | The one state the component makes visible itself. With no words supplied, meaning `undefined`, `false` from an `&&` branch, `0` from that branch on an empty collection, an empty array or a whitespace-only string, it prints one line saying the app has not added its notice, and raises a development warning. A body wrapped in an element is taken at its word, so an empty string inside `<strong>` is the one route to a silently empty note. |
| Partial | No partial state. The note is one or two sentences plus the optional icon, link and version marker. A note with words but without a `more` link or a `textVersion` simply omits those parts, which is the ordinary shape rather than a degraded one. |
| Stale | No staleness of its own. The note carries no timestamp. `textVersion` records which wording a reader saw, and the component renders it exactly as written without comparing it to a current version or flagging an old one, because deciding that a note's wording is out of date belongs to the product. |

## Content guidelines

Two sentences at most. Say what the product does, then what it does not do. Use plain words:
*this app*, not *the Service*; the concrete role a reader would recognise rather than *a
qualified healthcare professional*, unless a specific obligation requires the formal phrase.
That role is *a doctor or nurse* in the UK, and whatever those roles are called where the
product is used. The register is part of what has to be written locally: a care system's job
titles do not travel, and a sentence carried across from another one names people the reader
has never dealt with.

The commonest wrong note is the blanket instruction to seek professional advice before
doing anything, which every app carries at the foot of every screen. It is not written
out here, for the same reason nothing else is: a sentence in that shape, in a design
system, is a sentence somebody pastes. It is worth naming as a shape because it is
unactionable, it is not what the reader is being asked to do at that moment, and repeated
often enough it teaches people that the app has nothing useful to say.

No usable disclaimer sentence appears anywhere on this page, and the omission is the point
rather than an oversight. Individual words are discussed, because that is what guidance about
wording has to do. The discussion covers a register, a job title and the shape of a wrong
note; what is never written is a sentence that could be lifted whole. A two-sentence note
written here would name no product. Naming no product is exactly what would make it fit every
product, and the note would reach the next one looking reviewed, because it came from the
design system. The words are written by whoever is legally accountable for the consuming
product, in consultation with whoever is accountable for its clinical safety, in that
product's own language and for its own jurisdiction. opsinjs is not that owner and cannot
become one; what the pair below describes is the shape those sentences should have,
not the sentences.

<DoDont>
  <DoDont.Do>
    **Name what the product does, then the one limit that matters most to this reader. Write
    each in one sentence, in the product's own register.** Role before limit, because a reader
    who does not yet know what they are looking at has nothing to attach a caveat to.
  </DoDont.Do>
  <DoDont.Dont>
    **Open with the product's registered trading name, stack four abstract nouns for the
    things it is not, and close by placing reliance on the reader.** Written for a court
    rather than for a reader, and the closing move is an attempt to shift risk rather than to
    inform.
  </DoDont.Dont>
</DoDont>

<DoDont>
  <DoDont.Do>
    **One quiet note beneath the results, in the same place on every results screen.**
    Predictable, findable, ignorable by people who have read it once.
  </DoDont.Do>
  <DoDont.Dont>
    **A yellow warning-styled panel at the top of every screen.** It occupies the position the
    reader's actual information should have, it looks like an alert, and within a week nobody
    sees either.
  </DoDont.Dont>
</DoDont>

Name the link for where it goes. *Read our full statement* and *how this app uses your
readings* are destinations; *learn more* is not, and a screen reader can list every link on a
page with no sentence around any of them. `more` takes the label and the destination together
so that a link cannot be added without one, and a label from a short list of vague ones raises
a development warning. That list is nine English strings, so the identical failure in another
language is not caught, and the check covers one language of the many the requirement is
written for. The failure it misses is a literal translation of *learn more*.

If `textVersion` is used, write something a reader could quote back in a support conversation
rather than an internal identifier. It is rendered exactly as written, with no word added
around it, because any word this system added would be English in a note that may be read in
any language.

The same limit reaches one sentence the component owns rather than the caller. When no words
are supplied it prints its own admission, and that line is English. There is no prop through
which a product can translate it, for the reason the version marker carries none: any wording
this system shipped would be English in a note meant to be read in any language. A product
shipping in another language should therefore guard the missing case upstream, supplying its
own copy for it rather than relying on the component to speak, and the absence of a
translation seam here is deliberate and recorded in
[ADR 0005](../project/decisions/0005-no-lang-segment-yet.mdx).

## Motion

This component declares no motion. There is no transition, no animation, no transform, and
no duration or easing token anywhere in the source or in either example, so it reads no token
from `tokens/motion.json` and there is nothing for `prefers-reduced-motion` to reduce. That
is a deliberate answer rather than an omission: a standing legal statement that faded, slid or
counted itself in would be asking for the attention the component exists to withhold, and the
note appears in its final position on first paint.

The component also renders no health value, so the rule that a health number is never animated
on first paint has nothing here to bind to. It is worth stating anyway, because the rule is why
this note would refuse a count-up or a sweep even if it ever showed a reading: a value that
animates in reads as a value still settling, which is the wrong thing to say about a number a
reader is being asked to act on.

## Accessibility

Some of what follows is checked by a gate on every commit and the rest is argued. They are
labelled separately, because `beta` promises that accessibility is claimed only where it has
been checked, with the gaps listed rather than left out. Nobody has yet listened to this
component in a screen reader.

**Checked, by `pnpm run check:a11y` on every commit:**

- **No `px` type size anywhere.** The one type step this component uses is `text-opsin-body`,
  which is a rem from the generated ramp, so the note scales with the reader's own text size
  and with `[data-text-size]` rather than staying put at a fixed size. This is what makes
  *at least the body text size, and it scales at 200%* checkable rather than asserted.
- **No raw colour literal and no ramp step.** The ink and the hairline are the neutral
  `--foreground` and `--border` roles, so they follow the theme; a hex, an `oklch()` or a
  numbered ramp step fails the build.
- **Nothing that resolves to nothing under the product theme.** `bg-secondary`, `bg-accent`
  and `bg-destructive` exist only in the documentation chrome, and the gate fails on any of
  them. That matters here because every one of them is a fill somebody would reach for to
  make a disclaimer stand out.
- **No banned word in the one reader-facing string this component owns, none in its
  development warnings, and none as a code identifier.** That single string is the line
  printed when no words were supplied, and it is the only sentence the component itself
  puts in front of a reader.
- **No shipped threshold and no unowned numeric interval.** No clinical number is written
  into this component and none passes through it: no threshold, no reference range, no score
  band, no plausibility bound and no staleness boundary, which is the honest shape for one
  that says nothing about a reading. That, and only that, is what the gate checks. The
  numbers the file does contain are layout steps and the target-size fallback described
  below, and it audits neither.

**Enforced by the API rather than by a gate:**

- **If an icon is present it is never a warning triangle.** `icon` is a boolean and the glyph
  is not a prop, so there is no `ReactNode` for a triangle to arrive in. The shape sets the
  register before a word is read, and a component that accepted an arbitrary node could only
  ask callers not to.
- **The link names its destination.** `more` carries the label and the href together, so a
  link cannot be added without a label, and the label this system would otherwise have had to
  invent is exactly the one the requirement refuses.
- **It cannot be tinted from either axis without being told.** There is no colour prop.
  `className` reaches the root, which is the one hole, and a class from either axis raises a
  development warning naming what to use instead.

**Argued, and true of the implementation, but not yet measured:**

- **The note is ordinary text in the reading order.** No `role`, no `aria-live`, no
  `role="alert"`, and nothing that announces itself over what the reader is doing.
  [AlertBanner](./alert-banner.mdx) is the one component in this system entitled to speak,
  and styling a disclaimer as one is the most common mistake with this component. The cost of
  a plain element is real and is not hidden here: a screen-reader user meets the note as two
  loose sentences with no boundary and no name. `role="note"` or a named `<aside>` would
  supply one; neither is adopted on a guess, and a landmark on every screen for a sentence
  that never changes is its own kind of noise. It is an open question above.
- **It meets the same contrast floor as body text**, because the statement and the link use
  the same two roles as body text. There is no muted role and no footnote step on either of
  them, the parts a reader has to read; the single exception is the version marker, which
  takes the footnote step in the secondary ink precisely because it is the note's identifier
  and not its message. Legal text set one step down in pale grey complies with the letter of
  a requirement and none of its purpose. The neutral pairs the note draws its colour from are
  measured and published in the table below, and the ink pair clears the body floor by a wide
  margin in both themes. The chrome roles the note uses do not stand on their own: each
  resolves through an `--opsin-chrome-*` role to a step on the `--opsin-neutral-*` ladder, so
  `--border`, the colour of the one boundary this note draws, is a measured ladder step rather
  than an independently authored value. Read that boundary in the `border-on-page` and
  `border-on-card` rows, which measure the exact token the border uses, once the contrast
  table is regenerated. One row below is not a verdict on this note: `neutral.hairline-on-page`
  measures a grouping cue drawn between two list rows and not the edge this component draws, so
  do not read its figure as this note's result. See
  [Contrast conformance](../accessibility/contrast-conformance.mdx).
- **It reflows at 200% text** without truncating and without horizontal scroll: no fixed
  height, no overflow container, `min-w-0` with `wrap-break-word` on the paragraph and on the
  version marker, and `wrap-anywhere` on the link. The link needs the stronger of the two and
  it is worth saying why, because it is the part a caller's own text arrives in: the anchor is
  a grid item, so its `inline-flex` blockifies to `flex` and its label becomes an anonymous
  flex item whose minimum size `min-w-0` does not reach and `break-word` does not reduce.
  `anywhere` does. So a long word or a bare URL breaks in all three parts rather than widening
  the layout past the viewport. Reasoned from the CSS; the measurement belongs to the nightly
  layout job.
- **There is no motion to reduce.** No transition, no animation, no transform, no duration or
  easing token and no entrance treatment anywhere in the component or either example, so
  `prefers-reduced-motion` has nothing here to act on and the component declares no handling
  for it. Listed because the absence of a requirement is still an answer to it, and a reader
  should not have to read the source to establish that there is nothing here to reduce.
- **The 44x44 target floor is written twice, and nothing checks the two copies agree.** The
  link declares `min-h-(--opsin-target-minimum,2.75rem)` and the same on the inline axis, and
  the `2.75rem` inside the `var()` is a second copy of what the space tokens publish. It is
  there because a bare `var(--opsin-target-minimum)` is invalid at computed-value time in a
  project that installed this file without the generated token stylesheet. `min-height`
  reverts to `auto` and the floor goes with it, silently. The cost is that raising the token
  would leave this copy behind for exactly the consumers the fallback exists to protect, and
  no gate in this repository compares them. [Card](./card.mdx) declares the same floor with no
  fallback, so the two components disagree about this and one of them is wrong.
- **Print includes the note.** Nothing here is `print:hidden`, and there is no fill to lose:
  a browser drops background colours on paper unless the reader has changed a setting, and a
  component whose whole treatment is a hairline and some space survives that. The dark-theme
  case that [Callout](./callout.mdx) once recorded as outstanding is now answered in the theme
  layer: its `@media print` block takes all four selector groups, the two light roots and the
  two dark ones, to black ink on a white page, so a note printed from the dark theme is no
  longer near-white on white. The one residual left to the reader is their own browser setting
  for whether background colours print at all.
- **Its one boundary widens under `prefers-contrast: more`.** The root carries a
  `contrast-more:` rule on the top border, so the hairline thickens to the emphasis width,
  `--opsin-border-emphasis`, when a reader asks the platform for stronger contrast. This is
  the model [Surface](./surface.mdx) already uses for its edge, so a card the note sits in
  and the note's own boundary answer the same setting together. The rule changes the border
  width and not its colour, so it moves no contrast ratio; what nobody has measured is
  whether a thicker line at that ratio reads as a boundary on a phone outdoors, which is a
  question for a browser rather than for the source.

**Not yet checked at all, and listed rather than omitted:**

- This component declares no `forced-colors` rule, and nothing here is tested against a
  forced-colours palette, so a reader in that mode meets whatever the browser substitutes
  rather than a treatment this note chose. The gap is in this file, not in the system: other
  components do answer forced colours in their own utilities, among them
  [Button](./button.mdx), [Field](./field.mdx), [RangeBar](./range-bar.mdx),
  [Sheet](./sheet.mdx), [ScoreDial](./score-dial.mdx) and
  [TrendSparkline](./trend-sparkline.mdx). This note simply has not been given one yet.
- The link's hit area. The floor is declared in rem on both axes so that it grows with the
  reader's text size rather than pinning at 44 device pixels, and no browser has measured it.
  See [Target size and motor](../accessibility/target-size-and-motor.mdx).
- Whether a reader using a screen reader finds the note at all, given that it has no
  boundary. That is the open question above rather than a measurement waiting to happen.
- How `textVersion` is announced. It renders as a bare span with no label, no association with
  the paragraph it versions and no word around it. That last absence is by design, since any
  word added would be English. A listener therefore meets it as a fragment arriving straight

  footnote size and the secondary ink, to tell them what it is; a listener still has neither. Whether visible text is the
  right home for the marker at all is the third open question above.

## Data attributes

Every part is addressable from outside by a `data-slot`, so a surface can adjust the note's
layout without reaching for a class the component does not publish. The root and the statement
paragraph are always present; the glyph, the link and the version marker each appear only when
the caller asks for them. What is not here is the point of the table as much as what is: the
root carries neither `data-status` nor `data-category`, and there is no `data-opsinjs-value`,
because the note sits outside both colour axes and displays no measurement. This is the
two-axis rule answered by absence rather than by a choice of which axis to use. The glyph also
carries `aria-hidden="true"`, because it is a scanning aid and a duplicate of what the words
already say.

## CSS variables

<CssVariablesTable name="disclaimer-note" />

The component declares no custom property of its own. Its colours are the semantic token
roles, `--foreground` for the ink, `--border` for the hairline and `--muted-foreground` for
the version marker, read straight from the token layer and listed under Tokens below. It does
read a few token custom properties inside `var()`, among them `--opsin-target-minimum` for the
link's target floor, `--opsin-measure-comfortable` for the paragraph's measure and
`--opsin-border-emphasis` for the thicker hairline under `prefers-contrast: more`, each with a
literal fallback so the declaration stays valid in a project installed without the generated
token stylesheet. Reading a token is not authoring one, so there is no tier-3 property to
document here.

## Tokens

These are the tokens the component reads, resolved by `scripts/build-tokens.mts` from the token
source rather than listed by hand, so the table cannot drift from what the component actually
consumes. A health component never reads a category token and a status token onto one element,

## API reference

<PropsTable name="DisclaimerNoteProps" />

`children` is typed optional and is required by the contract, which is the same shape
[EmptyState](./empty-state.mdx) uses. Marking it required buys nothing, because `{copy.text}`
with an undefined `copy.text` type-checks either way. It costs the ability to render the
missing state at all, which is the state that most needs seeing.

`textVersion` renders as visible text. An attribute would be tidier and would be a record only
the product that already had the value could read: it survives no screenshot, no printout and
no support ticket. The data-attribute vocabulary is closed at four in any case, so a fifth
would be a change to the system rather than to this component.
