SegmentedControl is a row of mutually exclusive options where exactly one is chosen at a
time. Its home is switching a single view between a small set of windows, and the case it
was built for is a chart's day, week or month range, where all the options are worth showing
at once rather than folding into a menu.

The design decision that shapes the whole component is that it is one tab stop. A reader
arrowing along a row of options expects Tab to pass the row, not to stop on each option in
it, so the control is a radio group: the group takes the single tab stop, and the Arrow keys
move a roving focus between the options inside it.

## Preview

A three-option row with one segment chosen. The thing worth checking is whether the options
read as siblings and the chosen one is lifted without a colour doing the work, so read it in
greyscale: the selection is carried by the card surface lifting the segment off the muted
track and by a hairline around it, and underneath both by `aria-checked` rather than by any
pixel at all.

The exclusion that matters is the first, and it is a question about what the choice does.
A segmented control sets a parameter of one view: the chart stays the chart, and the option
chosen changes the window it is drawn for, which is a single-select input and so a
radiogroup. [Tabs](./tabs.mdx) swap between distinct panels of content, each with its own
material, which is a different pattern with a different keyboard contract. If choosing an
option replaces what is on the surface, it is tabs; if it changes one setting of what stays
on the surface, it is this control.

The second exclusion is the honest limit of the form. A segmented control has to fit on one
row and be read as one set, so once the options pass about five, or the labels grow past a
word or two, a [Field](./field.mdx) with a select is the control that still works. Reaching
for a segmented control there produces a row that wraps or scrolls sideways, and a wrapped
segmented control is no longer one legible set of siblings.

The parts above are identified by `data-slot` and are styleable from outside; none of them is
an export, and there is no way to render a segment without the group. Each Radio also renders
a visually hidden `<input type="radio">` beside its span, which Base UI uses to carry a form
value. This control passes no `name`, so that input submits nothing; it is `aria-hidden` and
out of the tab order, so it changes nothing a reader meets, and it is named here rather than
left for someone to find in the DOM.

There is no `SegmentedControl.Indicator` and no icon slot. The selected state is the segment's
own surface and boundary, not a separate mark, and adding a tick beside the label would be a
second carrier for a state the fill and `aria-checked` already carry.

## Content guidelines

Keep the labels short, parallel and in sentence case: one or two words each, the same part of
speech, so the row reads as one set of siblings. Name the value the option sets, not an
instruction to the reader, and let the options carry no terminal punctuation.

Order the options the way the reader thinks about them rather than the way the data is stored:
a day, week and month window runs shortest to longest, and reversing it to match a database
column is the row nobody can scan. Do not change a label's wording between screens for the
same option, because a reader who learnt that this control offers "Week" should not meet "7
days" and "Weekly" meaning the same window elsewhere.

<DoDont>
  <DoDont.Do>
    **"Day" · "Week" · "Month"** Three parallel windows, each a single word, ordered shortest
    to longest, so the set reads at a glance and the choice is obvious.
  </DoDont.Do>
  <DoDont.Dont>
    **"Today" · "This week's readings" · "Show me the month"** Three different lengths and
    three different grammars, so the row no longer reads as one set and the labels compete with
    each other rather than sitting as siblings.
  </DoDont.Dont>
</DoDont>

## Accessibility

The control is a radio group, which is what makes it one tab stop with a roving focus rather
than one stop per option. Base UI's RadioGroup renders `role="radiogroup"` on its Composite
primitive, each segment is a Radio rendering `role="radio"` with `aria-checked`, and selection
follows focus, which is the WAI-ARIA radio group pattern rather than a bespoke one nobody has
tested. The single tab stop is the contract this control exists to keep, and it is the reason
it is not built by composing the shipped [Button](./button.mdx): Base UI's `useButton` stamps
a tab index on every control it renders, so a row of four Buttons would be four tab stops.

The radiogroup needs an accessible name, and `label` is required for it. It is applied as the
group's `aria-label`, so a screen-reader user hears what the row selects before its options.
Without it a reader hears a set of radios with no idea what they set, so a missing or empty
`label` raises a development warning rather than rendering an unnamed group.

The selected state is carried three ways so none of them stands alone: `aria-checked` for
assistive technology, the card surface lifting the segment off the muted track for a sighted
reader, and a hairline around the selected segment for greyscale and for a reader stylesheet
that strips fills. A disabled segment drops to the measured muted ink rather than being faded
with opacity, so it stays readable while reading as unavailable, and the Arrow keys skip it.

The focus ring is carried in the segment's own class list rather than left to the product
stylesheet, for the reason [Link](./link.mdx) gives: a project installed without that
stylesheet would otherwise lose the ring silently. Each segment floors its target at
`--opsin-target-minimum` in rem on the vertical axis, so a 44pt pressable region survives and
grows with the reader's text size rather than pinning at a device pixel.

What is not yet checked is listed rather than left out, and it matches the open questions at
the top of this page. No contrast pair has been measured for the selected segment against the
track or for the track's hairline; nobody has listened to the control in a screen reader;
Home and End are not bound, because the RadioGroup primitive disables them, so they keep the
browser's default; and there is no `forced-colors` or `prefers-contrast: more` rule, so a
reader in either mode meets whatever the browser substitutes.

## API reference

<PropsTable name="SegmentedControlProps" />

`value` and `onValueChange` make this a controlled component with no internal selection state:
the caller stores the chosen value and passes it back, and a `value` that matches no option
renders the row with nothing chosen and raises a development warning. `label` is required
because a radiogroup with no accessible name is a defect the type system cannot otherwise
prevent.

## Related

<RelatedComponents name="segmented-control" />

**Easily confused with**

- [Tabs](./tabs.mdx) swap between distinct panels of content, each with its own material. A
  segmented control sets a parameter of one view that stays on the surface. If choosing an
  option replaces what is shown, it is tabs.
- [Field](./field.mdx) with a select is the control for a choice too large or too wordy to sit
  on one row. Once the options pass about five, or the labels grow past a word or two, a select
  is the honest form.
- [Button](./button.mdx) performs an action rather than setting a value. A row of buttons is
  also the wrong build for this control, because each would be its own tab stop.

**Used by**

- No pattern, recipe or screen composes it yet. It was built to switch a
  [TrendSparkline](./trend-sparkline.mdx) between its day, week and month windows, and wiring
  the two together on a surface is a product's to make rather than something the corpus ships
  today.
