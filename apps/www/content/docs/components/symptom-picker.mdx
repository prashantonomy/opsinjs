SymptomPicker is a multi-select over a list of options the product supplies: a reader ticks the ones that apply to them, and the component records that selection. It is the plainest reading of the words "symptom picker", and the plainness is the whole design, because the richer reading is a regulated device this design system has no business shipping.

The boundary that shapes every decision here is the line between recording and interpreting. This component records which options were ticked and hands the values back, and it stops there. It runs no check, it performs no triage, it computes no score, and it reaches no conclusion about the reader. A symptom picker sits one step from a symptom checker, and a symptom checker is a regulated device in most of the markets this system targets, so the one step is the one this component refuses to take.

## Preview

A short list with one row ticked. The thing worth checking is that the ticked state is carried by the check shape inside the box and a quiet neutral fill rather than by a colour, so read it in greyscale: the ticked row stays legible as ticked, and nothing on the surface reads as a status or a category. Turn the text size up and the rows grow and the targets stay past the 44pt floor.

The picker is built on Base UI's CheckboxGroup and Checkbox primitives, which is where the shared selection array and each option's checkbox semantics come from, so installing it pulls in `@base-ui/react`. It also pulls in `lucide-react` for the check glyph inside each box and, when the filter is on, the search glyph in the field. It composes no other opsinjs component and ships no symptom list.

The exclusion that matters most is not in the list above, because it has no component to point at. Anything that interprets the selection, that checks it against a rule, triages it into a level, or reaches a conclusion about the reader, is not a thing opsinjs builds. The product and its regulatory pathway own that, and the value of this component is precisely that it stops at the selection and leaves the meaning where it belongs.

Within what it does do, the honest limit is the length and the source of the list. A picker over three options a product owns is the right control; a picker over a vocabulary opsinjs supplies is a control that does not exist here, because opsinjs supplies no vocabulary. If the reader is describing rather than choosing, the list is the wrong shape and a [Textarea](./textarea.mdx) is the honest form.

## Clinical meaning

**What it asserts.** SymptomPicker asserts exactly one thing: these are the values a reader ticked from the list you gave it. It asserts nothing about what any option means, nothing about how the ticked set should be read together, and nothing about what happens next. It is a record of a selection, and a record is not a reading.

**What it must never be read as.** It is not a symptom checker, not a triage, and not a diagnosis. A ticked row says the reader selected that option from a product's list; it does not say the reader has a condition, that the selection is urgent, or that any action follows. The moment a product treats the returned array as an input to a rule that reaches a clinical conclusion, the meaning has moved onto the regulatory pathway the roster warned about, and that pathway is the product's to own, never this component's to imply.

**Which colour axis it may use.** Neither. A ticked option is a selection, not a clinical level, so the component carries neither `data-status` nor `data-category` and draws only neutral chrome. The ticked state travels as the check shape and a quiet fill rather than as a hue, so it survives greyscale and colour-vision deficiency without ever borrowing the status axis. Putting an urgency colour on a ticked row would say the selection means something the component is not entitled to say, which is the collision [The two colour axes](../health/two-colour-axes.mdx) exists to prevent.

**Who owns the thresholds and the words.** The consuming product, always. SymptomPicker ships no symptom list, no option labels and no default text, because the controlled vocabulary is product specific and shipping it inside a component library would be shipping a clinical decision to every product that installed it. Every option arrives through `options`, the group's question arrives through `label`, and the only thing this component supplies is the neutral chrome that records the choice.

## Content guidelines

Write every option in the reader's own words, and keep each label short enough to scan: a plain description of the thing, not a sentence and not a clinical register. The group's `label` is the question the list answers, so phrase it as a question the reader would recognise, such as "Which of these apply to you right now?", rather than a heading like "Symptoms".

Never phrase an option as a verdict or a finding. An option names something the reader can recognise and tick; it does not tell them what the selection means, because the component does not know and must not pretend to. Keep the labels stable across screens, so a reader who learnt an option's wording in one place meets the same wording in another, and never change a label to carry urgency the row is not allowed to show.

<DoDont>
  <DoDont.Do>
    **Options written as plain, recognisable descriptions the reader ticks, with a question for the group label.** Each row names one thing in the reader's words, the reader chooses the ones that apply, and the picker records the set without adding meaning to it.
  </DoDont.Do>
  <DoDont.Dont>
    **Options that smuggle a severity or a conclusion into the label, such as a row that names an urgent condition rather than a thing the reader recognises.** That reaches a finding the component is not entitled to reach and dresses an interpretation as a plain choice.
  </DoDont.Dont>
</DoDont>

<DoDont>
  <DoDont.Do>
    **Take the returned array and store it against the reader's own record, or pass it to a person who can interpret it.** The selection is a record, and a record is handed to whoever owns the meaning.
  </DoDont.Do>
  <DoDont.Dont>
    **Feed the returned array into a rule that checks it, triages it into a level, or shows the reader a conclusion.** That is the step from a picker to a checker, and it moves the product onto a regulatory pathway this component was built to stay off.
  </DoDont.Dont>
</DoDont>

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The picker draws only the neutral chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **The ticked state is not carried by colour.** A ticked row shows the check shape inside its box, so the state is a shape a reader without the fill can still read, and the gate that fails a status told by colour alone has nothing to catch because the picker paints no status at all.
- **No px type size.** Every label and the filter field use the semantic type steps rather than a pixel size, so a reader who has turned their text size up gets a larger picker instead of a pinned one.

**Argued, and true of the implementation, but not yet measured:**

- **Each option is a real checkbox in the accessibility tree.** Base UI's Checkbox renders `role="checkbox"` with `aria-checked`, the label inside it is the accessible name, and the decorative box and glyph carry `aria-hidden`. A reader hears the question, then each option as a checkbox that is ticked or not.
- **The whole row is the target.** The pressable element is the option row, not the small box, and it floors its hit area at `--opsin-target-minimum` in rem, so a 44pt region survives and grows with the reader's text size. The filter field floors at the same minimum.
- **The filter changes what is shown, not what is chosen.** Narrowing the list unmounts the rows that do not match and leaves their ticked values in the array untouched, so a reader never loses a selection by filtering, and clearing the filter brings every option back ticked as it was.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the box hairline and its muted fill against the host ground, the check glyph against the fill, and the filter field's border and placeholder ink against the ground. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring, and this component sets no surface of its own, so each pair is painted on whatever ground the host provides.
- Whether the group and its checkboxes read usefully in a real screen reader, and whether the filter's changing result count should be announced as rows appear and disappear. It has been reasoned about and not listened to.
- What the picker draws under `forced-colors: active`, where the box fill and the field border are replaced by the platform's own pair. None of this has been put in front of a machine or a high contrast user.

## API reference

<PropsTable name="SymptomPickerProps" />

`options` is the product's controlled vocabulary and the whole of what the picker draws: opsinjs ships none of it, so an empty array renders nothing and raises a development warning rather than an empty group. `value` and `onValueChange` make this a controlled multi-select with no selection state of its own, so the caller holds the array of ticked values and passes it back; a value that matches no option is kept untouched and named by a development warning rather than dropped. `label` is required because a group with no accessible name is a defect the type system cannot otherwise prevent, and `searchable` adds the filter field for a list long enough to need one.
