A screen reader reads a screen as a stream of words, and a great deal of what a sighted
reader understands never reaches that stream: an icon-only button is a picture with no
name, three identical "Read more" links are three identical words with nothing to tell
them apart, and a figure sitting under a column heading loses the heading the moment it
is read on its own. VisuallyHidden puts the missing words back into the stream without
drawing them, so the two readings say the same thing.

It is the `sr-only` pattern that every component in this system already uses internally,
named once and shipped as a component so a product can reach it in JSX. What it
deliberately is not is a skip link. A skip link hides until it is focused and then
appears; this component is always hidden, and the difference is the subject of the
accessibility section below.

The line that separates a good use from a misuse is whether a sighted reader would ever
need the content. If they would, hiding it takes something away, and the answer is a
visible element instead. This component is for content a sighted reader already has by
other means, so it fills the gap for a screen-reader user without changing what anyone
else sees. Never reach for it to hide something from everyone, because the eye and the
screen reader are not the same audience: content clipped this way is still fully present
to assistive technology.

## Examples

### A name for an icon-only button

The button shows a cross and nothing else, so a sighted reader knows what it does and a
screen-reader user meets a control with no name. The words go inside a VisuallyHidden
child, so the button's accessible name becomes the full action while the surface stays a
plain icon. The icon itself is marked `aria-hidden` so the name is read once rather than
twice.

<ComponentPreview name="visually-hidden-a-name-for-an-icon-button" kind="example" align="start" />

### Context for a repeated link

Every row ends in the same two words, "Read more", which a sighted reader disambiguates
instantly from the title beside it. A screen reader can list every link on a page with
no sentence around any of them, so the list becomes three identical links to nowhere in
particular. Appending the subject inside VisuallyHidden gives each link its own name
without changing a pixel of the layout.

## Content guidelines

Write the hidden words as the words a sighted reader already has, no more and no less.
For an icon-only control, that is the action the icon stands for, phrased as a control
would be labelled: "Close the reminders panel", not "Close" alone if the surface holds
more than one thing to close. For a repeated link, it is the subject the row supplies
visually, so "Read more" plus " about keeping a daily log" reads as one sentence. Keep
the leading space when you splice hidden words into visible text, because a screen
reader concatenates them and "Read moreabout" is the result of forgetting it.

Do not use it to hide a caveat, a source or a status a sighted reader ought to see.
Provenance, disclaimers and clinical status are content everyone needs, and clipping
them out of view is how a product ships a screen that looks reassuring and reads as
something else. If the content matters to a sighted reader, it is visible content, and
this is the wrong component for it.

<DoDont>
  <DoDont.Do>
    **"Close the reminders panel"** inside an icon-only button names the action in full, so a screen-reader user hears what a sighted user reads from the cross.
  </DoDont.Do>
  <DoDont.Dont>
    **An empty VisuallyHidden, or one holding only "button"**, gives the control no meaning at all, which is worse than the bare icon because now the markup looks labelled and is not.
  </DoDont.Dont>
</DoDont>

## Accessibility

The component is announced precisely because it is not `display:none` and not the
`hidden` attribute. Both of those, and `visibility:hidden` as well, remove content from
the accessibility tree at the same time as they remove it from view, so none of them can
carry a screen-reader-only string. This component clips the box to nothing instead,
which takes the content off the screen and leaves it in the tree, which is the one
behaviour the job needs.

It is not focusable and it is not a tab stop, because it is text. Do not place a
focusable control inside it. An always-hidden focusable control is a keyboard trap:
focus moves to a place the reader cannot see, with no visible ring and no way to tell
where they are. A control that must appear when it is focused is a skip link, which
reveals itself on focus and is a different pattern built from a focus-driven reveal.
Keep this component for content that is always hidden, and reach for a link when the
target has to become visible.

Because the component paints nothing, no type size and no colour applies to it, and
there is nothing to reflow at 200% text. That is also why its contrast report below is
empty: there are no rendered pixels to measure, so the empty table means nothing to
measure here rather than not yet measured. Nobody has yet listened to the component in a
screen reader, which is the open question above.

## API reference

<PropsTable name="VisuallyHiddenProps" />

`children` is required, because a VisuallyHidden with nothing to announce is a silent
no-op. Empty children, an empty string, `undefined`, `false` from a conditional, or an
array of only those, raise a development warning naming the mistake, and the span still
renders, because a presentation layer reports rather than throws on the render path.
`className` reaches the span for positioning; a class that makes the content visible
defeats the component and is a misuse rather than a feature.
