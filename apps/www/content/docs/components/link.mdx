Link is the other half of Button. Button refuses `href` on principle and says, on its own
page, that a control which produces a new URL is a link. This is the component that
sentence points at. Between the two, the system's anatomy rule, a real button element or
an anchor only when it navigates, is implemented in full: Button owns the first clause and
Link the second.

It exists because six components used to each ship their own raw anchor with its own class
string, and the treatments drifted. A banner's action and a card's action rendered with
different focus rings, underline offsets and target heights on the same screen. Link is the
one place a navigation link's appearance is decided, so those treatments now agree.

## Preview

Three emphases on a neutral ground: an underline inside a sentence, a bordered action, and
a quieter one beside it. The thing worth checking is whether the ladder reads as a ladder
without colour doing the work, because it differs by a box and a boundary rather than by
hue, and whether each rung takes the focus ring on keyboard focus.

Link pulls in Button, because its `action` and `secondary` emphases share Button's card
action recipe. Installing Link installs Button with it, so the anchor and the handler form
of the same action cannot drift.

## Usage

```tsx
import { Link } from "@/components/ui/link"
```

```tsx
<Link href="/results" emphasis="action">
  See your results
</Link>
```

Every use names three things and defaults none of the ones that matter. `href` is where it
goes, and it is required, because a link with no destination is a button. `emphasis` is the
weight, and it is required, because there is no sensible default weight and a guessed one is
a decision nobody made. The label is the accessible name, so write it to read on its own out
of a screen reader's list of links.

## When to use it

The first exclusion is the one that gets ignored, and it is the mirror of Button's. Button
is always a real button element and refuses `href`, because a link that navigates can be
opened in a new tab, copied, and found in a screen reader's link list, and none of that
survives a button with a click handler. The same line drawn the other way is why Link
refuses to be an action that merely does something: if pressing it produces no new URL, it
is a button however it is styled.

The defect Link exists to close is two link treatments on one card. A ResultCard used to
render its primary action as a bordered, button-shaped anchor and its secondary action as an
underlined one, and because each of six components spelled its own anchor by hand, the two
did not even agree with the same action on a neighbouring banner. Reaching for Link for both
means one focus ring, one underline offset and one target floor across every navigation link
on the screen.

Link is a single element, and its `data-slot` is `link` and nothing else. It emits no
`data-status` and no `data-category`, because a link is on neither colour axis: it carries
no reading and no measurement, so nothing about it should ever be coloured by what a value
means or by how urgent it is. Style it from outside through `data-slot` or `className` if you
need to.

The `render` slot is the escape hatch, and it follows the pattern Field.Control uses. A
product on Next or React Router passes its router's own link element, and Link keeps its
contract on it: the emphasis classes, the `data-slot` and the target floor are merged onto
the element the product supplied, and Link's own attributes win where they meet the router
element's. Without it Link renders a plain anchor, which reloads the whole page on every
client-side app that does not route through it.

## Examples

### Each emphasis

The weight is a required prop rather than a default, so each call states which of the three
it wants. `action` is a card's primary action, `secondary` the quiet one beside it, and
`inline` a link that sits inside a sentence.

```tsx
<p>
  Your readings are yours to keep, and you can{" "}
  <Link href="/how-it-works" emphasis="inline">
    read how this measurement is worked out
  </Link>{" "}
  before you share them.
</p>

<Link href="/appointments/new" emphasis="action">
  Book a repeat appointment
</Link>

<Link href="/about/this-measurement" emphasis="secondary">
  Read about this measurement
</Link>
```

### Routing through the product's own link

Pass the product's router link as `render` so navigation stays client-side. Link merges its
classes, its `data-slot` and its target floor onto the element you give it, and replaces its
children with the label you pass to Link.

```tsx
import NextLink from "next/link"
import { Link } from "@/components/ui/link"

<Link href="/results" emphasis="action" render={<NextLink href="/results" />}>
  See your results
</Link>
```

## States

Link is interactive, an anchor a reader points to and clicks, and its states differ by
which emphasis is rendered rather than being one behaviour for all three, and no state
is claimed for a variant that does not carry it. Every emphasis draws a focus ring in
its own class list,
`focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-ring`, for
the reason the Accessibility section below gives: the product theme already outlines
every focused element, but a project installed without that theme should not lose the
ring silently. `action` and `secondary` add a hover fill, `hover:bg-muted`, from the same
card action recipe Button's handler form shares, so resting a pointer over either reads
as a pressable box rather than as static text. `inline` carries no hover class of its
own, because the underline is already its resting state and there is no quieter form for
hover to lift it out of. The one-pixel press, `active:translate-y-px`, belongs to
`inline` alone: the card action recipe behind `action` and `secondary` never declares it,
so a boxed link gives no positional feedback on press beyond the hover fill it is already
showing. Link has no disabled state, because an anchor is not a control Base UI can
disable, and a destination a product does not want followed is a link the product should
not render, rather than one drawn in place and dimmed. Link asserts no `:visited` rule of
its own either: nothing in its class list touches that pseudo-class, so a reader who has
already opened the destination meets whichever colour the browser or the product
stylesheet gives a visited anchor, if either gives one, which is a fact about the
surrounding page rather than a behaviour this component owns.

Link carries no reading, so most of the five canonical
[data states](../foundations/data-states.mdx) describe a value it never holds rather
than a gap in the implementation.

| Data state | What Link renders |
| --- | --- |
| Error | Nothing of its own. `href` is required rather than defaulted, so a destination that cannot be resolved is a Link the caller does not render, not one rendered pointing nowhere. |
| Loading | Nothing of its own. A destination not yet known is a Link not yet rendered; the surface composing it shows a Skeleton in its place until the `href` exists to pass in. |
| Empty | Not a state Link can reach silently. `children` is required and is the accessible name a screen reader's link list depends on, so there is no route to a Link with a destination and no label. |
| Partial | No partial form. A Link is one destination and one label together, and there is no state where it renders one without the other. |
| Stale | None of its own. Link carries no timestamp and no measurement; a reading old enough to doubt is wrapped in [RelativeTime](./relative-time.mdx) beside the link, not signalled by the link itself. |

## Content guidelines

Link text names the destination, in sentence case, without terminal punctuation. The reader
should be able to read the link alone, out of a screen reader's list of links, and know
where it goes.

Never *click here*, *read more*, *learn more*, or a bare *here*. Each forces the reader back
up the page to reconstruct what the link is about, and each is useless in a link list where
the surrounding sentence is gone. Write the destination into the words: *read how this
measurement is worked out*, not *read more*.

  <DoDont.Do>

  <DoDont.Dont>
    **"Click here"** · **"Read more"** · **"here"** A reader hearing *link, here* three
    times in a list has learnt nothing about any of them.
  </DoDont.Dont>
</DoDont>

## Motion

Link declares no motion. None of the three emphases names a `transition`, a `duration`
or an `ease` utility anywhere in `link.tsx`: the one-pixel press on `inline`,
`active:translate-y-px`, is an instantaneous position change rather than an animated
one, and the hover fill `action` and `secondary` borrow from the card action recipe,
`hover:bg-muted`, swaps in on the same frame it fires because that recipe carries no
transition class beside it either. Link reads no token from `tokens/motion.json`, so
there is nothing here for `prefers-reduced-motion` to reduce, and no reduced-motion
branch to write. A future revision that adds a transition to the hover fill or the press
would need to name the duration and easing token it took and quote that token's own
reduced-motion fallback here; nothing does that today, so this section makes no such
claim.

## Accessibility

Some of this is checked by a gate on every commit. Most of it is argued, and the things
nobody has measured are named rather than left out.

Link renders a real anchor with an `href`, which is what makes it reachable by keyboard,
openable in a new tab, and present in a screen reader's list of links. A button with a
click handler has none of those, which is the whole reason the two are separate components.
When the `render` slot substitutes a router link, that element must still render an anchor
with an `href` for the same guarantees to hold.

The focus ring is carried in Link's own class list rather than left to the product
stylesheet, for the reason Card gives: the product theme gives every focused element an
outline, but a project that ran the install without that stylesheet would otherwise lose the
ring silently. Whether a router element that draws its own focus behaviour leaves the reader
with two rings or none has not been tested, and it is listed as an open question above.

The `action` and `secondary` emphases floor the target at `--opsin-target-minimum` in both
axes, so a 44pt pressable region survives in a project installed without the product
stylesheet. The `inline` emphasis does not, and this is the one exception, named rather than
hidden: SC 2.5.8 exempts an inline target, and a 44pt floor on a link that sits in a line of
body text would inflate that line to roughly twice the height of the ones around it and open
a gap in the paragraph. The `inline` form instead carries `wrap-anywhere`, so a long compound
label reflows with the paragraph instead of widening the document, and its underline offset
grows with the type rather than sitting at a fixed distance, so at 200% text the rule stays
clear of the descenders.

A link that opens in a new tab or context should say so in its own text, because a reader
using assistive technology gets no warning from the tab change alone. opsinjs does not add
that word for you: it is the product's to write, in the product's language.

The neutral pairs Link draws its ink, its boundary and its card fill from are measured, and
they are shown below. What is not yet measured is the per-emphasis and per-level boundary
contrast, which the open question in the status note above records; the rows here are the

## Data attributes

Link emits exactly one data attribute, on the root, whichever form the root takes. When
`render` is not passed the root is Link's own `<a href>`; when it is, the same
`data-slot` is merged onto the router element the product supplied, alongside `href` and
Link's own attributes, which win where they meet the router element's. There is no
second data attribute anywhere in the source.

Link carries neither `data-status` nor `data-category`, because a link sits on neither
colour axis: it holds no reading and no clinical level, and colouring it by category or
by urgency is the exact collision the two-axis rule exists to prevent. There is no
`data-opsinjs-value` either, for the same reason: nothing rendered here is a
measurement. `data-slot="link"` is the one hook a product has for a rule of its own,
whether that rule targets a plain anchor or the router element Link merged onto.

## CSS variables

<CssVariablesTable name="link" />

Link exposes no custom property of its own. Its ink, its fill and its boundary are the
semantic roles the card action recipe reads for `action` and `secondary`, `--foreground`
for the neutral ink, `--card` and `--muted` for the fill and its hover swap, and
`--border` for the boundary, listed under Tokens below. The one place a raw custom
property appears in the file is inside the card action recipe's target floor,
`min-h-(--opsin-target-minimum,2.75rem)`, and that is a token being read with a literal
fallback for a project installed without the generated stylesheet, not a property Link
declares. To recolour any emphasis, write a rule against `[data-slot="link"]` rather
than reaching for a variable this file does not set.

## Tokens

<TokenTable component="link" />

These are the tokens Link actually reads, resolved from the source by
`scripts/build-tokens.mts` rather than listed by hand, so the table cannot drift from
what the component consumes. They are the neutral chrome roles the card action recipe
shares with Button, `--foreground`, `--card`, `--muted` and `--border`, together with
the `--opsin-target-minimum` floor and the type step each emphasis sets. Link never
reads a category token and never reads a status token onto its own element, because it
sits on neither colour axis, and a row here naming one would be the defect the two-axis
rule exists to catch.
