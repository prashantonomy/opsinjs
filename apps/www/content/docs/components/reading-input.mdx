Numeric entry is where unit confusion, decimal slips and transposed digits enter a health
record, and everything downstream inherits them. This component is the last place those
mistakes are cheap to catch, and the first place a heavy-handed check will stop somebody
recording a true value.

It is also the component that has the least opinion of anything in the system. It holds no
bound, performs no comparison, rejects no entry and rewrites no digit. What it owns is
narrow and worth owning: the unit is on screen while the reader types, a compound reading is
one named group of separately-typable parts, and a unit switch says out loud what it did to
the number.

## Preview

The field in the state it spends most of its life in: empty, with the unit already visible
beside the box rather than waiting in a placeholder. Switch it to °F and watch the line
underneath. The entry converts by the definition of the Fahrenheit scale and says so.

Open it under the product theme and turn the text size up. Two claims are meant to be
checked rather than believed: that the unit wraps *beneath* the number instead of
overlapping it or pushing the page sideways, and that nothing on the surface changes colour
because of what has been typed into it.

## Clinical meaning

**What it asserts.** That the reader entered this number, in this unit, meaning it as a
measurement of themselves. Self-reported provenance travels with the value from here to
every surface that displays it, and this component has no way to mark a reading as anything
else. A field somebody typed into is a field somebody typed into.

**What it must never be read as.** A validated measurement, a device reading, or an assessed
value. Nothing that happens in this field asserts anything clinical about the number,
including the absence of a warning: a reading nobody warned about is a reading nobody
checked.

**Which colour axis it may use.** Neither, and there is no prop that changes that. A field
that turns amber because the value entered is outside a reference range is delivering a
verdict during data entry, before anyone has checked whether the number is even right. There
is no `data-status` in this component, no status class, no category class, and the advisory
sentence is a paragraph in the ordinary foreground colour with no glyph, set at the emphasis
weight so it is found without either. Form chrome and
clinical status are separate vocabularies, and the two-axis rule is worth nothing if one
leaks into the other. [Field](./field.mdx) arrives at the same answer from the other
direction.

**Plausibility is the product's, comparison included. This is where the implementation
departs from what this page proposed.** The specification had a `plausible` prop carrying a
minimum and a maximum, with the component doing the comparison. It does not exist. The
product supplies the finished `warning` sentence instead, and this component performs no
comparison of any kind, because:

- A bound this component holds is a bound it has to compare against, and that comparison is
  four clinical decisions nobody has made: whether the ends are inclusive, what happens to
  each part of a compound reading, which unit the bounds are stated in once the reader has
  switched units, and what counts as *outside* for a value somebody is halfway through
  typing.
- A shipped bound is forbidden for any metric in any population. The ban reaches example
  data, and it holds however the constant is named, so the prop could never have appeared
  in a demo, an example or a preview. A feature nobody can ever see working is a feature
  that is wrong in a way nobody notices.
- What a reader actually needs is a sentence, not an interval, and only the product can
  write it.

**What the warning does and does not do.** It is tied to the control's description, so
somebody using speech reaches it. It does **not** mark the field invalid, so a form still
submits. It does not move focus, it does not clear the box, and it does not change a digit.
Real readings fall outside plausible ranges, and that is often precisely when they matter
most; the reader always wins the argument, and a value nobody has said is impossible is a
value this field accepts and passes on unchanged.

**Units are a correctness surface.** mmol/L and mg/dL differ by a factor of about eighteen
for glucose; kilograms, pounds and stones are three different input shapes; Celsius and
Fahrenheit cross near body temperature in a way that makes a wrong unit look plausible. The
unit is always visible beside the value, never inferred from a locale, and never implied by
a placeholder. See [Unit systems](../health/unit-systems.mdx).

**Which switches this component will make, and the one it refuses by name.** A switch asks
`tokens/units.json`, which carries conversions that are true by **definition** and nothing
else: kg ↔ lb ↔ st is the 1959 international pound, °C ↔ °F is the definition of the
Fahrenheit scale. mmol/L ↔ mg/dL is not in that table and will not be. The factor is the
molar mass of the substance being measured, which is a property of the *substance* rather
than of either unit, and glucose, cholesterol and creatinine each carry a different one. The
same goes for HbA1c mmol/mol ↔ %, which is a fitted regression rather than a definition, and
for kcal ↔ kJ, because there is more than one calorie. [ADR 0016](../project/decisions/0016-the-unit-table-ships-no-factors.mdx)
records all three refusals.

So a switch this system cannot make **clears the entry and says so**, rather than relabelling
the digits: keeping 5.2 and changing the label above it from mmol/L to mg/dL is an
eighteen-fold error that looks entirely reasonable on screen. A product that needs that
switch supplies the arithmetic itself. The field is controlled, `onChange` reports
`cause: "unit"` with `unitEffect: "cleared"` and the unit the reader asked for, and the
product re-renders with its own converted value so the reader keeps their entry. It supplies
the conversion, or there is no switch.

The entry is not destroyed when it is cleared, though. A reader who goes back to the unit they
typed in gets their own digits back, and the line says the entry was restored, so a switch
brushed by accident on a phone costs nothing.

**Whose unit the value is in.** The one named by `unit`, always. The specification had
`value` in a canonical unit with the display converted, which means every keystroke
round-trips display → canonical → display; [Unit systems](../health/unit-systems.mdx) rule 6
says to round after conversion and that a round trip is lossy, so that design visibly mangles
digits as they are typed. Here nothing round-trips. Storing the reading canonically is the
product's job, which is where the knowledge of what canonical means for this measurement
already lives.

<SafetyCallout severity="attention" evidence="opinion">
Changing the unit selector must never silently change the stored value or silently keep the
typed digits. Whichever the component does, it must say so on screen in words such as
*converted from 10 kg* or *cleared, please re-enter*, because both behaviours are correct in
some situation and the reader is the only person who knows which one this is.
</SafetyCallout>

The two shapes differ in exactly one place, and the tree above can only draw one of them: a
simple reading has **one** Field wrapping everything from `ReadingInput.Control` down, so the
label and the hint are Field's own parts; a compound reading has one Field **inside each
segment**, so each box carries its own label and the group is named by a `<legend>` above
them. Everything else is identical, and that covers the slots, the wrapping row, the unit
and the warning.

The parts are identified by `data-slot` and are styleable from outside. None of them is an
export and there is no dot-notation API: content arrives as a prop, and there is nothing a
compound export would let you place that a prop does not. The one exception is the box
itself, which is `Field.Control` and belongs to [Field](./field.mdx) rather than to this
component.

`ReadingInput.Unit` is never a placeholder and never lives only in the label. A unit the
reader cannot see while typing is a unit they will assume, and the assumption is often wrong.

## Examples

### Two numbers that are one measurement

`segments` turns the field into a real `<fieldset>` with a `<legend>`, and each part into its
own labelled box. The group has a name, each box has a name, and the unit belongs to the
whole group and is printed once after the last box. Both parts of a compound reading are in
the same unit by definition, and a pair in two different units is two measurements.

This is the entry side of a rule that reads the other way round on the display side.
[Numbers, units and precision](../health/numbers-units-precision.mdx) rule 11 says a compound
value is *written* in its conventional form, which is one string with a solidus rather than
two fields, and [ResultCard](./result-card.mdx) obeys it. Here,
[Units and numeric entry](../patterns/forms/units-and-numeric-entry.mdx) requires the
opposite: separate fields under one legend, because asking somebody to type a solidus is
asking them to format their own record, and a single box cannot tell you which half is
missing when only one number arrives. Neither document says it is talking about only one
half, which is why this paragraph exists.

What comes back is a `ResultCard`'s `segments`, unchanged. The two components agree on
`{ label, value }[]` so that a reading goes from the box it was typed in to the card that
displays it with no mapping step in between.

### Switching the unit, and the sentence that follows it

Switch it and watch the line underneath. `precision` is why the result is readable: it is the
decimal places of the *measurement*, and without it 10 kg becomes 22.046226218487757 lb,
which is the honest arithmetic and is unusable. There is no per-unit default anywhere in
opsinjs to fall back on. Decimal places belong to the measurement rather than to the unit,
and two measurements reported in the same unit do not share one. So a conversion with no
precision is not rounded at all and says so in development.

### A sentence the product wrote

The comparison is not in the component and it is not in this example either, which is the
more interesting half: an example that compared a reading against a number would be opsinjs
shipping a plausibility bound, and those are forbidden for any metric in any population,
examples included. So the example shows the component's side of the contract and stops
exactly where the clinical decision starts.

Notice what has *not* happened. The box is not marked invalid, the entry is exactly as it was
typed, focus has not moved, and nothing is a different colour. Clear the box and the sentence
goes.

## States

ReadingInput is interactive and runs as a client component, so its live states are the
ordinary ones of a form control rather than the data states below. Each box and the unit
switch take the browser's own focus ring, and both hold the minimum target floor in each
axis with a rem fallback, so the floor survives an install that has not wired the token
sheet. The `disabled` prop disables every box and the unit switch together. There is no
hover or pressed styling of this component's own, because the boxes are text inputs and the
switch is a native `<select>`, and each keeps its platform affordances. Nothing on the
surface changes colour on any interaction, from the category axis or the status axis, which
is the same promise the field makes about what has been typed into it.

The five canonical data states describe a value a surface displays, and this component
collects a value rather than displaying one, so several of them belong to whatever composes
it rather than to the field. Each is named honestly below rather than left out.

| Data state | What ReadingInput renders |
| --- | --- |
| Error | Nothing of its own. The field never marks itself invalid: the advisory `warning` is a description, so it sets no `aria-invalid`, blocks no submission and moves no focus. A true validation error belongs to the surrounding form, through `Field`'s `error` prop. |
| Loading | Nothing. The field is controlled and paints what the caller passes on the same render, so there is no fetch to wait on. A surface loading a prior reading shows its own placeholder around the field. |
| Empty | The state it spends most of its life in: an empty box with the unit already visible beside it, `data-opsinjs-value` an empty string, and `ReadingInputChange.value` `null`. Empty is never a zero. |
| Partial | A compound reading with one box filled and another blank stays exactly that. Each box is independent, the blank part reports `value: null`, and `ReadingInputChange.value` is `null` for any compound reading, because half a pair is not the reading. Nothing is flagged and nothing is filled in. |
| Stale | None. Staleness is a property of a stored reading's age, and an entry control owns no age: a number being typed has not been anywhere yet. The surface that later displays the saved value carries staleness, through [Value](./value.mdx) and [ResultCard](./result-card.mdx). |

## Content guidelines

Label the measurement in the reader's words and put the unit beside the field, never in the
label. A reader who thinks in pounds and meets a field labelled *Weight (kg)* types pounds,
and nothing on screen stops them or records what they meant.

Hints show the **shape** of an answer, not an example reading and not a bound. *To one
decimal place* and *both parts, in whole numbers* help. A specimen number does not: it is a
plausible reading published by a system with no clinical owner, and readers anchor on it. A
sentence naming two bounds is worse still. It reads as a rule the reader has already broken,
and it is a threshold nobody has signed for.

Advisory messages ask a question and offer the likely fix. They never say *invalid*, never
say *error*, and never imply the reader has done something wrong, because most of the time
they have not. Write them in the product's voice: the component supplies the wiring and none
of the words.

<DoDont>
  <DoDont.Do>
    **"That is a long way above most readings. Did you mean to type a decimal point?"** with
    the entry left exactly as typed and the correction offered as a control.
  </DoDont.Do>
  <DoDont.Dont>
    **"Invalid value. That reading is outside the accepted range."** Rejects a number that
    might be real, blames the reader, and hands them a bound to satisfy rather than a mistake
    to check.
  </DoDont.Dont>
</DoDont>

<DoDont>
  <DoDont.Do>
    **"Example measurement [ 10 ] [ kg ▾ ]"** with the unit visible and switchable beside
    the number.
  </DoDont.Do>
  <DoDont.Dont>
    **"Example measurement (kg) [ 10 ]"** with the unit only in the label. Readers who use
    pounds will type pounds, and nothing on screen will stop them or record what they meant.
  </DoDont.Dont>

## Motion

This component declares no transition, no animation and no motion token, and it reads
nothing from `tokens/motion.json`. So there is nothing for `prefers-reduced-motion` to
reduce: a reader who asks for less motion sees exactly what every reader sees. That is the
right answer for a field rather than an omission, because the one thing a reading input
could animate is the number itself.

A health value is never animated on first paint, and a converted reading is a health value
the instant it lands, so neither the digits a reader types nor the digits a unit switch
writes back count up or sweep into place: they appear at once, at full precision. The line a
switch draws beneath the boxes appears the same way, without a transition, so a reader using
speech is not waiting on an animation to settle before the description is stable enough to
read.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`. The rest
is argued, and it is labelled as such: a component page claims accessibility only where it has been checked, with the gaps listed rather than left out. Nothing here has been
through a review with a disabled user, and the components overview says as much above
its table, for all sixty.

**Checked, by `pnpm run check:a11y` on every pull request and every push to `main`:**

- **No shipped threshold, and no unowned interval.** A name matching *stale*, *threshold*,
  *cutoff*, *limit*, *minimum*, *maximum*, *expiry*, *band* or *plausib* given a numeric
  literal is an error anywhere under `registry/`, including by way of a named constant; so is
  an object literal with two numeric bounds and no `source` beside them. There is no bound in
  this component and none in any of its three examples. One example did briefly hold a
  comparison constant while this was being written, under a name that would have passed the
  gate. It is gone rather than renamed, because renaming a plausibility bound does not stop
  it being one.
- **Nothing on this surface takes colour from either axis.** The rig fails a component that
  paints a status colour without also reading `CLINICAL_STATUS_META` and a glyph, and one that
  stamps `data-status` without a word beside it. This file does neither of those things
  because it does neither of the things they guard: there is no status word, no status class
  and no `data-status` anywhere in it, which is what the *no verdict during data entry* rule
  looks like when a machine checks it.
- **No type size in pixels and no raw colour literal**, so the field scales with the reader's
  own text size, and **no class that resolves to nothing under `/view`**. The docs chrome's
  palette is larger than the product's, and a component that reaches into it looks correct in
  review and renders unstyled in the app.
- **No banned word in the copy or in an identifier.** The strings this component and its
  examples own are read by the same gate that reads a page.

**Argued, and true of the implementation, but not yet measured:**

- **The label is visible, persistent and programmatically associated**, and none of that is
  implemented here. `Field` renders a real `<label for>` against the id Base UI mints for the
  control, and there is no prop on either component that hides it. A compound reading is a
  `<fieldset>` with a `<legend>` and one `Field` per part, so the group has a name and each
  box has its own.
- **The unit is in the field's description.** The spoken form comes from `tokens/units.json`,
  so the box announces as *Example measurement, edit, 10, in kilograms* rather than leaving a
  screen reader to improvise a pronunciation of a symbol. The description ids this component
  adds are *merged* with the ones Field registered rather than replacing them. That is
  checked by reading Base UI's labelable provider, which splits the incoming attribute and
  concatenates, and not by listening to it. The list a reader arrows through carries the same
  spoken form: each option is given its plural on an `aria-label`, so `st` announces as
  *stone* and `lb` as *pounds* while the visible text stays the bare symbol and the control
  keeps its width. Chromium computes the option's accessible name from that `aria-label`,
  confirmed by reading the accessibility tree; folding the plural into the visible option text
  instead would widen the closed control off the number, which is why the name rides the
  attribute rather than the text. So choosing `st` from `lb` by ear now names the unit rather
  than reading only the symbol.
- **The right keyboard appears.** `inputMode` defaults to `"decimal"`, which can type a whole
  number where `"numeric"` cannot type a fraction, so the default is the one that fails
  safely. `enterKeyHint` is the caller's, because only the form around the field knows what
  the return key will do.
- **The box is `type="text"`, not `type="number"`**, and that is an accessibility decision
  rather than a stylistic one. A number input silently discards what it cannot parse,
  exposes the spin buttons this component is required not to rely on, and changes its value
  when a trackpad scrolls over it. A reader typing a comma on a European keyboard watches
  their entry vanish with no message. A comma is accepted as a decimal separator here,
  exactly one of them, because guessing whether *1,234* is a thousands separator is how a
  reading moves by a factor of a thousand.
- **The unit switch is a real control** with a name that says what it switches, and in the
  example that name is *Unit for Example measurement*. The 44px floor is set in both axes
  with a rem fallback, so it grows with the reader's text size and survives being installed
  in a project that has not wired the token sheet.
- **The advisory sentence is a description and never an error.** No `aria-invalid`, no focus
  move, no cleared box, no blocked submission. There are no spin buttons anywhere.
- **At 200% text the unit wraps beneath the number.** The control row is a wrapping flex row
  with no fixed height, checked by eye in both themes and not yet by a machine.

**Not yet checked at all, and listed rather than omitted:**

- **Nobody has listened to it.** The compound announcement is the largest unknown: this page
  used to say a pair should announce as *systolic, 128; diastolic, 78* while
  [Numbers, units and precision](../health/numbers-units-precision.mdx) says the same reading
  is spoken *118 over 76 millimetres of mercury*. Those are two different contracts, the entry
  side and the display side, and only the display side has ever been written down properly.
- **The component announces no unit switch itself, and whether the product does has not been
  listened to.** The substrate contract forbids a component mounting a live region on the
  caller's behalf, because an input that speaks on every keystroke is an input nobody can use.
  That refusal stands. What has changed is that the sentence is no longer a dead end: it
  leaves through `onChange` as `effectText`, character for character what a sighted reader
  sees, so a product that offers a unit switch can route it through its own polite announcer.
  The gap is now the product's announcement rather than a component that swallows the words,
  and nobody who relies on that route has yet listened to confirm it fires at the right
  moment.
- **The component itself has not been measured, and its boundary inherits a number rather
  than owning a measured pair.** The hairline around the box and around the unit switch draws
  `border-input`, the field's boundary role. Under D5 that role is the same neutral-500 step
  as `--border` in both themes, so the field reads at whatever `--border` reads at. Only
  `--border` is put through the gate, though. The pairs `neutral.border-on-page` and
  `neutral.border-on-card`, recorded in `lib/generated/contrast.json` once the contrast
  generator has run, measure the card hairline, which is `--border`. The field takes that
  number without a gated pair of its own, so a drift in the `input` role alone would move the
  field's boundary and still pass every gate. The contrast report below resolves the neutral
  scope through this component's catalogue row, which is a measurement of the token pairs the
  field draws its colour from and not a reading taken off the rendered control. The two are
  not the same thing. The dark boundary is honest about its own shortfall: neutral-500 on the
  near-black page reaches about Lc 28.72 against an Lc 45 non-text floor, so it is published,
  measured and below the APCA floor while it clears WCAG 3:1. `prefers-contrast` and
  `forced-colors` are not answered by this component, so the increased-contrast claim still
  cannot be made for the field itself.
- **No hit area has been measured** at 1.3× zoom or at 200% text, on the boxes or on the unit
  switch.
- **Choosing a unit from the open list by ear now names the unit, but has not been heard on a
  real screen reader.** Each option carries its spoken plural on an `aria-label`, so a reader
  arrowing `kg`, `lb` and `st` reads *kilograms*, *pounds* and *stone* rather than the glyphs,
  and the accessibility tree confirms the computed name. The switch stays a native `<select>`
  for the platform behaviour it brings, and the spoken name rides the attribute rather than a
  non-native listbox, so no platform behaviour is given up to get it. What stays unchecked is
  how a given screen reader voices a native select's own open popup, which is platform
  behaviour this component does not control and which nobody has listened to here.
- **The three owned sentences are English**, with no way to translate them.

## API reference

<PropsTable name="ReadingInputProps" />

Five differences from the interface this page proposed while it was unbuilt, each named here
rather than slipped in.

**There is no `plausible` prop**, and its absence is argued in full under *Clinical meaning*
above. `warning` takes the finished sentence instead.

**`value` is in the displayed unit, not in a canonical one**, and `canonicalUnit` is gone.
The proposed design converted for display on every render, which round-trips the reader's
digits through a rounding step while they are typing them. `unit` is required and is the unit
the number is in.

**`onChange` takes one object rather than two positional arguments**, because the proposed
`(value, displayUnit)` could not say which of a compound reading's parts had changed, could
not carry the parts at all, and could not distinguish an empty box from one holding something
that is not a number. `ReadingInputChange` carries the segments, the unit, the raw text of
every box, what the reader did, and what a unit switch did to the numbers.

**`onUnitChange` is gone.** It was a mode enum of `"convert" | "clear"` wearing a React
handler's name, with no stated default, and two pages
([Units and numeric entry](../patterns/forms/units-and-numeric-entry.mdx) and
[Capture a daily log entry](../recipes/daily-log-entry.mdx)) already required *convert*. So
conversion is not a mode: it happens whenever `tokens/units.json` owns the factor, the entry
is cleared when it does not, and either way the component says which on screen. A product
that wants different behaviour has it, by handling `cause: "unit"` itself.

**`ReadingInputChange` carries `effectText`, and the component speaks none of it.** The
proposed interface had no field for the sentence a unit switch draws, because it assumed the
component would announce the change on the reader's behalf. It does not: it mounts no live
region, for the reason [screen readers](../accessibility/screen-readers.mdx) rule 1 gives, so
the exact sentence a sighted reader sees leaves through `effectText` and a product that offers
a unit switch routes it through its own polite announcer. The number can change under a focus
that never moves, and a description a screen reader has already read is not read again, so a
caller that does nothing leaves a blind reader saving a value they were never told had
changed.

`ReadingSegment` and `ReadingInputChange` are exported alongside the props interface. The
generator emits a table only for interfaces named `<Pascal>Props`, so these are the shipped
declarations, copied from `registry/bases/base/reading-input.tsx`:

```ts
export interface ReadingSegment {
  /** What this part is, in the reader's language. A real visible label on its own box. */
  label: string
  /** This part's number, in the displayed unit. `null` is an absence, never a 0. */
  value: number | null
}

export interface ReadingInputChange {
  /** Every part of the reading, in `unit`. Interchangeable with ResultCard's `segments`. */
  segments: ReadingSegment[]
  /** The number, for a simple reading. `null` for a compound one. Half a pair is not it. */
  value: number | null
  /** The unit the numbers above are in, which is the one the reader is looking at. */
  unit: string
  /** Exactly what is in each box, unparsed. The only way to tell empty from unparseable. */
  text: string[]
  /** Whether the reader typed in a box or moved the unit switch. */
  cause: "value" | "unit"
  /** On a switch: converted by a definitional factor, cleared, restored to the typed unit, or unchanged. "Unchanged" is two cases: nothing had been typed, or a cleared refusal was retargeted to name the newly selected unit. That second case still ships an effectText, so do not gate an announcer on unitEffect. */
  unitEffect: "converted" | "cleared" | "restored" | "unchanged" | null
  /** The sentence drawn beneath the boxes, or `null`. The product must announce it politely. */
  effectText: string | null
}
```

`ReadingSegment` is deliberately identical to `ResultSegment`. The specification proposed
`{ name, label }` with no value at all, which cannot carry a reading in either direction.

Several constraints are stated in prose and enforced at runtime rather than in the type,
because this file ships as source into JavaScript projects where a type is advice: a blank
`label`, a blank `unit`, an empty `segments` array, a `value` passed alongside `segments`, a
`unit` missing from the `units` it offers, `optionality` on a compound reading, a conversion
this system does not own, and a conversion with no `precision`. Each is reported once per
distinct offender in development and each renders the honest fallback rather than dropping
the field. A form control removed from the screen to report a copy mistake takes somebody's
form away. None of them is an `OPSIN-` code: those describe mistakes a consumer makes with
the clinical API, they are a versioned contract generated from `tokens/errors.json`, and a
component may not mint one.

There is no `plausible`, no `canonicalUnit`, no `onUnitChange`, no `locale` and no `error`.
The last two are the ones somebody will ask for: this component formats nothing, and the
digits on screen are the digits typed or the digits the caller passed, so there is nothing
for a locale to shape. An error belongs to the form, which is `Field`'s `error` prop and
marks the control invalid, which an advisory must never do.
