## Accessibility

`pnpm run check:a11y` confirms on every commit that the badge draws only
neutral chrome roles, carries no `data-status` and sets its text at the
`caption1` step rather than a `px` size. The audit fixed one defect: `aria-label`
on a bare `span`, whose implicit role is generic, does not reliably carry an
author-supplied name, so a non-empty `srLabel` now adds `role="img"`, the
pairing [Avatar](./avatar.mdx) uses. Nothing else changed.

**Argued from the source, not measured.** `srLabel=""` sets `aria-hidden`, so a
count already spoken beside the badge is not read twice. Nothing takes focus,
answers a key or animates, so there is no keyboard contract and nothing for
`prefers-reduced-motion` to reduce. At 200% text and under a wider text-spacing
override the chip grows rather than clipping, because nothing fixes its height
or hides its overflow.

**Residual items.**

- No contrast pair in either weight has been measured against real token
  values, so the figures below are whatever the generator has produced so far.
- Nothing checks that `srLabel` textually contains the visible content, so a
  caller can still write a disjoint label. That is a documented usage contract,
  not enforced behaviour.
- Nobody has listened to a labelled badge in a screen reader in the flow of its
  host, so how it reads there is reasoned from the roles.

## Props interface

<PropsTable name="BadgeProps" />

`variant` defaults to `soft` and chooses a neutral weight only. There is no
colour prop, because a badge is on neither axis, and colour passed through
`className` is the caller's to keep off both. `srLabel` names a bare count, and
an empty string hides a decorative badge from the accessibility tree.
