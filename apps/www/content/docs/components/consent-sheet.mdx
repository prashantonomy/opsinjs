Consent is the surface where dark patterns are most profitable and most damaging, so this
component is unusually prescriptive about what a product may not remove. The same component
is unusually unhelpful about what it may not supply. **opsinjs ships no consent wording at
all.** Not a heading, not a purpose, not a data category, not a retention period, not a
jurisdiction, and not the words on the two controls. Every consent string a reader sees here
arrives as a prop, and the sheet refuses to ask when one of them is missing. One sentence is
the exception, and it carries no legal content: the line that says nothing was asked. It
names the state of the interface rather than any purpose, recipient or retention period, it
ships in English only as a last resort, and `notAskedMessage` replaces it.

## Preview

The default sheet, with everything it can carry. The two things worth checking are both
visible without reading a word: the decision controls are the same size as each other, and
nothing in the consent text is set smaller or paler than anything else. There is no small
print on a consent surface. The one quiet mark on screen is Sheet's header Close control,
which is footnote-size and muted on purpose, because it is the way out rather than a third
answer, and making it as loud as the two decision controls would turn it into one. Close it
with the escape key and watch nothing happen: leaving is not an answer, and the component
calls nothing.

One sheet asks for one permission. If you have three to ask for, that is three sheets, each
shown when it becomes relevant. The answer is never one sheet with three paragraphs and a
single button. Bundled consent is not consent to any of its parts, and the reader who would
have said yes to two of the three has been given no way to say so; see
[Consent and disclosure](../health/consent-and-disclosure.mdx).

That rule is in the API rather than only in this paragraph. There is no `purposes` array, no
per-item switch and no way to make the purpose the introduction to a list, because a sheet
that could carry three purposes will carry three purposes under one control the first time a
deadline is close. What a granular ask actually looks like is under
[Examples](#examples).

## Clinical meaning

**What it asserts.** That the product is asking for one specific permission, that the reader
has been told what will be collected, what it will be used for, who will see it and how long
it will be kept, and that a decision either way has been recorded.

**What it must never be read as.** A condition of using the product, unless it genuinely is
one and the sheet says so plainly. It must never be read as permanent: every consent this
component takes must be withdrawable from somewhere the reader can find without asking, and
the sheet says where.

**Which colour axis it may use.** Neither. A consent sheet is not a clinical status and not a
category. Status colour on a consent surface reads as a warning about the reader's health,
which is a false alarm about a completely different subject. The component carries neither
`data-status` nor `data-category` on any element, which is what makes that claim checkable
rather than merely stated.

**Refusal is a first-class outcome.** The decline control has the same size, the same
prominence and the same visual weight as the accept control, and it is never a plain-text
link beneath a filled button. If the product cannot function after a refusal, the sheet says
so before the reader chooses, not after. That is what `consequenceOfDeclining` is, and why
it renders above the controls rather than in a confirmation afterwards.

**Closing is not deciding, and it is not refusing either.** `onDecision` fires when a reader
presses one of the two controls and at no other time. A close by the escape key, the scrim, a
drag or the header's close control calls nothing at all; the product hears about it on
`onOpenChange`, which is Sheet's and says which route was taken. A consent has three
states, and they are agreed, refused, and not answered. `granted` is a boolean with two
values, so the third is spelled as the absence of a call. A boolean that could also mean
*did not answer* is a boolean somebody will store as `false`, and a refusal nobody made is a
record about a person that is not true.

**What the product records.** A decision, a timestamp, the identifier and version of the text
that was shown, and the scope consented to. All five are handed back on `ConsentDecision`;
storing them is the product's job, and this component holds nothing between one opening and
the next.

**What happens when the wording is incomplete.** The sheet does not ask. If the heading, the
purpose, any of the three scope facts, the withdrawal sentence, either control label, the id
or the version is missing or blank, the decision controls are not drawn, the sheet says on
screen that nothing was asked, and nothing is recorded. That is a harder failure than anything
else in this system makes, and it is deliberate: the alternative is a stored record saying
somebody agreed to something the interface never told them, which is the one outcome nobody
can undo afterwards.

<SafetyCallout severity="urgent" evidence="opinion">
No pre-ticked boxes, no default-on switches, no *agree* that is also *continue*, and no
sheet that cannot be closed without deciding. Every one of these is a way of collecting a
decision the reader did not make, and in health data the consequences of a decision nobody
made are borne entirely by the person who did not make it.
</SafetyCallout>

**Heading** states what is being asked, as a question. **Purpose** says what the data is
for, in the reader's terms. **Scope** lists what is collected, who sees it and how long it is
kept. Those are three facts rather than a paragraph. **Withdrawal** says where to change this
later. **Decisions** are two equally weighted controls. **Details** is the optional full text
for the reader who wants it, never hidden behind a link labelled only *terms*.

None of these parts is an export. They are identified by `data-slot` and are styleable from
outside; there is no way to render one without the others, and no way to render `Accept`
without `Decline`. A sheet whose two decisions differ in size or prominence is a composition
error, and this component holds that promise by construction rather than by assertion. The
construction is one grid, two tracks, one component, one variant, one size, and no prop that
reaches either control on its own.

The one route left open is a descendant selector smuggled through `className`, which is the
same hole [Callout](./callout.mdx) and [DisclaimerNote](./disclaimer-note.mdx) name on
themselves. Rather than claim it is closed, the component measures the two controls after
layout in development and warns when they come back different sizes. That check runs in a
browser, not in CI, and is the only place equal weight is measured anywhere.

## Examples

### Closing is not consent

The asymmetry the whole component is built around. Press a control and a record arrives; leave
by any of the four exits and nothing does. There is no record, no `false` and no call.

<ComponentPreview name="consent-sheet-closing-is-not-consent" kind="example" align="start" />

### Two questions, two sheets

There is no `purposes` array, so this is what asking for two things looks like: two sheets,
two ids, two versions, two records. The reader can grant one and refuse the other. The second
one also shows `consequenceOfDeclining`, stated before the choice.

The second question follows an answer to the first, never a dismissal of it. Leaving question
one by escape, the scrim or Close returns the reader to the page rather than raising the next
request, and only an answer through `onDecision` moves the sequence on. When the last sheet
closes, focus returns to the control that opened it, so a keyboard reader is never left with
focus on the page body. This is the rule above made concrete: each permission is shown when it
becomes relevant, and "relevant" is never "the reader just tried to leave".

### When the wording is missing

The state a product ships by accident, from a content service with an empty field or a locale
nobody filled in. The sheet refuses to ask, says so where the controls would have been, and
names the missing pieces in the development console. It draws none of the wording it could
not stand behind: the scope list, the purpose paragraph and the withdrawal line are all
absent from the DOM in this state, rather than rendered empty.

## States

ConsentSheet is a client component, so it has real interaction states as well as the
canonical data states. Its interactive parts are the two decision controls and, when
`details` is supplied, the disclosure trigger. Both decision controls are `Button` instances
of the same secondary variant, so they take their hover, focus-visible and pressed treatments
from Button unchanged, and they take them identically because both carry one shared class
string. Neither is focused when the sheet opens. The component sets no disabled state on
either control: when the wording is incomplete the controls are removed rather than greyed,
because a greyed pair still reads as a question the reader could answer. The disclosure
trigger is a plain button carrying its own focus-visible ring, declared in the file because
the product stylesheet's ring does not travel with `shadcn add`.

The five canonical data states map onto a component that displays no reading of its own but
does have one hard branch, the state where the wording is incomplete and the sheet refuses to
ask.

| Data state | What ConsentSheet renders |
| --- | --- |
| Error | Wording that arrives broken, from a content service that returned an error and left a required field blank, is treated as missing. The sheet draws no decision controls, shows the not-asked line where they would have been, and names the missing fields in the development console. It never asks a question with pieces of it absent. |
| Loading | The component has no loading state of its own. A product opens the sheet once it holds the wording, and wording still in flight reads as missing, so an early open shows the not-asked line rather than a spinner or a skeleton. |
| Empty | The not-asked state is the empty case. When any required string is blank the two controls become the single not-asked line and nothing is recorded. The scope list is drawn only when the sheet can ask, so it is always absent from the DOM in this state; the purpose paragraph, the withdrawal sentence and the consequence sentence are each absent only when their own string is missing, independently of the others. |
| Partial | A content service that supplies some fields and leaves others blank still resolves to the not-asked state, because the sheet asks only when every required field is present. There is no partial ask by design, since a consent recorded against half its wording is the outcome the component exists to prevent. |
| Stale | Not applicable. The component holds nothing between one opening and the next and renders exactly the wording it is handed each time. Keeping a version current is the product's work through `textVersion`, so a stale record is a product concern rather than a render state here. |

## Content guidelines

Ask a question. Use *we* for the product and *you* for the reader. Say what the data is for
in terms of what the reader gets, not in terms of the product's internal purposes: a purpose
names what the reader ends up with; a category names an activity the product performs.

Never write *by continuing you agree*. Never write *we value your privacy*. Never label the
decline control *not now* when it means *no*, or *maybe later* when there is no later. The
component warns about both in development and renders them exactly as written, because only
the product knows whether there genuinely is a later.

Write the two labels as the answers they are. A screen reader can list every control on a
surface with no sentence around them, and in that list *Allow* and *Not now* are not
equivalent choices: one grants and the other postpones. A pair that is equivalent is a pair
where each label starts from the reader's own word for yes or no and then names what will
happen, or will not, in the same number of words. Those are sentences your legal owner
writes; opsinjs does not write them here either.

None of these sentences is supplied by opsinjs, and none of them is supplied below either. The
examples on this page are placeholder text that says so of itself, for the same reason
[DisclaimerNote](./disclaimer-note.mdx) ships none: a consent sentence written by a design
system arrives in a product whose author never read it, describing a use that product may not
have, and it arrives looking reviewed because it came from a library.

<DoDont>
  <DoDont.Do>
    **Five things, in this order, each in one plain sentence somebody has signed off:** the
    question; what the reader gets from saying yes; what is collected; who can see it, named;
    how long it is kept and what happens at the end; and where to change the decision later.
    Every one of them is a prop, and the sheet will not ask without them.
  </DoDont.Do>
  <DoDont.Dont>
    **"We value your privacy… in accordance with our Privacy Policy. [Accept] [Manage
    preferences]"** No question, no named recipient, no retention, a benefit claim doing the
    work of an explanation, and a second control that is a maze rather than a refusal.
  </DoDont.Dont>
</DoDont>

<DoDont>
  <DoDont.Do>
    **Both decisions written as the answer they are**, the refusal naming what will not
    happen, at the same size and the same distance as the agreement.
  </DoDont.Do>
  <DoDont.Dont>
    **A large filled "Allow" with a small grey "Not now" underneath.** The visual hierarchy
    is the real question being asked, and it is not a neutral one.
  </DoDont.Dont>
</DoDont>

## Motion

A consent sheet carries no health value, so the rule that a measurement never animates on
first paint, with no count-up and no sweep, has nothing here to act on. There is no figure to
reveal, only wording to read. Two pieces of motion remain, and each brings its own
reduced-motion answer from the token layer rather than a branch this component writes.

The larger one is Sheet's entrance, which ConsentSheet takes unchanged because it extends
Sheet. That travel is the `spring-sheet` token, an overdamped spring so a large surface
arriving does not bounce at the top of its travel and read as a dropped object. Its own
reduced-motion fallback is a cross-fade in place, because a sheet that appears with no travel
still needs to be seen to appear. Stripping the motion out entirely is the wrong answer, so
the token keeps the appearance cue and drops only the travel.

The smaller one is this component's own: the disclosure glyph that turns when the full wording
opens, on `--opsin-duration-fast` eased with `--opsin-ease-standard`.

<MotionDemo easing="--opsin-ease-standard" duration="--opsin-duration-fast" />

Under `@media (prefers-reduced-motion: reduce)` a rotation is one of the movements the token
policy removes, so the glyph turns without travel for a reader who asked for less. Nothing is
lost by that, because the open state the turn illustrates is also carried on the trigger's
`aria-expanded`, which every reader gets whether the glyph moves or not.

## Accessibility

Three of these are checked by a gate on every commit. The rest are arguments from the markup,
and they are labelled as such: `beta` promises that accessibility is claimed only where it
has been checked, with the gaps listed rather than left out.

**Checked, by `pnpm run check:a11y` on every commit:**

- **Neither colour axis reaches this component.** The static rig fails the build on any
  element that resolves both a category and a status custom property, and on any status
  surface with no `data-status`. Neither attribute appears anywhere in this file, and no
  status or category utility does either. The claim that a consent sheet takes no clinical
  colour is therefore enforced rather than asserted. See
  [The two colour axes](../health/two-colour-axes.mdx).
- **No type size in pixels, and no raw colour anywhere.** Every size is a step of the eleven,
  so the whole sheet scales with the reader's own root font size, and every colour is a
  semantic role rather than a hex value or a ramp step.
- **No banned word, in copy, in an identifier or in a shipped comment.** The same rig reads
  string literals, JSX text, identifier segments and comments in this file, and `shadcn add`
  copies all four into a consumer's project.

**Argued from the markup and true of the implementation, but not yet measured:**

- **The sheet is a modal dialogue named by its heading.** `heading` is Sheet's `title`, which
  Base UI renders as an `<h2>` and points the popup's `aria-labelledby` at, so the visible
  question and the accessible name are the same string. Focus moves to the popup on open,
  which is what makes the heading the first thing announced. It is also why neither decision
  control is focused. Auto-focusing accept is a keyboard dark pattern.
- **The purpose sentence is the sheet's accessible description.** It renders through
  `Sheet.Description`, which registers its id with the drawer store so the popup gains
  `aria-describedby` pointing at it, and a screen reader then announces the heading and then
  the purpose when the sheet opens. The scope list is deliberately left out of that
  description: `aria-describedby` is read in full on open, and a long list read before the
  reader has reached the controls would bury the one sentence that frames the decision. The
  scope stays in the reading order instead, after the description and ahead of the controls.
- **Escape closes without deciding.** `onDecision` is not called; the close arrives on
  `onOpenChange` with the route `escape`. Setting `dismissible={false}` cancels that route
  along with the scrim and the drag, and never the close control in the header. See
  [Sheet](./sheet.mdx) for why that does not make it a [Dialog](./dialog.mdx).
- **Accept and decline are adjacent in the tab order and identical in size.** They are two
  cells of one grid, separated by `--opsin-target-separation`, and each holds a `Button`,
  which floors its own hit area at `--opsin-target-minimum`. The pair never stacks: stacking
  would make one of them the control under the thumb. At 200% text the labels wrap and both
  controls grow taller together. The horizontal inset is reduced on both cells identically
  through the one class string they share, so the doubled padding does not eat the label, and
  `overflow-wrap: anywhere` is the last-resort guard that makes a word with no break
  opportunity break inside its box rather than be clipped by it. The pair stays equal by
  construction in every one of those states, because it is one grid carrying one class string
  on both controls.
- **The explanation is read before the controls in the DOM, and only there.** A screen reader
  follows source order, so the purpose, scope, details, withdrawal and consequence all precede
  the two answers. A sighted reader on a short viewport is not guaranteed the same order: the
  footer is pinned, so the answers stay in view while the last sentences may still be below the
  fold. This is a known property of pinning a decision control so it cannot scroll out of
  reach, not an oversight. Sheet stamps the footer while text remains below it, but that
  sighted-reader cue is not yet measured as perceptible, so a reader who cannot hear the
  DOM order is not yet promised it.
- **The scope facts are a list.** A `<ul>` with the browser's own markers rather than
  `list-style: none` and a restored `role="list"`, because Safari drops the list role from a
  marker-less list and a repair that depends on remembering an attribute is one that goes
  missing. It is spaced with a sibling margin rather than a flex `gap` for the same reason: a
  flex container blockifies its children, and an `<li>` that computes to `display: block` has
  no marker at all.
- **The full details disclose in place and announce their state.** The trigger carries
  `aria-expanded` and `aria-controls`; the panel is a named `role="group"`. It stays in the
  DOM while collapsed so that a printout carries the whole wording.
- **Nothing is conveyed by colour.** Both controls are the same variant, so the difference
  between them is their words. There is no fill that distinguishes accept from decline and no
  prop that could add one.
- **Reduced motion** is Sheet's answer rather than this component's: the slide becomes a
  crossfade in place. The one piece of motion here is the disclosure glyph's rotation, on
  `--opsin-duration-fast`, which the product stylesheet collapses to 1ms under the query.

**Not yet checked at all, and listed rather than omitted:**

- Contrast for the two decision controls against the sheet's material, in both themes and
  under increased contrast. Surface now answers `contrast-more:` in its own utilities and
  draws the sheet's edge as an `outline` that forced colours keeps and recolours rather than
  as a box-shadow it would strip, so the panel holds a boundary. The scrim's dimming is still
  lost, because a forced-colours palette replaces its tint with `Canvas`. Nobody has opened
  the site under a real Windows contrast theme, and that is the part still owed.
- Whether any screen reader announces the disclosure's expanded state as intended, and whether
  the heading is in fact the first thing read on open. Both are argued from the markup and
  from Base UI's source; nobody has listened to this component.
- Whether a browser reveals the collapsed panel on paper in every print path. The panel is
  hidden by `@media not print` rather than by the `hidden` attribute. Tailwind's own
  preflight declares that attribute `display: none !important`, so an attribute here would
  print nothing. The compiled output was checked against the pinned tailwindcss 4.3.3. What
  has not been checked is a printer.
- The 44pt targets and the 200% reflow are layout facts, and the layout half of the
  accessibility rig runs nightly rather than on commit. Neither has been measured for this
  component, and the specific number still owed is the rendered width of each decision label
  at 200% text against the width of its cell at a 390 viewport.
- **Print and export of the decision itself.** The sheet renders the wording; the decision and
  its timestamp exist only in what `onDecision` handed the product, because this component
  stores nothing. A reader entitled to a copy of what they agreed to needs that copy from the
  product, and no opsinjs component produces it yet.

Every part ConsentSheet draws carries a `data-slot`, so a product can style any of them from
outside without a single export or a class the component owns. What it never carries is either
colour axis: no element takes a `data-status` and no element takes a `data-category`, which is
how the claim that a consent surface is neither a clinical status nor a category stays
checkable rather than merely stated. It renders no measurement, so there is no
`data-opsinjs-value` anywhere either. Two of the slots above are conditional. The scope list
and the decisions grid appear only when the sheet can ask, so a rule written against
`consent-sheet-scope` or `consent-sheet-decisions` must not assume its element is present. The
question and the purpose are the exception to the naming: they render through Sheet's own
`title` and `Sheet.Description`, so they carry `sheet-title` and `sheet-description` rather
than a slot of their own, and both are documented on [Sheet](./sheet.mdx).

## API reference

<PropsTable name="ConsentSheetProps" />

`ConsentSheetProps` extends [SheetProps](./sheet.mdx#api-reference) with `title`, `children`
and `footer` removed, so `open`, `onOpenChange`, `detents`, `modal`, `dismissible` and
`className` are inherited unchanged and are documented on Sheet's own page. That is
[ADR 0021](../project/decisions/0021-modal-surfaces-own-their-open-state.mdx): the
specification said "extends Sheet" and declared neither half of the open pair, which as
written left this component unopenable. `title` is gone because `heading` is it. A
TypeScript `extends` that kept both would produce a modal surface with two names, one
announced and one read.

`<PropsTable>` reads only interfaces whose name ends in `Props`, so the three shapes those
props refer to are written out here. The installed file is the authority; this is a summary
of it.

```ts
interface ConsentScope {
  collected: string   // what is collected, as a complete sentence
  sharedWith: string  // who can see it, named
  retention: string   // how long it is kept, and what happens at the end
}

interface ConsentDetails {
  label: string       // what the control revealing the full text is called
  content: ReactNode  // the full text, disclosed in place
}

interface ConsentDecision {
  granted: boolean    // true for accept, false for decline; never for a close
  at: string          // ISO timestamp, taken when the control was pressed
  consentId: string
  textVersion: string
  scope: ConsentScope // the scope as it was shown, carried through unchanged
}
```

`ConsentDecision.scope` is the one addition to the specification's own record. The page's
Clinical meaning has always said the record is "a decision, a timestamp, the identifier and
version of the text that was shown, **and the scope consented to**", and the interface it
declared carried four of those five. A version id resolves to a scope only for a product that
kept every version it ever published; this puts the answer in the record.

`ConsentDetails` is the other. The specification typed `details` as a bare `ReactNode`, which
leaves the disclosure control with no name. The name a design system would invent is *terms*,
*details* or *learn more*, which is the exact class of label the specification refuses, in the
one list a screen reader can read with no sentence around it. Both halves travel together,
which is the shape `DisclaimerNote.more` already uses.

There is no `defaultGranted`, no `required` and no `hideDecline`. There is also no
`acceptVariant`, no `declineVariant`, no `emphasis`, no `order` and no `purposes`. Their
absence is the specification.
