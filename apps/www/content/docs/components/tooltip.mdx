Tooltip is a short supplementary label that appears when a pointer rests on a control or a keyboard moves focus to it, and vanishes when either leaves. It is built on Base UI's Tooltip primitive, which owns the hover and focus state, the open delay and the portal, and it draws only the neutral material surface: a card fill with a hairline and the one shadow the material ladder publishes for a floating note.

The decision that shapes the whole component is that a tooltip carries only the label you could delete. opsinjs is a phone-first system, and a phone has no hover: a touch reader never rests a pointer on anything, so a touch reader never sees a tooltip at all. There is no touch gesture that means hover without also meaning activate, so this is a limit to design around rather than a gap to close. Anything a reader needs to use a control goes on the screen, in the layout, where every reader meets it. A tooltip holds the note that is nice to have and safe to miss.

<ComponentInstall

The component is built on Base UI's Tooltip primitive, which is where the hover and focus handling, the open delay, the portal and the positioning come from, so installing it pulls in `@base-ui/react`. It mounts its own `Tooltip.Provider` inside, so a single tooltip works with nothing above it in the tree. A product that shows many tooltips on one screen should still hoist a shared provider of its own, so they open on one coordinated timer rather than each on its own.

```tsx
import { Tooltip } from "@/components/ui/tooltip"
```

```tsx

</Tooltip>
```

## When to use it

The exclusion that matters is the first, and it is the reason this component sat on the considered roster for so long. A tooltip is invisible on a touch screen, so anything it carries that a reader needs to act is a barrier for the readers who cannot reach it. The test to apply before reaching for a tooltip is simple: if the control cannot be used without the label, the label is not supplementary and does not belong in a tooltip. Put it on the surface, in a [Callout](./callout.mdx) or beside the control, where a thumb finds it.

The second and third exclusions keep a tooltip from standing in for two components that keep their content in the reading order. A [Term](./term.mdx) attaches a plain-English meaning to a clinical word without leaving the sentence and never removes that meaning from the accessibility tree, which is exactly what a tooltip would do. A [Field](./field.mdx) carries a hint that is part of the control and read with it. A tooltip is the right tool only when the content is genuinely optional and the control already names itself.

The parts above are identified by `data-slot` and are styleable from outside; none of them is an export, and there is no way to render the popup without the trigger it describes. The trigger is deliberately the caller's own element rather than a button this component adds, because the pressable control keeps its own role, its own name and its own focus ring, and the tooltip only borrows it to hang a description on. That is why `children` must be focusable: an element that cannot take focus never opens the tooltip for a keyboard reader.

## Examples

### On an icon button

The case people reach for a tooltip first. Each icon button carries its own name through `aria-label`, so a screen-reader and a voice-control user get the name whether or not a tooltip ever opens, and the tooltip repeats that name visibly for a reader using a pointer or the keyboard. The labels name fictional actions rather than measuring anybody, because an opsinjs example must never be mistakable for a reading.

### A supplementary hint

The setting is named in plain words on the surface, so a touch reader knows what it is without any hover, and the tooltip adds a second, optional sentence for a reader who wants it. ## Content guidelines

Keep a tooltip to a phrase, in sentence case, with no terminal punctuation unless it is a full sentence. It is a supplementary note, not a paragraph, and a long one is a block of text that belongs on the surface where every reader meets it. Write what the control does or what the value means, never an instruction that only appears on hover, because the reader who most needs the instruction is the touch reader who never sees it.

Never put the one fact a control cannot be used without in a tooltip. If the icon needs a word to be understood, the word goes beside the icon, not behind a hover. When a tooltip repeats an icon-only control's name, keep that name on the control's `aria-label` as well, so the name reaches assistive technology and voice control rather than living only in a popup that opens on hover.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user, and the largest limit, that a touch reader never sees a tooltip, is a property of the platform rather than a defect to fix, which is why the whole component is built around carrying nothing essential.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The popup and the arrow draw only the neutral chrome and material roles, so the component carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size.** The label is the `footnote` semantic step rather than a pixel size, so a reader who has turned their text size up gets a larger label rather than a pinned one.

**Argued, and true of the implementation, but not yet measured:**

- **The label is a description, not a name.** Base UI wires the popup to the trigger through `aria-describedby`, so it is announced after the control's own name rather than replacing it. The trigger keeps its own accessible name, which is why an icon-only trigger still needs an `aria-label`.
- **Focus opens it, Escape dismisses it, and focus never moves.** A keyboard reader reaches the tooltip by focusing the trigger, and Escape closes the label while focus stays on the control, so opening a tooltip never takes a reader out of their place.
- **At 200% text the popup grows with the text.** The label is sized from the type step and its padding is in space tokens, and the width is capped at the tight measure so a long label wraps into a readable block rather than clipping.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the footnote ink against the card fill, and the arrow's fill against the surface behind it. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the popup and the arrow draw under `forced-colors: active` and `prefers-contrast: more`, where the fill and the shadow are both replaced by the platform's own pair, and how the arrow reads on each of the four sides. None of this has been put in front of a machine or a high-contrast reader.

## API reference

<PropsTable name="TooltipProps" />

`content` is the whole of the label and is required, because a tooltip with nothing to show is a description that announces nothing. `children` is the trigger, and it must be focusable: the caller's own element is rendered in place and becomes the control the tooltip is attached to, so a bare span of text gets no tooltip on the keyboard and an icon-only trigger still needs its own `aria-label`. `side` is a preference that Base UI flips when the popup would run off screen, and `delay` governs the pointer only, because focus opens the tooltip at once.

## Related

**Easily confused with**

- [Term](./term.mdx) attaches a plain-English meaning to a clinical word without leaving the sentence, and never removes that meaning from the accessibility tree. A tooltip hides its content until hover or focus, so a definition belongs in Term, not a tooltip.
- [Field](./field.mdx) carries a hint that is part of a form control and is always visible. A tooltip is optional and appears only on hover or focus, so a hint a reader needs to fill in a field belongs in Field.
- [Callout](./callout.mdx) sets a piece of information apart on the surface, where every reader meets it. When a note is essential rather than supplementary, it is a Callout and not a tooltip.

**Used by**

- No pattern, recipe or screen composes it yet. It is a neutral primitive that a product attaches to its own icon buttons and labelled controls, keeping anything a reader needs on the surface rather than behind a hover.
