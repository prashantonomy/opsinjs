ScrollArea is a bounded region whose overflow scrolls, drawn with a thin neutral scrollbar in
place of the platform's default one. Its job is to keep a long stretch of content reachable
inside a box that is shorter than the content, such as a list, a card body or a wide row of
panels, on a page that still scrolls on its own.

The design decision that shapes the whole component is that it is for a bounded inner region
and never for the page. A custom scrollbar that replaces the browser's own is a frequent cause
of content becoming unreachable once a reader turns their text size up to 200%, because the
region's height was set for one text size and does not grow with the reader's. So the page
keeps its native scroll, and this component is reached for only where a single card or panel
has to hold more than it can show.

The region is built on Base UI's ScrollArea primitive, which is where the scrollable viewport,
its keyboard tab stop and the measured thumb come from, so installing it pulls in
`@base-ui/react`. It composes no other opsinjs component and renders no icon.

## Usage

```tsx
import { ScrollArea } from "@/components/ui/scroll-area"
```

```tsx
<ScrollArea maxHeight="16rem" className="rounded-lg border">
  <ul>
    {items.map((item) => (
      <li key={item.id}>{item.label}</li>
    ))}
  </ul>
</ScrollArea>
```

The exclusion that matters is the first, and it is the reason this name spent so long off the
roster. The single most damaging thing a scroll container does is replace the page's own
scroll. A reader who enlarges their text to 200% expects the page to grow and reflow, and a
region pinned to a height set for the smaller text clips the content against a ceiling instead,
which is a way to make the page's own words unreachable. So the page keeps the browser's native
scroll, and this component is set inside it for one bounded block at a time. If the thing that
has to scroll is the page, the answer is to change nothing and let the browser scroll it.

The second exclusion keeps the region from being reached for out of habit. A block that already
fits does not need a scroll area, and wrapping it in one adds a rail with nothing to do and a
height that will clip the block once its content or the reader's text grows. A plain
[Card](./card.mdx) holds the content and grows with it, which is the calmer default until the
content genuinely outgrows the box.

The parts above are identified by `data-slot` and are styleable from outside; none of them is
an export, and there is no way to render a scrollbar without its region. The rail and thumb are
kept deliberately plain, because a scroll area's whole promise is that the content stays
reachable, and a heavier rail competing with the content works against that promise rather than
for it.

## Content guidelines

Bound the region to a height that leaves the content reachable rather than one that looks tidy
at a single text size. Set `maxHeight` in a unit that grows with the reader, a rem rather than a
pixel count, so the region enlarges with the text instead of clipping it, and prefer a height
that shows a few whole rows so a reader can tell at a glance that there is more below.

Do not reach for a scroll area to shorten a page. A long page is not a defect to be boxed away,
and folding it into a scrolling window hides content from a reader who scans, from find-in-page,
and from a reader at larger text. If a page is too long, cut it or split it into sections a
reader can navigate, and let the browser scroll what remains.

<DoDont>
  <DoDont.Do>
    **A card body bounded to `maxHeight="16rem"` inside a page that scrolls on its
    own.** The panel holds a fixed place on the surface, the content inside it
    stays reachable from the keyboard, and the region grows with the reader's
    text rather than clipping it.
  </DoDont.Do>
  <DoDont.Dont>
    **The whole page wrapped in a scroll area with a fixed pixel height.** The
    browser's own scroll is replaced by one that does not grow with the text, so
    at 200% the page's own words are trapped below a ceiling the reader cannot
    move. Leave the page to scroll natively instead.
  </DoDont.Dont>
</DoDont>

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest
is argued and labelled as such. Accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with
a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The region draws only the neutral
  chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the
  two axes. The gate reads every element and would fail the build on a colour drawn from either
  axis or on a raw colour value, and there is neither here.
- **No px type size, no oversized radius.** Any text inside the region is the caller's, and the
  component's own chrome uses the space and radius tokens rather than pixels, so it scales with
  the reader's text.

**Argued, and true of the implementation, but not yet measured:**

- **The viewport is keyboard-scrollable.** Base UI renders the viewport with `overflow: scroll`
  and gives it a tab stop when there is more to see, so a keyboard reader reaches the region and
  scrolls it with the arrow keys. Nothing custom traps focus: the viewport is one ordinary tab
  stop a reader passes through, and the focus ring on it shows which region they have entered.
- **The content is not trapped.** The region scrolls its own overflow and, through
  `overscroll-contain`, hands the scroll back to the page once it reaches its end, so a reader is
  never stuck inside it.
- **At larger text the region grows with the content when `maxHeight` is a rem.** The height
  ceiling is the caller's to set, and a rem-based one enlarges with the text; a pixel-based one
  would clip, which is why the content guidance names the unit.

**Not checked at all, and listed rather than omitted:**

- The thumb's contrast against the surfaces it rides over, at the non-text floor for a control.
  `scripts/check-contrast.mts` has not been run for this component, which is why the report below
  is empty rather than reassuring.
- What the rail draws under `forced-colors: active`, and whether the fade-in leaves a screen-
  reader or switch user a handle to aim at. None of this has been put in front of a machine or a
  disabled user.

## API reference

<PropsTable name="ScrollAreaProps" />

`maxHeight` is the load-bearing prop: it is what gives the region something to overflow, so a
vertical scroll area needs either it or a height class through `className`, and given neither
the region grows to fit its content and a development warning names the omission. Set it in a
rem so the region grows with the reader's text rather than clipping at a pixel ceiling.
`orientation` chooses which axes may scroll and defaults to `vertical`; `both` adds a second
rail and the corner where they meet. `className` is the one route by which colour can reach the
region, and the two-colour-axes rule applies to it in full.

## Related

<RelatedComponents name="scroll-area" />

**Easily confused with**

- [Card](./card.mdx) draws a bounded surface but does not scroll: it grows with its content. A
  scroll area is what a card body becomes once its content outgrows the height you want to hold.
- [Sheet](./sheet.mdx) is an overlay that slides in and owns its own scroll inside. A scroll
  area is an inline region on the surface, not a layer over it.
- [Table](./table.mdx) may be wrapped in a scroll area to let a wide table scroll sideways inside
  its column, but the table is the content and the scroll area is only the box around it.

**Used by**

- No pattern, recipe or screen composes it yet. It is a neutral layout primitive that a product
  wraps around its own long lists and card bodies where the content outgrows the box.
