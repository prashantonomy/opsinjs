Questionnaire is the styled shell around a set of questions a product owns. It groups them under one title, gives the group a single accessible name, shows the reader where they are in the set, and tells the product when the reader has reached the end. It holds no question of its own, and it reaches no verdict about any answer.

The design decision that shapes the whole component is the one the roster asked for when it declined the name. A validated instrument is licensed, worded, scored and interpreted by its publisher, and a component that rendered one would invite a product to edit its wording or its scoring, which is a clinical-safety problem rather than an API one. So this shell ships no instrument, no question, no option, no score, no band and no interpretation. Every one of those arrives from the product, and the product does its own scoring off this component, where opsinjs cannot reach it.

A named set of three fictional questions, each with a control the product supplied, and the progress readout turned on. Questionnaire has no dependency beyond the shared substrate every component installs. It composes no other component and is built on no Base UI primitive, because a shell that renders the controls it is handed needs none of them. The controls themselves, a Field, a RadioGroup, a ScaleInput or a Textarea, are the product's to install and compose.

The exclusion that matters most is the one no `instead` can point at, because there is no component for it: scoring and interpreting the answers. The moment a surface turns a set of answers into a number, a band or a sentence about the reader, that surface is the product's own, built with the product's own logic and the status components, and it belongs well away from this container. Questionnaire renders the questions and signals completion; it never grades what came back, and there is no code path in it that could.

The first exclusion is the honest lower bound of the form. One question is a [Field](./field.mdx), because a shell that groups a set adds nothing around a set of one. The second keeps the shell from swallowing a pattern that reads differently: a grid of symptoms a reader taps on and off is a [SymptomPicker](./symptom-picker.mdx), not a sequence of questions, and forcing it into a question list loses the multi-select shape.

## Clinical meaning

**What it asserts.** Questionnaire asserts exactly two things: here are the questions to answer, in this order, and here is how far through them you are. Both are about the form rather than the person. It makes no claim about anyone's health, states no reading, computes no score, and reaches no conclusion. The progress count is an ordinal of position in the list, nothing more, and it is drawn as plain text so it can never be mistaken for a value.

**What it must never be read as.** It is not a score, not a screening result, not a diagnosis and not triage. A questionnaire on a screen does not mean the product has assessed anything; it means the product has asked. Rendering a validated instrument's wording or its scoring is the product's responsibility and its hazard, never opsinjs's: the shell will draw whatever questions it is handed, so a product that alters a licensed instrument's text or grades it wrongly owns that mistake in full. opsinjs supplies the container and refuses the clinical judgement, which is the line [Regulatory context](../health/regulatory-context.mdx) draws around a presentation layer.

**Which colour axis it may use.** Neither. A questionnaire states no clinical level and names no category of measurement, so it carries neither `data-status` nor `data-category` and draws only neutral chrome. A result the product computes from the answers is a status surface, and it is built with the status components on the product's own screen, not tinted into this form. Putting a status or a category colour on the shell would be the axis collision [The two colour axes](../health/two-colour-axes.mdx) exists to prevent, and it would also dress a container as though it had reached a verdict.

**Who owns the thresholds and the words.** The product, always. Every question, every option, every word of the title and every piece of scoring arrives from the product or lives entirely on the product's side. opsinjs ships no instrument, no default question, no threshold and no interpretation text, because shipping any of those would be shipping a clinical decision to every product that installed the shell. The container is the only thing this component supplies.

## Content guidelines

Write every question and every option in the reader's own words, and let the product own all of that text. Where a question comes from a licensed instrument, render its wording exactly as the publisher licenses it and change nothing, because the shell will draw whatever it is handed and cannot tell an edited item from the original. Keep the title a short name for the set rather than an instruction, and let the progress readout do the work of saying how far through it the reader is.

Never write a score, a band or a sentence about the reader into the shell. If the product computes a result from the answers, that result is a separate surface built with the status components, and it sits after the form rather than inside it. A verdict rendered in the questionnaire would be a clinical judgement opsinjs does not make, dressed as part of a container that exists precisely so it makes none.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The shell draws only the neutral chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size.** The title, the prompts and the progress readout are all semantic type steps rather than pixel sizes, so a reader who has turned their text size up gets a larger form rather than a pinned one.

**Argued, and true of the implementation, but not yet measured:**

- **The form has one accessible name and the progress readout speaks its changes.** The title is wired as the form's `aria-labelledby`, so a screen-reader user hears what the set is before its first question, and the progress line is an `aria-live="polite"` region so its "Question N of M" text is announced as focus moves. Whether that announcement helps or talks over the reader has been reasoned about rather than heard.
- **The shell adds no key of its own and steals none.** Tab moves through the product's controls in order, and every arrow, space and return belongs to the control it lands in. The one event the shell owns is submit, which it cancels so a stray Return cannot reload a half-answered form.
- **At 200% text the questions stack and wrap.** The spacing is in space tokens and the type is in steps, so the whole form scales, and nothing is truncated and no ellipsis is set anywhere in the file.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the hairline between questions against the host ground, the title ink against it, and the muted progress ink against it. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring. This shell sets no surface of its own, so each pair is painted on whatever ground the host provides rather than a matching `-surface`.
- How the aria-live progress readout plays for a screen-reader user, and whether announcing position on every focus move is the right amount of speech or too much. It has been reasoned about and not listened to.
- What the form draws under `forced-colors: active`, where the hairlines are replaced by the platform's own pair. None of this has been put in front of a machine or a high contrast user.

## API reference

<PropsTable name="QuestionnaireProps" />

`questions` is the whole of the content: an array of an id, a prompt and a control, in the order the reader answers them. The shell renders each control untouched and reads no value from it, which is what makes it structurally unable to score or interpret the answers. `onComplete` is told that the reader finished and nothing else, because the shell has no answers to give it; a product reads its own controls and does its own scoring on its own side.

`showProgress` turns on the "Question N of M" readout, which is a plain ordinal of position rather than a health value, and `title` supplies the form's accessible name. `title` is optional so a product can name the set in the surrounding page, but a form with no name of its own raises a development warning, because a set of questions a screen-reader user meets unnamed is a set they cannot place.
