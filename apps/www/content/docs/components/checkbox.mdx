Checkbox is a single labelled box a reader ticks, unticks, or leaves in a mixed state that is neither. Its home is a lone agreement or a single setting a reader turns on or off, and it carries its own visible label with, when there is one, a line of supporting guidance beneath it.

This is the single box, not a set. A box for choosing any number of options from a list, where a head box reflects and drives its children, is a checkbox group, and this component is one box you compose into that group rather than the group itself. The mixed state is offered here so that a group built from these boxes has a head box to render, and the three-state parent in the examples is a relationship a product wires up by passing `checked="indeterminate"` and handling the change.

## Preview

A single box with a label and a line of guidance beneath it, ticked so the filled state is what you meet first. The thing worth checking is that the ticked box carries a Check glyph inside the action fill rather than resting on the fill's colour, so read it in greyscale: the tick is still a tick, the box is still filled, and toggling it off leaves a neutral hairline that reads as clearly empty.

The box is built on Base UI's Checkbox primitive, which owns the keyboard contract, the hidden form input and the mixed state, so installing it pulls in `@base-ui/react`. It also draws the tick and the mixed dash with lucide's Check and Minus glyphs, so it pulls in `lucide-react`.

## When to use it

<WhenToUse
  use={[

    { case: "The label has to say what a reading means or how urgent it is. A ticked box carries no clinical level, and dressing one up as a status tells that level by a fill with no word and no glyph a reader can rely on.", instead: "status-pill" },
    { case: "You need the box wired into a form's label, hint, error and validity as one unit rather than standing on its own.", instead: "field" },
  ]}

The exclusion that matters is the first, and it is a question about what the choice permits. A checkbox permits any number of answers, including none, so a set of boxes says "tick every one that applies". A [RadioGroup](./radio-group.mdx) permits exactly one, so choosing a second answer clears the first. Using checkboxes for a one-answer question invites a reader to tick two, and using a radio group for a many-answer question makes them unable to tick the second, so the shape of the answer decides the control rather than how the row looks.

The second exclusion keeps a checkbox off the status axis. A ticked box is filled with the shared action role, the same neutral fill the primary [Button](./button.mdx) uses, and it never carries a category or a status colour. A label that has to mean "steady" or "needs attention" is a [StatusPill](./status-pill.mdx), which draws the colour, the icon and the word together, because a state told by a fill alone is a state some readers cannot read.

The parts above are identified by `data-slot` and are styleable from outside; none of them is an export. The `<label>` element wraps the box and the label words rather than the description, which is the one structural choice worth knowing: the words inside the label become the box's accessible name and toggle it on a tap, while the description sits outside as a sibling and is tied to the box with `aria-describedby`, so it is announced as guidance and does not lengthen the name. The indicator has a cardinality of `0..1` on purpose, because Base UI mounts it only while the box is ticked or mixed and there is genuinely no mark in the DOM when the box is empty.

## Content guidelines

Write the label as the thing the reader is agreeing to, phrased so that a tick means yes and an empty box means no. "Email me a copy" ticks to opt in; a label phrased as a negative, such as "Do not email me", makes an empty box a double negative nobody can read at a glance. Keep the label to a short line, and put anything longer, such as what ticking the box will do or where the copy is sent, in the `description` rather than swelling the label.

Never write a clinical status word into a checkbox label. "Steady" and "Needs attention" belong in a [StatusPill](./status-pill.mdx), where the word sits beside the colour and the glyph that let a reader who cannot use the colour still read the level. A status word beside a tick is a level told without its carriers, which is the mistake the two axes are kept apart to prevent.

<DoDont>
  <DoDont.Do>
    **"Email me a copy" with a description of what that does.** The label ticks to
    opt in, reads as a single clear yes, and hands the detail to the description so
    the choice stays scannable.
  </DoDont.Do>
  <DoDont.Dont>
    **"Do not exclude me from reminders" as the label.** A double negative on a box
    where a tick already means yes leaves the reader working out whether ticking
    opts them in or out. Phrase the label so a tick is a plain yes.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The box draws only the shared action role and the neutral chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size.** The label is the `body` step and the description the `footnote` step, so a reader who has turned their text size up gets a larger box and larger words rather than a pinned size.

**Argued, and true of the implementation, but not yet measured:**

- **The box has a real keyboard contract, delegated to Base UI.** Tab moves focus onto the box, Space toggles it, and the mixed state is exposed as `aria-checked="mixed"` rather than as a third colour. This is the WAI-ARIA checkbox pattern the primitive implements rather than a bespoke one, but it has not been driven with real assistive technology here.
- **The label names the box and toggles it.** The label wraps the box, so its words are the accessible name and a tap anywhere along the row toggles the box, and the pointer target is the whole row rather than the small box. A missing or empty `label` raises a development warning rather than rendering a box a reader cannot identify.
- **The description is announced as guidance, not as the name.** It is tied to the box with `aria-describedby` and sits outside the label, so a screen reader reads it after the name rather than folding it in.
- **At 200% text the box and its words grow together.** The box is sized in rem and its label and description are type steps, so the whole control scales rather than clipping.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair for this component's own surfaces: the neutral hairline of the unticked box against the page ground, and the muted description ink against that ground. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the box draws under `forced-colors: active`, where the action fill and the hairline are both replaced by the platform's own pair, and whether the ticked, unticked and mixed states stay distinct in that mode.

## API reference

<PropsTable name="CheckboxProps" />

`label` is required, because a box with no words asks a reader to agree to something they cannot see, and a missing one raises a development warning rather than rendering a bare box. `checked` accepts `true`, `false` or the string `"indeterminate"` for the mixed state, and omitting it leaves the box uncontrolled from an unticked start; `indeterminate` is the alternative route to the mixed state for a caller who keeps `checked` as a plain boolean, and it wins when both are given. `onCheckedChange` reports the new ticked state as a boolean, so a box that was mixed reports `true` when the reader ticks it, and the caller stores that and passes it back.

## Related

<RelatedComponents name="checkbox" />

**Easily confused with**

- [RadioGroup](./radio-group.mdx) is the control for a choice where exactly one option can be chosen. A checkbox permits any number of answers including none; a radio group permits one. The shape of the answer, not the look of the row, decides between them.
- [Switch](./switch.mdx) is the control for turning one thing on or off with an immediate effect, such as a setting that takes hold the moment it flips. A checkbox records a choice that a form or a save commits later, and it has a mixed state a switch does not.
- [Field](./field.mdx) wires a control to its label, hint, error and validity as one accessible unit. Reach for it when a box has to live inside that machinery rather than stand on its own.

**Used by**

- No pattern, recipe or screen composes it yet. It is a form primitive a product drops into its own agreements, preferences and lists, and the checkbox group it heads is a product's to assemble rather than something the corpus ships today.
