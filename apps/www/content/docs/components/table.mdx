Every chart in this system owes the reader a way to read it that does not depend on seeing it. A line going up is a shape, and a shape is not a figure a screen reader can read out or a keyboard user can tab to. So every chart ships a table beside it, and this is that table: the same numbers, in rows and columns, in a real `<table>` with a caption, headers that carry their scope, and its own sideways scroll.

Everything unusual about it follows from what it refuses to be. It is not a data grid. It does not sort, it does not let a reader select a row, and it does not virtualise ten thousand rows. Those are a project of their own, and they would turn the honest twin of a chart into the largest component in the catalogue. The data driven API keeps it small and keeps the parts a reader relies on, the caption and the header scopes, out of a caller's reach to get wrong.

## Preview

One caption, one text column that labels each row, and two numeric columns that right-align in tabular figures. Open it under the product theme and turn the text size up. Two things are worth checking by eye: that the numbers in a column line up on their digits as the widths change, and that a table wider than the frame scrolls inside its own box rather than dragging the page sideways.

## Installation

<ComponentInstall
  name="table"

Table composes nothing and depends on nothing, so it installs on its own. The numbers you put in its cells are usually a [Value](./value.mdx), which you install separately and nest in the cell.

## Usage

```tsx
import { Table } from "@/components/ui/table"
```

```tsx
<Table
  caption="Example figures by period, and not a real record"
  columns={[
    { key: "period", header: "Period" },
    { key: "count", header: "Count", numeric: true },
  ]}
  rows={[
    { period: "Period one", count: "12" },
    { period: "Period two", count: "1,000" },
  ]}
/>
```

The last exclusion is the one that matters most, and it is a decision made before the first row is drawn. opsinjs ships no data grid, and Table is deliberately not one: it has no sorting, no selection and no virtualisation, and adding them on top of it fights the component rather than extending it. A surface that genuinely needs a grid builds one on Base UI, on a Card or a surface of its own, and owns the comparator, the selection model and the announcement of a new order. Card is the surface such a grid sits on rather than the grid itself. Table is the readable twin of a chart, and its job is to be read.

That is the whole component. The parts are identified by `data-slot` and are styleable from outside, and none of them is an export: there is no `Table.Row` to render on its own, which is what stops a caller assembling a table with no caption or a header cell with no scope. The caption is the one part that is required and always drawn, because a table a screen reader user meets with no caption is a grid of numbers naming nothing.

## Content guidelines

Write a caption that names the rows and the columns, so the table stands on its own when a screen reader reaches it away from the chart beside it. "Weekly figures for the example account, in the example unit" is a caption; "Table" and an empty string are not. Where a visible heading already names the data, keep the caption in the markup with `captionHidden` rather than dropping it, because the heading names it for the eye and the caption names it for the ear.

Mark a column of numbers `numeric`. It right-aligns the column and sets it in tabular figures, so the numbers line up on their digits and do not re-kern as a digit changes, which is what lets a reader compare two rows at a glance. A column of numbers left as text ragged-aligns and shifts sideways as the data changes, and two rows no longer line up. Use the same precision down a column, through the [Value](./value.mdx) you nest in each cell, so a comparison the reader is meant to make is arithmetic they do not have to do.

## Accessibility

Some of what follows is checked by a gate on every commit and the rest is argued. They are labelled separately, because `alpha` promises that accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nobody has yet listened to this component in a screen reader.

**Checked, by the gates on every commit:**
- **No `px` type size anywhere.** The caption, the headers and the cells are set from the generated ramp, `text-opsin-subheadline`, `text-opsin-footnote` and `text-opsin-body`, so the table scales with the reader's own text size.
- **No raw colour literal and no ramp step.** The ink is the neutral `--foreground` and `--muted-foreground` roles and the dividers are `border-border`, so a hex, an `oklch()` or a numbered ramp step fails the build.
- **No banned word in the reader facing strings this component owns, none in its development warnings, and none as a code identifier.**
- **No shipped threshold and no unowned numeric interval.** No clinical number is written into this component and none passes through it.

**Enforced by the API rather than by a gate:**
- **The caption is required and always rendered.** It is a `string` a caller cannot omit at the type level, and `captionHidden` takes it off the screen with the sr-only pattern rather than out of the markup.
- **The headers carry their scope.** Every column header is `scope="col"`, and the first cell of each row is `scope="row"` when `rowHeader` is on, which is the default, so a listener meets each value with a row name and a column name rather than as a loose number.
- **It cannot be tinted from either axis.** There is no colour prop, no `data-status` and no `data-category`. The one hole is `className` on the container, which reaches only chrome.

**Argued, and true of the implementation, but not yet measured:**
- **A wide table scrolls inside its own box.** The container is `overflow-x-auto`, so a table wider than the viewport scrolls sideways within itself and the page body does not. The container is focusable with `tabIndex={0}` and carries the focus ring, so a keyboard reader can reach the scroll. It has no role and no name of its own, and whether it should be a labelled region is the open question above.
- **It reflows at 200% text.** No fixed height and no `px` size anywhere, cells wrap rather than truncate, and a table too wide to fit falls to the scroll container rather than to the viewport. Nobody has watched this at 200% in either theme.
- **There is no motion.** No transition and no animation, so `prefers-reduced-motion` has nothing here to act on.

**Not yet checked at all, and listed rather than omitted:**
- Whether a screen reader reads the row and column structure usefully from the scopes and the caption. Argued from the markup, not heard.
- The measured contrast of the header ink, the caption ink and the hairline dividers on the surfaces a table sits on. The neutral token roles are published below; the rendered pixels are not.

## API reference

<PropsTable name="TableProps" />

`caption` is typed `string` and required. A table with no caption passes every code gate in this repository and reaches a screen reader user as a grid of numbers naming nothing, so the requirement is at the type level and there is no honest caption this component can invent in its place. `captionHidden` is the escape hatch for the twin under a heading, and it hides the caption without removing it.

`columns` and `rows` are the whole data model, and the model is flat on purpose. A cell is a `ReactNode`, so the number in a numeric column is usually a [Value](./value.mdx): Table owns the grid, the scope and the alignment, and Value owns the rounding, the unit and the spoken form. `numeric` on a column right-aligns it and sets it in tabular figures, and it stamps `data-opsinjs-value` on those cells as the tabular-figures hook, empty because Table never owns the magnitude.

There is no `onSort`, no `selectedRows` and no `virtualized`. A number that has to be sortable or selectable belongs in a product's own grid, and Table is the readable twin of a chart rather than that grid.
