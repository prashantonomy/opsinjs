NumberField is a single number a reader types directly or steps up and down with two buttons. Its home is a plain quantity or a count, the number of copies to print or the number of people sharing an entry, where nudging the value one at a time is as natural as typing it.

The decision that shapes the whole component is that it is not a clinical control. A number a reader walks up one press at a time is the wrong shape for a measurement, which is read off a device and typed in whole. This field holds no unit, no reference range and no clinical vocabulary of any kind. It counts, and when the number means something a clinician would recognise the control is [ReadingInput](./reading-input.mdx) instead.

The exclusion that matters is the first, and it is what keeps this component off the clinical surface. A stepper invites a reader to walk a number up from a default, which is exactly the wrong gesture for a measurement: nobody arrives at their blood pressure by pressing plus. So a health reading is a [ReadingInput](./reading-input.mdx), which carries the unit beside the number, takes an out-of-range warning the product writes, and holds a compound reading as one named group. A NumberField carries none of that, because a count needs none of it.

The other case worth naming is a value on a continuous track, where the position in a range matters more than the exact number. That is a [Slider](./slider.mdx)'s job, and the roster declined a slider for readings, so a health reading on a track is neither this component's to hold nor a slider's. Where a count genuinely wants stepping and a sensible `step`, a NumberField is the control that stays; where a reading wants a track, the answer is not this component and not a slider but a number typed in whole through ReadingInput.

The parts above are identified by `data-slot` and are styleable from outside; none of them is an export, and there is no way to render a stepper without the group. There is deliberately no scrub area. Base UI offers one, a label the reader drags across with the pointer to change the value, and it is left out because it is a pointer-only affordance with no keyboard or touch equivalent, so a field that relied on it would hide a way to change the number from anyone not using a mouse. The buttons and the arrow keys are the two routes this field ships, and both work for a touch reader and a keyboard reader alike.

## Content guidelines

Name the count itself in `label`, the thing being counted rather than a bare "Number" or a unit. "Number of copies" tells a screen-reader user what the value means before they hear it; "Number" leaves them with a figure and no noun. Keep the name the same wherever the same count appears, so a reader who learnt this field counts "copies" does not meet "prints" meaning the same thing elsewhere.

Choose `step` to match the smallest change the count is really measured in, which for a whole count is `1`, and set `min` and `max` only where a real floor and ceiling exist. A bound the count does not actually have is a bound the reader hits for no reason, and a `step` finer than the count is measured in gives the buttons a value nobody wanted. When you say a count has no upper limit, do not invent a `max` to be safe; leave it off, and the increment button never disables.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The field draws only the neutral chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size, and a 44px target floor.** The input's number is the `body` semantic step rather than a pixel size, and each stepper floors its hit area at `--opsin-target-minimum` in rem on both axes, so a reader who has turned their text size up gets a larger field with pressable buttons rather than a pinned one.

**Argued, and true of the implementation, but not yet measured:**

- **The control is one tab stop with a real keyboard contract.** Base UI renders the input as a spinbutton, steps it with the Up and Down arrows, jumps with Page Up and Page Down, and snaps to the bounds with Home and End, so a keyboard reader changes the value without ever reaching for the buttons.
- **The buttons are named and wired.** Each stepper carries an `aria-label`, "Increase" or "Decrease", and an `aria-controls` pointing at the input, so a screen-reader user meets two named controls rather than two anonymous icons, and each disables itself at its bound so a reader cannot press past `min` or `max`.
- **The accessible name is required.** `label` is applied as the input's `aria-label`, and a missing or empty `label` raises a development warning rather than rendering an unnamed spinbutton.
- **The focus ring travels with the component.** It is carried in each button's and the input's own class list rather than left to the product stylesheet, so a project installed without that stylesheet keeps the ring.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the group hairline against the ground, the stepper glyphs against the button fill, the input ink against its background, and the muted disabled ink at a bound. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the field draws under `forced-colors: active`, where the hairline, the hover and the focus ring are all replaced by the platform's own pair, and whether reaching a bound is announced to a screen reader at all.

## API reference

<PropsTable name="NumberFieldProps" />

`value` and `onValueChange` make this a controlled component with no internal value state: the caller stores the number, or `null` when the field is empty, and passes it back. `label` is required because a spinbutton with no accessible name is a defect the type system cannot otherwise prevent. `min`, `max` and `step` shape the count and its stepping, and they are the count's own bounds rather than a clinical range: the field holds no reference range and reaches no verdict about the number it carries.

## Related

<RelatedComponents name="number-field" />

**Easily confused with**

- [ReadingInput](./reading-input.mdx) is the control for a clinical measurement. It carries the unit beside the number, takes an out-of-range warning the product owns, and holds a compound reading as one named group. A NumberField counts and carries none of that, so the moment the number is a reading, it is ReadingInput.
- [Field](./field.mdx) with a numeric control is the plainer choice for a number typed once and not nudged, such as a year or a reference code. It draws no steppers, so it does not invite a reader to walk the value up and down.
- [Slider](./slider.mdx) is the shape for a value on a continuous track, where position in a range matters more than the exact number. The roster declined a slider for readings, so a health value on a track is a number typed in whole rather than dragged.

**Used by**

- No pattern, recipe or screen composes it yet. It is a neutral counting primitive that a product drops into its own forms and settings.
