Textarea is a multi-line text box for a free-text note a reader writes in their own words, such as a line about how a day went or a question for a clinician to read later. It is a native `<textarea>` element with the opsinjs border, radius, type step, padding and focus ring pulled onto it, and nothing more.

The design decision that shapes the whole component is that it is the native element rather than a Base UI primitive. Base UI ships no textarea, because a multi-line box has no roving focus, no popup and no composite behaviour for a primitive to own. What the raw element lacks is the tokens: left to the browser it draws a grey box in the system font at a pixel size, off every scale the rest of the system keeps. So this component is the native control wearing the tokens, which is why it stays a server component with no state of its own.

## When to use it

<WhenToUse

  ]}
  avoid={[

    { case: "The reader is entering a measurement with a unit, such as a blood pressure or a weight, which needs the number formatted and the unit shown rather than free text.", instead: "reading-input" },
    { case: "The reader is choosing from a fixed set of answers rather than writing one, which is a select or a radio group inside a field, not a text box.", instead: "field" },
  ]}
/>

The exclusion that matters is the second, and it is a question about what the reader is entering. A note is prose the reader owns, and opsinjs formats none of it: it stores and shows back exactly the characters typed. A measurement is not prose. It has a number, a unit and a precision the product owns, and typing it into a free-text box loses all three, so a reading belongs in [ReadingInput](./reading-input.mdx), which shows the unit beside the number and keeps the formatting the same everywhere.

The first exclusion keeps a note field from standing in for a plain input. A textarea sized for a paragraph around a one-word answer wastes the space and invites a reader to write more than the question wants. A single-line answer belongs in a [Field](./field.mdx) with an input, which reads as a question with one line to answer rather than a box waiting for an essay.

Textarea is a single element, so there is no part tree to nest and no composable slot to fill. What a caller controls is the text through `value` or `defaultValue`, the resting height through `rows`, the ceiling through `maxLength`, and how the box is named for assistive technology. There is deliberately no character-count part and no toolbar: a live count is content a product places beside the box in its own words, and a formatting toolbar would make a rich-text editor of a plain note field, which is a different component with a different accessibility contract.

## Content guidelines

Put the question in a label, never only in the placeholder. A placeholder is grey by design and disappears the moment a reader types, so a box whose name lives only there loses it for the very reader who needs it most, the one part way through a long note who has forgotten what it was for. Use the placeholder for an example of the kind of answer, such as a short phrase, and let the label or `aria-label` carry the question.

When the field has a length limit, say so in words near the box before the reader reaches it, rather than letting `maxLength` refuse a keystroke in silence. State the limit as a plain sentence, and if the product shows a running count, count down to the ceiling rather than up from zero, so the number a reader watches is the room they have left.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The box draws only the neutral chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size, and a 44pt target floor.** The text is the `body` semantic step rather than a pixel size, so it grows with the reader's text size, and the box floors its height at `--opsin-target-minimum` in rem, so a box dragged short stays tappable and the floor grows with the text too.

**Argued, and true of the implementation, but not yet measured:**

- **The box needs an accessible name, and the component will not invent one.** Inside a Field the field's label names it; standalone, `aria-label` or an `id` with a real `<label htmlFor>` does. When none of `aria-label`, `id` or `name` is present a development warning names the gap rather than shipping an unnamed box.
- **Validity is not carried by colour.** `invalid` sets `aria-invalid` and leaves the border on the neutral role, because a form error is not a clinical status. The message that says what to fix is [Field](./field.mdx)'s to place, in words beside the label, which a reader can read whether or not they see a colour.
- **The focus ring is carried in the box's own classes.** A project installed without the product stylesheet keeps the ring, and a disabled box takes the muted surface and the not-allowed cursor rather than an opacity wash, so its text stays legible while it reads as unavailable.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the body ink and the muted placeholder against the background, and the neutral border around the box. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the box draws under `forced-colors: active` and `prefers-contrast: more`, where the border and the browser's own resize handle are replaced by the platform's pair. None of this has been put in front of a machine or a high contrast user.

## API reference

<PropsTable name="TextareaProps" />

The load-bearing choice is `value` against `defaultValue`: pass `value` with `onChange` and the box is controlled and the caller owns the text, or pass `defaultValue` and the box owns it and the caller reads it off the form on submit. `invalid` is the one to read carefully, because it sets `aria-invalid` and nothing else: it draws no colour, since a form error is not a clinical status, and the visible message belongs to [Field](./field.mdx). `aria-label`, `id` and `name` are the three routes to an accessible name, and a box with none of them raises a development warning rather than shipping unnamed.

**Easily confused with**

- [Field](./field.mdx) with an input is the control for a single-line answer, such as a name or a place. A textarea is sized for a paragraph, so reaching for it around a one-word answer wastes the space and invites more than the question wants.
- [ReadingInput](./reading-input.mdx) is the control for a measurement with a unit. It formats the number and shows the unit beside it, which a free-text box cannot do, so a reading never belongs in a textarea.

**Used by**

- No pattern, recipe or screen composes it yet. It is a neutral form primitive a product drops into its own long-answer fields, most often as the control inside a [Field](./field.mdx).
