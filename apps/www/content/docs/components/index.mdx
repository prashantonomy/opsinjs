Every component is `shipped`, which means its source installs and renders and its API may change in any release. Each was audited against WCAG 2.2 AA by its own authors. None has had an independent accessibility review or a clinical review, so none is ready for a production health surface.

## Install

```bash
npx shadcn@latest add @opsinjs/<name>
```

The CLI copies the component's source and the opsinjs `lib/` files it reads into your project, and adds its npm dependencies. `<name>` is the id in each link below. Add the `@opsinjs` entry to `components.json` first, as [Getting started](../getting-started.mdx) shows.

## Usage

```tsx
import { Button } from "@/components/ui/button"
```

```tsx
<Button variant="primary" onClick={save}>
  Save reading
</Button>
```

The import path follows the `ui` alias in `components.json`.

## Choosing a component

Start from your data, and from who assigned any status it carries.

- A measurement the reader interprets is a ResultCard, or a RangeBar when its place in the range is the point. A MetricTile that needs interpreting is a ResultCard at the wrong size.
- A ScoreDial implies a composite index, so it never shows a single measurement.
- Status appears only where a rule your product owns assigned it, and no component computes one. A category, a trend or a position against a range is not a status. See [Two colour axes](../health/two-colour-axes.mdx).
- Allow at most one urgent surface per screen. See [Alerts](../health/alerts.mdx).
- Decide what each component renders in all five data states: empty, loading, error, stale and partial. See [States](../foundations/states.mdx).
