component page follows, without the clinical material doing the work.

The first exclusion is the one that gets ignored and the one that costs most. A button that
navigates cannot be opened in a new tab, cannot be copied, does not appear in a screen
reader's list of links, and does not work when JavaScript has not loaded. If the result is a
new URL, it is a link, however it is styled.

## Anatomy

<Anatomy name="button" />

<CompositionTree name="button" />

**Label** is the text and it is never optional — an icon-only control is a different
component, because it needs an accessible name supplied some other way and a different target
treatment. **Icon** is a leading or trailing glyph, always decorative. **Busy** is the
in-place loading indicator that replaces the icon slot, never the label. **Target** is the
hit area, which extends beyond the visible bounds to meet the 44pt floor when the button is
visually smaller.

Proposed part hierarchy. This is the specification the implementation must match.

```text
Button                         root; a real <button>, or an <a> only when it navigates
├── Button.Icon                optional, leading or trailing; decorative
├── Button.Label               required; never removed by any prop
├── Button.Busy                replaces the icon slot; the label stays put
└── Button.Target              hit area; ≥44pt even when the visual is smaller
```

`Button.Label` cannot be removed. There is no `iconOnly` prop, because every system that
shipped one ended up with unlabelled controls in production.

## Proposed API

<NotBuiltYet name="button" />

```ts
// PROPOSED. Not implemented. A specification for review, not an API to generate
// code against. It will change without a deprecation cycle.

/**
 * Four variants, in descending emphasis. Deliberately few: the discipline of
 * one primary action per surface is enforced by not having nine ways to be
 * almost primary.
 */
export type ButtonVariant = "primary" | "secondary" | "quiet" | "destructive"

export interface ButtonProps
  extends Omit<React.ButtonHTMLAttributes<HTMLButtonElement>, "children"> {
  variant?: ButtonVariant
  /** Both sizes meet the 44pt target floor; "sm" is visually smaller only. */
  size?: "sm" | "md"
  /** Required. There is no icon-only Button; that is a separate component. */
  children: React.ReactNode
  icon?: React.ReactNode
  iconPosition?: "leading" | "trailing"
  /**
   * In-place loading. The label stays visible and the button stays in the
   * accessibility tree, announced as busy rather than removed from it.
   */
  busy?: boolean
  /**
   * Fills its container. Used at the bottom of sheets and forms, where the
   * primary action should be the width of the thumb's reach.
   */
  fullWidth?: boolean
}
```

There is no `disabled` convenience beyond the native attribute, and the guidance is to avoid
it: a disabled button gives the reader no way to find out why. Prefer an enabled button that
explains what is missing when pressed — see
[Cognitive accessibility](../accessibility/cognitive-accessibility.mdx).

## Content guidelines

Labels are verbs that name the outcome, in sentence case, without terminal punctuation. Two
or three words. The reader should be able to read the button alone and know what will happen.

Never *OK*, *Submit*, *Yes*, *No*, *Click here*, or *Learn more*. Each of them forces the
reader back up the page to reconstruct the question, and each of them is useless in a screen
reader's list of controls.

<DoDont>
  <DoDont.Do>
    **"Save reading"** · **"Book a repeat test"** · **"Delete this reading"** Each names its
    own outcome and survives being read out of context.
  </DoDont.Do>
  <DoDont.Dont>
    **"Submit"** · **"OK"** · **"Continue"** on a screen with three of them. A reader hearing
    *button, continue* three times has learnt nothing.
  </DoDont.Dont>
</DoDont>

<DoDont>
  <DoDont.Do>
    **One primary action per surface**, with everything else secondary or quiet.
  </DoDont.Do>
  <DoDont.Dont>
    **Three filled buttons of equal weight.** The hierarchy is the answer to *what should I do
    here?*, and three primaries answer it with a shrug.
  </DoDont.Dont>
</DoDont>

## Accessibility requirements

Requirements for the implementation, not results.

- **A real `button` element**, or an `a` when the action navigates. Never a `div` with a click
  handler: keyboard activation, Space and Return semantics, and the control's role all come
  free from the right element and must otherwise be rebuilt correctly, which nobody does.
- **The visible label is the accessible name.** Where a longer name is needed, it starts with
  the visible text, so voice-control users can say what they see.
- **The target is at least 44 by 44 points**, with at least 8 points of separation from
  neighbouring targets, even when the button looks smaller — WCAG 2.2 SC 2.5.8 is the floor,
  not the goal. See [Target size and motor](../accessibility/target-size-and-motor.mdx).
- **Focus is always visible**, meets the contrast floor against both the button and the page
  behind it, and is never removed. The focus ring is not decoration; it is the only way some
  people know where they are.
- **The busy state keeps the button in the accessibility tree**, announced as busy, with the
  label unchanged. Removing or replacing a pressed button loses the reader's place.
- **Disabled buttons are avoided.** Where one is unavoidable, the reason is available in text
  next to it, not only in a tooltip that requires hover.
- **Icons are decorative** and hidden from assistive technology; the label always carries the
  meaning.
- **At 200% text the label wraps rather than truncating**, and the button grows to fit.
  Truncated labels with an ellipsis are unreadable and unspeakable.
- **Under `prefers-reduced-motion`** the press feedback is an immediate state change rather
  than a scale animation, and nothing is lost.
- **Contrast is measured for every variant** against its surface, in both themes, for the
  label, the border and the focus ring — including the destructive variant, which is the one
  most often tuned for drama rather than legibility.
