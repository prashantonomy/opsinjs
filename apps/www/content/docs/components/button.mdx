Button is the reference page. It carries no clinical contract, which is exactly why
it was written first: it establishes the anatomy, the tone and the level of detail
every other component page follows, without the clinical material doing the work.

This documentation site also ships a Button of its own, at `components/ui/button.tsx`,
written by the shadcn CLI in the lyra style. It is docs chrome — square corners, dense,
extra-small type, and eight sizes of which four are icon-only — and it is **not** this
component and not a preview of it. Every `/view` route and every component preview on
this site renders under the product theme instead, which is squircle, system-ui and
generous. See [Lyra and the docs chrome](../theming/lyra-and-the-docs-chrome.mdx).

## When to use it

  use={[

  ]}
  avoid={[

    { case: "The control turns something on or off immediately, with no confirmation step.", instead: "switch" },
    { case: "The control chooses one of a few options rather than performing an action.", instead: "segmented-control" },
    { case: "The control is icon-only, in a toolbar or a header.", instead: "icon-button" },

  ]}

The first exclusion is the one that gets ignored and the one that costs most. A button
that navigates cannot be opened in a new tab, cannot be copied, does not appear in a
screen reader's list of links, and does not work when JavaScript has not loaded. If the
result is a new URL, it is a link, however it is styled — and this component gives you
no way to pretend otherwise: there is no `href`, no `as` and no `render` prop, so it can
only ever render a `button` element.

The parts are `data-slot` attributes, not exports. There is no `Button.Label` to import
and no way to render one without the others, which is what makes "the label cannot be
removed" a fact about the DOM rather than a request in prose. Style them from outside if
you need to; take them apart and you cannot.

`Button.Label` cannot be removed. There is no `iconOnly` prop, because every system that
shipped one ended up with unlabelled controls in production, and an icon-only control
needs a name supplied some other way and a different target treatment — which makes it a
different component.

`Button.Target` looks redundant inside this repository and is not. The product theme
floors every `button` element at `--opsin-target-minimum`, so here the span agrees with
the backstop rather than doing anything; its job is the project that ran
`shadcn add` and does not have that stylesheet. The floor is `2.75rem` rather than
`44px` in both places, because at 200% text the root font size genuinely doubles and a
rem floor doubles with the label.

Button does not override the native `type` attribute. Inside a `form` it submits, exactly
as a `button` element does, and a button that is not meant to submit needs
`type="button"` from the caller — the platform's default is left alone rather than
quietly reversed.

## Examples

### One primary per surface

The hierarchy is the answer to *what should I do here?*, and three filled buttons of
equal weight answer it with a shrug. Everything that is not the one action is secondary
or quiet. The row is spaced by `--opsin-target-separation`, because a component cannot
enforce its neighbours' spacing and the caller has to.

## Content guidelines

Labels are verbs that name the outcome, in sentence case, without terminal punctuation.
Two or three words. The reader should be able to read the button alone and know what will
happen.

Never *OK*, *Submit*, *Yes*, *No*, *Click here*, or *Learn more*. Each of them forces the
reader back up the page to reconstruct the question, and each of them is useless in a
screen reader's list of controls.

The destructive variant needs its label more than any other button in the system does.
opsinjs has no destructive colour, so *Delete* on its own is carried by a boundary weight
and nothing else; *Delete this reading* is carried by the words, which every reader gets.

## Accessibility

Some of this is checked by a gate on every commit. Most of it is argued. The two are
separated below, and the things nobody has measured are listed rather than left out —
that separation is what `alpha` promises.

**Checked, by `pnpm run check:a11y` on every commit:**

- **Every colour on this button is a role token.** The static rig fails the build on a
  hex literal, an `oklch()` call, a Tailwind palette colour or a numbered ramp step
  anywhere under `registry/`, so no variant can hold a value that dark mode and increased
  contrast will not follow.
- **No class that resolves only in the docs chrome.** This is the rule that makes the
  destructive question below unavoidable rather than optional: the roles a shadcn button
  reaches for are declared in `app/globals.css` and produce no CSS at all under the
  product theme, and the gate fails on them by name.
- **No type size in `px`.** Both sizes take a step from the eleven-step ramp, so the
  label scales with the reader's own text size instead of opting out of it. See
  [Dynamic type](../foundations/typography/dynamic-type.mdx).
- **No banned word, in copy or in an identifier.** The ban covers prop names and variable
  names as well as strings.

**Argued, and true of the implementation, but not measured:**

- **It is a real `button` element.** Base UI renders one natively, so Return and Space
  activation, the control's role and its form behaviour all come from the platform rather
  than from handlers somebody had to remember to write. There is no prop that changes the
  tag.
- **The visible label is the accessible name**, and the icon is `aria-hidden`. A longer
  name must start with the visible text so voice-control users can say what they see;
  nothing in the API removes the label, and a blank one raises a development warning.
- **Busy keeps the button in the accessibility tree.** It sets `aria-busy` and
  `aria-disabled` and blocks activation, but never the native `disabled` attribute — so
  the control keeps its tab stop and its name, and the reader keeps their place. Passing
  `busy` and `disabled` together raises a development warning, because the native
  attribute takes the control out of the tab order and the busy state it announces then
  reaches nobody.
- **The focus ring is drawn outside the box** with an outline and an offset, so it never
  changes layout and never gets clipped by an ancestor's overflow, and it is declared on
  the component as well as in the product theme so that it survives installation
  elsewhere. It is never removed.
- **At 200% text the label wraps and the button grows.** There is no fixed height and no
  `truncate`; the height floor is a rem, so it grows too. Checked by eye in both themes
  at 200%, not by a machine.
- **Nothing scales or fades.** The only motion in the component is the busy spinner, so
  `prefers-reduced-motion` changes nothing about pressing a button — the press
  acknowledgement is an immediate 1px shift with no transition, which is what that
  preference asks for anyway. The spinner is deliberately not stopped: a frozen spinner
  communicates nothing, and the label and `aria-busy` are already carrying the state for
  everybody.

**Not checked at all, and listed rather than omitted:**

- **Contrast, for every variant.** Label against fill, boundary against surface, and the
  focus ring against both the button and the page behind it, in both themes — including
  the destructive variant, which is the one most often tuned for drama rather than
  legibility. Nothing below is measured yet.
- **The 44 by 44 target, and the 8pt separation between adjacent targets.** The floor is
  asserted twice — by `Button.Target` and by the product theme's own backstop — and
  verified by neither until the nightly layout job runs, which needs a browser this
  repository deliberately does not install. Separation is the caller's, because a
  component cannot see its neighbours. See
  [Target size and motor](../accessibility/target-size-and-motor.mdx).
- **Whether `destructive` is distinguishable from `secondary` by anybody.** It differs by
  boundary weight and by fill, and by nothing else, and that has not been tested with a
  single reader.
- **Hover and press as specified.** [Interaction states](../foundations/interaction-states.mdx)
  defines a state as an OKLCH derivation of the role a component already uses. No state
  token is generated, so the values here are chosen rather than derived, and on the
  secondary, quiet and destructive variants press currently resolves to the same fill as
  hover.

Disabled buttons are avoided, and the native attribute is the only way to get one — there
is no convenience prop, on purpose. Where one is unavoidable, the reason belongs in text
beside the control and not in a tooltip that requires hover; a disabled control also
leaves the tab order, so a keyboard reader never reaches the explanation attached to it.
See [Cognitive accessibility](../accessibility/cognitive-accessibility.mdx).

## API reference

<PropsTable name="ButtonProps" />

The variant union is declared in the component file but is not exported. A registry file
ships exactly three public symbols — the props interface, the component and its zero-prop
demo — so a wrapper that needs to name the four values writes `ButtonProps["variant"]`
rather than importing a fourth. There is no `disabled` convenience prop either: the native
attribute is the whole of it.
