## The short version

Every page under Components is the same page. A page with code behind it has
seventeen sections in a fixed order, five of which it may leave out, and the
order is fixed whether or not a section appears.
`<PageTemplate kind="component" />` asserts the required sections exist and
**fails the build** when one is missing, so a page cannot rot into seventeen
headings with three sentences under each.

A `planned` page is ten sections long:
Status · Preview · Installation · When to use it · Clinical meaning (health
categories only) · Anatomy · Proposed API · Content guidelines · Accessibility ·
Related. Everything a specification cannot honestly report is **omitted, not left
empty**. An empty heading is a promise you have not kept; an absent heading is an
accurate description of a component that does not exist. No component sits at
`planned` today: all sixty are `shipped`, so every component page in the corpus
renders the longer outline.

The literal skeleton lives at `content/_templates/component.mdx` and is republished with
every other template on
[Documentation templates](../handbook/contributing/documentation-templates.mdx). Start
from it. Never start from a blank file, and never start from another component's page.
That is how a clinical contract gets copied onto a component it does not apply to.

## How it works

### The seventeen sections

Numbered in the order `SHIPPED_SECTIONS` in `lib/status.ts` gives them, which is
the order a page must present them in. A section marked optional may be left out
entirely; when it appears it appears in this position.

| # | Section | Written or generated | Required | What it is for |
| --- | --- | --- | --- | --- |
| 1 | Status | written from props | always | `<StubNotice>` naming the release phase, what has and has not been reviewed, and the safety questions still open. At `planned` it also carries the not-implemented marker |
| 2 | Preview | generated | always | `<ComponentPreview>` at a base and style, with theme, density and text-size switches |
| 3 | Installation | generated | always | `<ComponentInstall>` renders CLI and manual tabs built from the registry item, never typed by hand. The manual tab hosts `<ComponentSource>`, which resolves the id against the generated registry index and renders the component file's real bytes. That is the only place source appears on a page, and it is why no section owns it separately |
| 4 | Usage | written | always | The import line and the minimal JSX. Two code blocks, zero prose |
| 5 | When to use it | written | always | Two lists. Every entry in the *not* list names the component to use instead |
| 6 | Clinical meaning | written | health categories only | Required when `category` starts with `health-`, and forbidden when it does not |
| 7 | Anatomy | written + generated | always | Labelled parts over the render, plus the part hierarchy |
| 8 | Examples | written | always | One H3 per variation: the rule, then the demonstration |
| 9 | States | generated | optional | Interaction states and the five data states as one matrix |
| 10 | Content guidelines | written | always | What to write inside the component, with `<DoDont>` pairs |
| 11 | Motion | generated | optional | Which motion tokens it consumes and what each degrades to under reduced motion |
| 12 | Accessibility | written + generated | always | What has been checked and what has only been argued, labelled apart. Never delegated upstream |
| 13 | Data attributes | generated | optional | The state machine as a documented styling contract |
| 14 | CSS variables | generated | optional | Per selector, never a global dump |
| 15 | Tokens | generated | optional | Token, what it controls, what else uses it |
| 16 | API reference | generated | always | `<PropsTable>` from a named exported interface |
| 17 | Related | generated + written | always | Easily confused with, used by, governed by |

A `planned` page swaps section 16 for `## Proposed API`, the intended interface
written out as a specification and marked do-not-generate-against, and drops
sections 4, 8 and the five optional ones. The two API sections must never both be
present: a hand-written interface next to a generated one is an invitation to
trust the wrong one.

The five optional sections are the whole difference between the shortest and the
longest component page in the corpus. Write one where the answer has been worked
out and leave it out where it has not. A `## Motion` section saying motion has
not been specified teaches a reader nothing its absence did not already tell
them.

### What surrounds the sections

The H1 and the one-sentence definition under it are rendered by the docs route
from the page's `title` and `description`, so they are never typed as MDX. That
is the entire generated frame. There is no generated header strip and no
generated footer.

### Why the order is what it is

Installation is section 3, above every word of safety prose. That is deliberate and it was
argued about. A developer who came to copy an install command will scroll two screens and
leave whether or not the safety material is above it; putting the command first means they
find it, and it means the safety material sits where someone reading rather than skimming
will actually reach it. Burying the install command does not make anybody read the clinical
contract. It just makes the page feel hostile.

**When to use it** is section 5, because it is the section that prevents the most
expensive mistake. That mistake is reaching for
[AlertBanner](./alert-banner.mdx) when the situation calls for
[Callout](./callout.mdx). Every entry on the *not* side names an alternative. A prohibition
without a destination is not guidance; it is a dead end that the reader resolves by
ignoring you.

**Clinical meaning** is section 6 rather than an appendix because for a health component it
is the specification. What the component asserts about a person, what it must never be read
as, which colour axis it may use and who owns the thresholds are not decoration around the
API. They are constraints on it.

**Accessibility** is section 12 and it is mandatory at every status, including `planned`,
where it is written as the bar the implementation must clear rather than as results already
achieved. It is never delegated to a general accessibility page. A per-component keyboard
table that says "see the accessibility section" is how keyboard support goes missing.

### Where the research goes

There is no separate research heading. Why a component is designed the way it is
belongs in a `<ResearchNote>` inside the clinical or the accessibility material,
next to the claim it supports, with `evidence` declared every time. `cited` means
a real, checkable source; `opinion` means a considered judgement with no study
behind it. There is no third option, and an honest `opinion` is always better
than a plausible invention. Keeping the note beside its claim is what stops a
rationale section becoming the place arguments go to avoid being checked.

### What is generated

Half the table above says *generated*, and that is the rule that keeps these pages true.
Prop tables, token tables, data-attribute tables, CSS-variable tables, measured contrast
and the source of every example are produced by `scripts/*.mts` from the
registry and the token sources. Documentation contains **names**, not code and not
measured numbers. CI regenerates everything and fails on a diff, so a page cannot drift
away from the thing it documents without somebody noticing.

## Do this

- **Fill in the template.** Copy `content/_templates/component.mdx`, change the
  frontmatter, and write the sections it leaves for you.
- **Write the definition for the patient, not the engineer.** The one-sentence
  `description` is the hardest line on the page and it is the one that ends up in search
  results, in `llms.txt` and under the H1. *One test result with the number, where it sits
  against its reference range and what to do next* is a definition. *A card component for
  results* is a restatement of the name.
- **Name an alternative in every prohibition.** `avoid` entries take an `instead`, and the
  value is a catalogue id, so it is checked.
- **Declare `governedBy` for every `health-*` component**, and make sure the doctrine page
  lists the component back. `assert-ia` checks both directions; a rule that governs nothing
  is a rule nobody has to follow.
- **Take aliases from the catalogue.** `registry/catalogue.ts` owns the alias namespace.
  Add a synonym there, then reference it here.
- **Say what the component refuses to do.** A specification that only describes success is
  half a specification. What does it render when the reference range is unknown? When the
  reading is thirty days old? When the value is implausible? Those answers belong on the
  page before the code exists, because they are the answers that get skipped once it does.
- **Write a Related bullet as a sentence.** Section 17 takes the linked page as its
  subject and a verb from the closed table, so it reads
  `- [Button](./button.mdx) is the reference page.` rather than a link with a gloss
  hung off it. The link text stays the page title, the gloss keeps its wording and its
  lower-case first letter, the item ends in a full stop, and no colon stands between
  the link and its gloss.
  [Documentation templates](../handbook/contributing/documentation-templates.mdx) has
  the verb table in full, and the same shape governs a `- **Bold term**` bullet.

## Not this

- **Do not leave a heading empty**, and do not write *TODO: fill this in*. Omit the
  section, or if the gap is real and must be tracked, use `<Todo>`. It registers the gap
  in the build's coverage report, so incompleteness is measured rather than hidden.
- **Do not paste code into MDX.** `<ComponentSource>` and `<ComponentInstall>` resolve a
  name against the registry and render the real thing. A hand-copied snippet is wrong the
  first time the source changes and nothing tells you.
- **Do not state a measured number you did not generate.** No contrast
  ratios, no percentages of users. `<NoDataYet>` is the honest rendering of a table whose
  source is empty, and it names the script that will fill it.
- **Do not invent a citation.** Not a study, not a statistic, not a DOI, not a date. Mark
  it `evidence: opinion` and move on. See
  [Evidence and references](../health/evidence-and-references.mdx).
- **Do not add a section this contract does not have.** `assert-ia` compares your headings
  against the outline for the page's `kind` and fails on an unexpected one as well as on a
  missing one. If a page genuinely needs something the contract lacks, change the contract.
  Then every page gets it.
- **Do not give a non-health component a clinical meaning.** [Card](./card.mdx) is a box.
  The moment a box carries a verdict about somebody's blood pressure, the verdict is
  invisible to review.

## Gotchas

**Links are relative.** Write `[Two colour axes](../health/two-colour-axes.mdx)`. fumadocs
resolves it through `createRelativeLink`. An absolute site link is banned, with no exception
left, because the day a locale segment appears they all break at once and nothing tells you
which. The corpus is rooted, so an absolute link is also shorter than it looks: it is
`/health/two-colour-axes`, one rename away from being wrong everywhere.

**The MDX vocabulary is closed.** Only the tags listed in this contract exist. Content
authors use them and never define one; an unknown JSX tag fails the build rather than
rendering as an unknown HTML element that silently swallows its children.

**Component ids are kebab-case in every path, frontmatter field and prop; PascalCase only
in prose.** `range-bar` in `usedIn`, `RangeBar` in a sentence.

**British spelling in prose, American in code.** `colour`, `behaviour`, `visualisation` in
what a reader reads; `color`, `ColorScale`, `--color-*` wherever a language or a browser
forces it. The seam is real and it is the only place these two live together.

**`aliases` are globally unique**, not unique per page. If two pages claim `gauge`, the
build fails, and it fails on the second page rather than the wrong one. Check the catalogue
before you add one.

**A `planned` page is a specification, not a placeholder.** If you cannot answer what the
component asserts, what it refuses, how it composes and what it must never be read as, the
component is not ready for a page. It belongs in a proposal with a one-line reason, where
an honest *not yet* costs nothing.
