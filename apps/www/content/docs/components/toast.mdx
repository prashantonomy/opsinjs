Toast is a brief, self-dismissing confirmation of the reader's own action. "Saved" is the whole of it: a note that the action they took has landed, shown for a few seconds at the edge of the screen and then gone, drawn as quiet neutral chrome rather than as a status.

The design decision that shapes the whole component, and the reason it was left unbuilt for so long, is that a message which removes itself is the wrong shape for anything about someone's health. The reader who most needs a piece of information is the one most likely to miss it, so a Toast carries a confirmation of an action the reader themselves took and never a reading, a result, an alert, or anything a reader must not miss. What must be seen goes on a surface that stays.

The toast system is built on Base UI's Toast provider, viewport and manager, which is where the queue, the polite live region, the F6 shortcut and the dialog role on each toast come from, so installing it pulls in `@base-ui/react`. The close control carries the lucide `X` glyph, so it also pulls in `lucide-react`.

## Usage

```tsx
import { Toast } from "@/components/ui/toast"
import { Toast as ToastManager } from "@base-ui/react/toast"
```

```tsx
function SaveButton() {
  const manager = ToastManager.useToastManager()
  return (
    <button onClick={() => manager.add({ title: "Saved" })}>Save note</button>
  )
}

function Screen() {
  return (
    <Toast position="bottom-right">
      <SaveButton />
    </Toast>
  )
}
```

## When to use it

  use={[

    "Offering a brief, optional way to reverse the action they took, such as an Undo on a delete, that the reader may act on within a few seconds or ignore.",

    { case: "The message needs the reader's attention now and stays until they have dealt with it, such as a warning about a connection or a value.", instead: "alert-banner" },
    { case: "The information is a standing explanation, a note or a caveat that belongs on the surface for as long as the reader is reading it.", instead: "callout" },

The exclusion that matters is the first, and it is the reason this component exists on such a tight leash. A toast is defined by the fact that it leaves on its own, and that single property makes it safe for a confirmation and unsafe for anything else. A confirmation the reader misses costs nothing, because the action still happened and the state is still true on the surface behind the toast. A reading the reader misses is a reading they never saw at all, so a number, a result or a level of urgency belongs on a surface that stays, which is an [AlertBanner](./alert-banner.mdx) when it needs attention now and a [Callout](./callout.mdx) when it is a standing note.

The second and third exclusions are the same rule stated for time rather than content. If the message has to stay until the reader deals with it, it is not transient and a toast is the wrong container: the self-dismiss that makes a toast a toast is exactly what would let the message slip away before it was handled. Reach for a surface that persists, and let the toast keep its one honest job of saying "done" and then leaving.

The parts are identified by `data-slot` and are styleable from outside; none of them is an export, and a toast is never assembled by hand. A toast is pushed imperatively instead, through `useToastManager().add()`, because the decision to show one is made in an event handler after an action resolves rather than in the render tree. The title, description and action are each drawn only when the pushed toast carries one, so an empty element is never announced, and the close control is always present so every toast has a way out that does not depend on the timer.

There is deliberately no colour prop and no `severity`. A toast is a neutral acknowledgement on neither axis, and a status a reader must act on does not belong on a surface that erases itself, so the moment a confirmation wants a colour it wants a different component.

## Content guidelines

Keep a toast to the fact of the action, in the past tense and a word or two: "Saved", "Reminder set", "Note removed". A toast is read in the corner of the eye while the reader is doing something else, so it names what happened and then stops, and the detail that does not fit belongs on the surface behind it rather than in a line nobody has time to read before it leaves. Never write a clinical word, a reading or a level of urgency into a toast, because a surface that removes itself cannot carry anything the reader must not miss.

Give the action a verb that says what it does, "Undo" or "View", and make it optional in the true sense: the reader loses nothing by letting the toast leave without pressing it. If the reader has to act, a toast is the wrong container, because the timer will take the choice away.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. Accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The toast draws only the neutral chrome roles and the card material, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size and an opsinjs radius.** The title, description, action and close all take one of the eleven semantic type steps, and the surface rounds at `rounded-opsin-lg`, so a reader who has turned their text size up gets a larger toast rather than a pinned one.

**Argued, and true of the implementation, but not yet measured:**

- **The viewport is a polite live region with a name.** Base UI renders it as `role="region"` with `aria-live="polite"` and the accessible name from `label`, and it is reachable with F6, so a screen-reader user is told a confirmation appeared without it stealing focus. Whether the polite register and the default five-second life read well together has been reasoned about rather than heard.
- **Each toast is a labelled dialog.** The close control and any action are ordinary focusable controls inside it, Tab moves between them, and Escape dismisses the focused toast, so a reader is never trapped waiting on the timer.
- **The interactive controls clear the target floor.** The close control floors its hit area at `--opsin-target-minimum` on both axes and the action floors its height, both in rem, so a 44px pressable region survives and grows with the reader's text size rather than pinning at a device pixel.
- **The enter and leave transition respects `prefers-reduced-motion`.** Under the query the travel is pinned to its resting value and only the opacity crossfade is kept, so the toast still announces itself by appearing rather than arriving from nowhere.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the title and description against the card material, the close control's two states, and the overlay shadow that lifts the surface. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the toast draws under `forced-colors: active`, where the shadow is dropped and the hairline is replaced by the platform's own pair. None of this has been put in front of a machine or a high contrast user, and the timing has not been checked against a reader who reads slowly.

## API reference

<PropsTable name="ToastProps" />

`children` is the screen the toast confirms an action on, and it mounts inside the provider so a child can call `useToastManager().add()`. `position` and `limit` place and cap the stack, and `timeout` sets how long a toast stays: passing `0` stops it dismissing itself, which turns a transient confirmation into a standing surface and raises a development warning, because a message that must persist is an AlertBanner or a Callout rather than a toast. `label` and `closeLabel` are the two reader-facing words this component owns, taken as props so they can be translated; both default to English, which is the residual gap listed above rather than described as solved.

## Related

<RelatedComponents name="toast" />

**Easily confused with**

- [AlertBanner](./alert-banner.mdx) is the component for a message that needs the reader's attention now and stays until they have dealt with it. A toast leaves on its own, so anything a reader must not miss belongs on the banner, which persists and can carry a status.
- [Callout](./callout.mdx) sets a standing note, tip or caveat apart on the surface for as long as the reader is reading it. A toast is the opposite in time: it acknowledges an action and then removes itself.

**Used by**

- No pattern, recipe or screen composes it yet. It is a feedback primitive a product wraps around its own screens so an action taken anywhere inside can confirm itself.
