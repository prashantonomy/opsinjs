Combobox is a text input that filters a list as the reader types, then lets them choose one match from what is left. Its home is a single choice out of a list too long to scroll comfortably, a country, a city or a medication name being the shape it was built for, where typing a few letters is faster than paging through everything.

The design decision that shapes the whole component is that opsinjs ships no vocabulary. The hard part of a searchable list in a health product is never the widget, it is the list: which medicines, which conditions, which units, spelled which way, and kept current against which source. The component takes the items through the `items` prop and filters and renders exactly what the product hands it, because a list that is wrong is a clinical mistake and the presentation layer has no right to own it.

## Preview

A field over a list long enough that typing beats scrolling, with one item chosen at the start. The thing worth checking is that the list narrows as you type and the chosen item is marked without a colour doing the work, so type a letter and read the matches in greyscale: the highlight is a neutral surface, the tick is a lucide Check, and underneath both the carrier is `aria-selected` rather than any pixel at all.

<ComponentInstall

The control is built on Base UI's Combobox primitive, which is where the single tab stop, the default contains filter, the floating popup and the WAI-ARIA combobox keyboard come from, so installing it pulls in `@base-ui/react`. The chevron on the trigger and the tick on the chosen match are lucide icons, so it pulls in `lucide-react` as well.

## Usage

```tsx
import { Combobox } from "@/components/ui/combobox"
```

```tsx
<Combobox
  label="Medication"
  placeholder="Search medications"
  value={medication}
  onValueChange={setMedication}
  items={[
    { value: "amoxicillin", label: "Amoxicillin" },
    { value: "ibuprofen", label: "Ibuprofen" },
    { value: "paracetamol", label: "Paracetamol" },
  ]}
/>
```

## When to use it

<WhenToUse
  use={[
    "Choosing one item from a list long enough that typing a few letters is faster than scrolling it, such as a city, a country or a product-owned medication name.",

The exclusion that matters most is not in the table, because it points at no component. A combobox must never carry a clinical vocabulary that opsinjs itself ships. The list of medicines, conditions or units a reader searches is the product's to own, source and keep current, so it arrives through `items` and the component filters whatever it is handed. If you find yourself reaching for a built-in list of drug names, the list is the bug, and it belongs in the product rather than in this component.

The two exclusions in the table are both about the shape of the list. A [Select](./select.mdx) is the honest form for a short fixed set that fits in a closed menu, because filtering a handful of options is effort with no reward. A [RadioGroup](./radio-group.mdx) is the form for a small set worth showing all at once, because a reader comparing two to five options should see them rather than type toward them. A combobox earns its place only once the list grows past what either of those can hold comfortably.

## Content guidelines

Name the field for the thing being chosen, not for the act of typing: `label` reads "Medication" or "City", not "Search" or "Type here", because a screen-reader user hears the name before the role and needs to know what the field is for. Keep the placeholder a short instruction such as "Search medications", and let the item labels be the plain names the reader would type, spelled the way the product's own list spells them so the contains filter matches what a reader expects.

Write the empty message to help rather than to scold. "No matches. Check the spelling." tells the reader what to try next; a bare "No results" leaves them stuck. Never let the empty message, or any placeholder, imply that opsinjs knows the vocabulary. The list is the product's, so the words that describe it are the product's too, and the component only shows what it is handed.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. Accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The control draws only the neutral chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size.** The input, the items and the empty line are all the semantic type steps rather than pixel sizes, so a reader who has turned their text size up gets a larger control instead of a pinned one.

**Argued, and true of the implementation, but not yet measured:**

- **The control is the WAI-ARIA combobox pattern.** Base UI renders `role="combobox"` on the input, `role="listbox"` on the popup and `role="option"` with `aria-selected` on each match, and the input is the single tab stop with the Arrow keys moving a highlight through the popup. This is the primitive's contract rather than a bespoke one, but it has not been heard in a real screen reader.
- **The chosen match and the active highlight are never colour alone.** The selection is a lucide Check under `aria-selected`, and the highlight is a neutral surface under `data-highlighted`, so both survive greyscale. This is argued from the roles rather than measured against a colour-vision audit.
- **The input and the trigger floor a 44pt target and carry their own focus ring.** Each is sized from `--opsin-target-minimum` in rem, so the pressable region grows with the reader's text size, and the ring lives in the component's own classes so a project installed without the product stylesheet keeps it.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the field hairline against the background, the raised popup against its ground, the highlighted match's surface, and the muted ink of the empty line. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the control draws under `forced-colors: active`, where the border, the fill, the shadow and the highlight are all replaced by the platform's own pair. None of this has been put in front of a machine or a high contrast user.

## API reference

<PropsTable name="ComboboxProps" />

`items`, `value` and `onValueChange` make this a controlled component with no internal selection state: the caller supplies the list, stores the chosen value, and passes it back, and a `value` that matches no item renders with nothing chosen and raises a development warning. `items` is where the whole doctrine of this component lives, because opsinjs ships no list of its own and filters only what the product hands it. `label` is required because a combobox with no accessible name is a defect the type system cannot otherwise prevent, and `emptyMessage` is the one line a reader sees when their search finds nothing, so it is worth writing to help.

## Related

<RelatedComponents name="combobox" />

**Easily confused with**

- [Select](./select.mdx) opens a closed menu of a fixed list without a text filter. It is the form for a short set where typing to narrow buys nothing; a combobox earns its place once the list grows past what a menu holds comfortably.
- [RadioGroup](./radio-group.mdx) shows a small set of options all at once for a reader to compare. A combobox hides the list behind a search, so it is the wrong reach when the whole point is seeing the two to five choices side by side.
- [Field](./field.mdx) is the labelled wrapper that gives any input its visible label, description and error. A combobox is the input that goes inside such a field; it names itself for assistive technology through `label` but draws no visible label of its own.

**Used by**

- No pattern, recipe or screen composes it yet. It is a neutral primitive a product wires to its own vocabulary, so the list it searches and the surface it sits on are the product's to bring rather than something the corpus ships today.
