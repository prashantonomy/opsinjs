IconButton is the shipped Button with its label taken off the screen and made
mandatory. It composes [Button](./button.mdx) rather than rebuilding it, so the
real button element, the 44pt target floor, the focus ring and the four variants
all come from one place, and the only thing this component adds is a square shape
and a rule: an icon-only control must carry a name, and this one cannot ship
without it.

The rule is the whole reason it exists as its own component. Every design system
that offered an icon-only mode on its button ended up with unnamed controls in
production, announced as "button" and nothing else and invisible to voice
control. Here the name is a required prop, a missing one raises a development
warning, and there is no way to render the control with the label removed.

## Preview

Three of the four variants as icon-only controls, each carrying an accessible name you
cannot see but a screen reader and a voice-control user can. The thing worth
checking is that each control reads as pressable without a word inside it, and
that at the 44pt square floor the glyph sits centred rather than crowded, because
an icon lost in padding is the first sign the square shape did not take.

The first exclusion is the one that matters, and it is the one products ignore.
An icon is a guess the reader has to make, and a short verb is not. So the
default control is a labelled [Button](./button.mdx), and an icon button earns
its place only where a word genuinely will not fit: a toolbar of six controls, a
header with a single close cross, a table row repeated forty times. Everywhere
else, the space you are saving is smaller than the meaning you are spending, and
the labelled button is the honest choice.

Quiet is the variant that tempts most and reads least here. With no fill and no
boundary, a quiet icon button is a bare glyph, and a bare glyph is only a control
if the reader already knows it is one. Keep quiet for a toolbar or a header where
the surrounding chrome says plainly that these are controls, and reach for
`secondary`, which keeps a boundary, anywhere a reader might meet the glyph cold.

The parts are `data-slot` attributes, not exports. There is no `IconButton.Name`
to import and no prop that removes it, which is what makes "the name cannot be
taken off" a fact about the DOM rather than a plea in prose.

The root slot sitting on a wrapper rather than on the button is deliberate and
worth knowing. IconButton composes the shipped Button, which pins its own
`data-slot="button"` after it spreads the caller's props, so the pressable
element cannot carry `data-slot="icon-button"`. Rather than rebuild Button to
reclaim the slot, the component wraps it in a span that carries the slot and
nothing else. Style the button through `data-slot="button"` or through
`className`; the wrapper is identity, not a styling hook.

**The name is set two ways on purpose.** `aria-label` on the button is the
accessible name a browser computes, and the visually hidden `IconButton.Name`
node is a fallback: it survives a translation pipeline that drops the attribute,
and it keeps the name in the DOM as real text for tools that read content. Both
carry the same string, so a screen reader announces the label once, from the
attribute, and never twice.

## Examples

### A toolbar of icon buttons

The case the component is for. A header row where each control is a glyph a
reader of this kind of surface already knows, so the words would be noise rather
than help. Each button still carries a full accessible name, distinct from its
neighbours, because a toolbar of icon buttons is precisely where an unnamed one
disappears. The labels name fictional actions, so nothing here reads as a control
over somebody's own data.

### Icon buttons in a list row

Repeated row actions are the other place an icon button earns its keep: a labelled
Edit and Remove on every row would crowd the reading out, and the glyphs shrink
them to the margin. Each name carries its row's context, so a voice-control user
saying "edit the morning example reading" reaches one control rather than every
Edit at once, which is the discipline an icon button in a list demands.

## Content guidelines

The label is the whole of the message for a reader who does not see the glyph, so
it does the work the missing word would have done. Name the action and its
object, "Close the reading details" rather than "Close", in sentence case and
without terminal punctuation, so it survives being read out of context and a
voice-control user can say what they mean.

Choose a glyph the audience already knows, and let the glyph and the name agree.
A magnifier means search, a cross means close, a plus means add, and a reader who
meets one of those spends no guess on it. A novel or clever glyph spends a guess
the reader may not have, and when the guess is wrong the accessible name is the
only thing left carrying the action, which is a name they cannot see.

## Accessibility

IconButton is a real `button` element, because it composes one: Return and Space
activation, the control's role, and the tab stop all come from the platform
through [Button](./button.mdx) rather than from handlers somebody had to remember
to write. There is no prop that changes the tag.

The accessible name is the point of the component. It is set as `aria-label` on
the button and, as a fallback that survives a stripped attribute, as a visually
hidden text node inside it, so a screen-reader user hears the label rather than
"button" and a voice-control user can say it to target the control. A missing or
whitespace-only `label` raises a development warning, because it is the exact
failure the component exists to prevent and the type system alone cannot catch a
`label` that is present but empty. The glyph is `aria-hidden`, so it is never
announced as a second, pictorial name.

The target is a 44pt square. Button floors both axes at `--opsin-target-minimum`
already, and this component keeps the width equal to the height and removes the
horizontal padding, so the pressable region is square rather than a wide box with
a glyph adrift in it. The floor is a rem, so it grows with the reader's text size
rather than pinning at a device pixel. Separation between adjacent icon buttons is
the caller's, because a control cannot see its neighbours, and a toolbar of them
owes each control `--opsin-target-separation` so two glyphs set close together do
not share a hit area.

What is not yet checked is listed rather than left out, and it matches the open
questions above. No contrast pair has been measured for the glyph against any
variant's fill or for the focus ring, and IconButton inherits Button's neutral
scope and Button's own unmeasured pairs with it. Nobody has listened to the
control in a screen reader, so whether the doubled name reads as one name or two
is argued from how browsers compute it rather than heard. Forced colours and
`prefers-contrast: more` are unhandled, inherited from Button, and a quiet icon
button that leans on ink alone is the most exposed of the variants there.

## API reference

<PropsTable name="IconButtonProps" />

`icon` and `label` are both required, and that is the shape of the whole
component: a glyph a reader sees and a name they do not, neither optional. The
surface stops there on purpose. `variant` and `size` mirror
[Button](./button.mdx) so the two controls stay in step, and `variant` defaults
to `secondary` rather than `quiet` because a bordered control is easier to
recognise as one when there is no word inside it. `onClick`, `disabled` and
`className` are forwarded to the composed button unchanged.

There is no `busy`, no `busyLabel`, no `fullWidth`, no `iconPosition` and no
`type`. An icon-only control has no label to hold steady while it works, so a busy
state would hide both the glyph and the name; reach for a labelled Button where a
busy state matters. **IconButton takes neither a category nor a status, and its
`className` and `style` must not resolve either axis:** it makes no clinical
statement, so a fill or a boundary drawn from `--opsin-status-*` or
`--opsin-category-*` would put a clinical vocabulary on a control that has none.

## Related

<RelatedComponents name="icon-button" />

**Easily confused with**

- [Button](./button.mdx) is the labelled control this one defers to, and the
  confusion that costs most: an icon button saves space, a labelled button saves
  the reader a guess, and the guess is usually worth more than the space.
- [Switch](./switch.mdx) turns something on or off, where a glyph reads as a state
  to interpret rather than an action to take. An icon button acts; it does not
  hold a setting.
- [Tooltip](./tooltip.mdx) is reached for to reveal an icon's meaning on hover, but
  a tooltip is a supplement to a name and never the name itself, and there is no
  hover on a phone.

**Used by**

- No pattern, recipe or screen composes it yet. It was built for dense toolbars,
  card headers and repeated row actions, and placing it on one of those surfaces
  is a product's to make rather than something the corpus ships today.
