RadioGroup is a vertical list of labelled options where exactly one is chosen at a time. Each
option sits on its own row with a circle, a label and an optional line of helper text, so the
reader runs their eye down the list before picking one. It is the tall, readable form of a
single choice, and it is the control to reach for when the options need room to be read rather
than a tight row that reads at a glance.

The design decision that shapes the whole component is that it is one tab stop. A reader
arrowing down a list of options expects Tab to pass the list, not to stop on each option in it,
so the control is a radio group: the group takes the single tab stop, and the Arrow keys move a
roving focus between the options inside it. It is built on Base UI's RadioGroup on its Composite
primitive, which is where that single tab stop, the roving focus and the Arrow keys come from.

## Preview

A three-option list with one option chosen. The thing worth checking is whether the options

in greyscale: the selection is carried by the ring lifting to the primary ink and by the filled
dot inside the circle, and underneath both by `aria-checked` rather than by any hue at all.

installing it pulls in `@base-ui/react`. It composes no other opsinjs component and renders no
icon.

  ]}

The first exclusion is the one worth stating plainly, because RadioGroup and
[SegmentedControl](./segmented-control.mdx) are the same single choice built on the same Base UI
primitive, and the difference is shape rather than semantics. Reach for a segmented control when
the options are a tight set of siblings that belong on one line and switch a parameter of a view
that stays on the surface. Reach for this vertical list when the options need room, when an
option carries a description, or when the reader is picking a settled choice rather than toggling
a window. If the options fit on one line and read at a glance, it is a segmented control; if they
want a stacked list the reader runs their eye down, it is this.

The second exclusion is the honest limit of the form. A radio group lays every option out at
once, so past about seven options the list stops being something the reader takes in at a glance
and becomes a column they have to scroll. There a [Field](./field.mdx) with a select, which
collapses the options into one control and opens them on demand, is the form that still works,
and reaching for a radio group instead produces a wall of rows nobody scans.

The parts above are identified by `data-slot` and are styleable from outside; none of them is an
export, and there is no way to render an option without the group. Each Radio also renders a
visually hidden `<input type="radio">` beside its span, which Base UI uses to carry a form value.
This control passes no `name`, so that input submits nothing; it is out of the tab order, so it
changes nothing a reader meets, and it is named here rather than left for someone to find in the
DOM.

The description sits inside the option row rather than beside it, so a screen reader reads it as
part of the option's name. That is the intended trade: the helper line is genuinely part of what
the option means, so it is read with the option rather than as a separate note the reader has to
go looking for.

## Content guidelines

Keep the labels short, parallel and in sentence case, and name the value each option sets rather
than an instruction to the reader. Order the options the way the reader thinks about them rather
than the way the data is stored: a cadence that runs from most frequent to least is a list the
reader can scan, and reversing it to match a database column is the list nobody reads. Do not
change a label's wording between screens for the same option, because a reader who learnt that
this choice offers "Weekdays only" should not meet "Mon to Fri" meaning the same option elsewhere.

Use a description only when the label cannot stand alone. A helper line that repeats the label in
more words is noise, and a helper line under every option when only one of them needs it makes the
list heavier than it has to be. When a description is there, keep it to a phrase: it is read as
part of the option, so a paragraph turns one option into a speech.

<DoDont>
  <DoDont.Do>
    **"Standard" · "Quiet" · "None"** Three parallel options, each a short word, ordered from most

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest
is argued and labelled as such. Accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a
disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The control draws only the neutral chrome
  roles and the neutral primary ink, so it carries no `data-status`, reads no clinical vocabulary,
  and cannot mix the two axes. The gate reads every element and would fail the build on a colour
  drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size.** The labels are the `body` and `footnote` semantic steps and the circle and
  the dot are sized in `em`, so a reader who has turned their text size up gets a larger control
  rather than a pinned one.

**Argued, and true of the implementation, but not yet measured:**

- **It is one tab stop with a roving focus.** Base UI's RadioGroup renders `role="radiogroup"` on
  its Composite primitive, each option is a Radio rendering `role="radio"` with `aria-checked`,
  and selection follows focus, which is the WAI-ARIA radio group pattern rather than a bespoke one.
  The single tab stop is the contract this control keeps, so a keyboard user meets the whole list
  as one stop rather than one stop per option.
- **The choice has a visible, wired name.** `label` is required and is rendered as a legend above
  the list and wired to the radiogroup with `aria-labelledby`, so a screen-reader user hears the
  name of the choice before its options. A missing or empty `label` raises a development warning
  rather than rendering an unnamed group.
- **The selected state is carried three ways.** `aria-checked` for assistive technology, the ring
  lifting to the primary ink for greyscale, and the filled dot for a sighted reader, so no single
  carrier stands alone. A disabled option drops to the measured muted ink rather than being faded
  with opacity, so it stays readable while reading as unavailable, and the Arrow keys skip it.
- **Each option floors its target.** Every option row floors its hit area at
  `--opsin-target-minimum` in rem on the vertical axis, so a 44pt pressable region survives and
  grows with the reader's text size rather than pinning at a device pixel. The focus ring is
  carried in the row's own class list rather than left to the product stylesheet, so a project
  installed without that stylesheet does not lose it.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the primary ring and dot against the background, the muted ink of a
  description against its ground, and the disabled ink of a skipped option.
  `scripts/check-contrast.mts` has not been run for this component, which is why the report below
  is empty rather than reassuring.
- What the control draws under `forced-colors: active`, where the ring and the dot are both
  replaced by the platform's own pair. None of this has been put in front of a machine or a high
  contrast user, and nobody has listened to the control in a screen reader.

## API reference

<PropsTable name="RadioGroupProps" />

`value` and `onValueChange` make this a controlled component with no internal selection state: the
caller stores the chosen value and passes it back, and a `value` that matches no option renders the
list with nothing chosen and raises a development warning. `label` is required because a radiogroup
with no accessible name is a defect the type system cannot otherwise prevent, and it is a visible
legend rather than only an `aria-label`, so the name is on the screen as well as in the
accessibility tree. Each `options` entry is a value, a visible label, an optional `description`
line and an optional `disabled` flag, and a disabled option stays in the list, drawn in the muted
ink and skipped by the Arrow keys, rather than being removed.

## Related

<RelatedComponents name="radio-group" />

**Easily confused with**

- [SegmentedControl](./segmented-control.mdx) is the same single choice built on the same Base UI
  primitive, drawn as a compact single row. Reach for it when the options are a tight set of
  siblings on one line that switch a parameter of a view; reach for this vertical list when the
  options need room or carry a description.
- [Select](./select.mdx) collapses the options into one control that opens on demand, which is the
  form for a choice too large or too wordy to lay out in full. Once the options pass about seven, or
  the labels grow long, a select reads more calmly than a wall of rows.
- [Field](./field.mdx) wraps a single input with its label, hint and validation message. A radio
  group inside a form is composed with a field rather than standing on its own, so the choice gets
  the same label and error wiring as every other control on the form.

**Used by**

- No pattern, recipe or screen composes it yet. It is a single-choice primitive that a product
  drops into its own settings screens and forms.
