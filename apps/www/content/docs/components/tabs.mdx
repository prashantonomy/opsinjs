Tabs switches between distinct panels of content that occupy the same space, showing one panel at a time and letting the reader pick which through a row of tabs. Its home is a screen where two or three bodies of content compete for one region and only one is worth showing at once, an "Overview" and a "History" of the same subject being the case it was built for.

The design decision that shapes the whole component, and the one that keeps it apart from [SegmentedControl](./segmented-control.mdx), is what choosing a tab does. A segmented control sets a parameter of one view that stays on the surface. Tabs swap the content: choosing a tab replaces the panel underneath with a different panel that has its own material. The two controls look alike and behave differently, so the question to ask before reaching for either is whether the choice changes a setting of what stays on screen, which is a segmented control, or replaces what is on screen, which is this.

## Preview

The control is built on Base UI's Tabs primitive, which is where the single tab stop, the roving focus, the Arrow keys, Home and End, and the panel association come from, so installing it pulls in `@base-ui/react`. It composes no other opsinjs component and renders no icon.

## Usage

```tsx
import { Tabs } from "@/components/ui/tabs"
```

```tsx
<Tabs
  label="Reading detail"
  value={panel}
  onValueChange={setPanel}
  items={[
    { value: "overview", label: "Overview", panel: <Overview /> },
    { value: "history", label: "History", panel: <History /> },
    { value: "notes", label: "Notes", panel: <Notes /> },
  ]}
/>
```

## When to use it

<WhenToUse
  use={[

    { case: "The choice is a small set of exclusive options taken as a form input, where the answer is a value the reader submits rather than a panel they read.", instead: "radio-group" },
    { case: "The panels are steps in a sequence the reader works through in order, where progress and a next action matter more than free movement between them.", instead: "stepper" },

The exclusion that matters is the first, and it is a question about what the choice does. Tabs replace the panel; a [SegmentedControl](./segmented-control.mdx) adjusts a view that stays put. If choosing an option keeps the reader looking at the same thing and changes one setting of it, it is a segmented control, and the keyboard contract differs to match: a segmented control is a radiogroup where selection follows focus, and Tabs is a tablist where the reader arrows to a tab and then commits with Enter or Space. Reaching for Tabs to switch a chart's window gives the reader a panel swap where they expected a redraw.

The second and third exclusions keep Tabs from standing in for an input or a flow. A small set of exclusive options taken as a form answer is a [RadioGroup](./radio-group.mdx), because the reader is choosing a value to submit rather than a panel to read. A set of panels worked through in order, where the point is progress and a next action, is a [Stepper](./stepper.mdx), because Tabs offer free movement between panels and say nothing about sequence.

The parts above are identified by `data-slot` and are styleable from outside; none of them is an export, and there is no way to render a tab without the list or a panel without its tab, because the data-driven `items` prop keeps the tab, its label and its panel together as one object. The dotted names in the tree are the Base UI parts this wrapper composes, not symbols a consumer imports.

There is deliberately no icon slot on a tab and no close affordance. A tab names a panel and switches to it; an icon beside a short label competes with the word, and a closable tab is a different pattern with its own state to own, which this component does not grow into.

## Content guidelines

Keep the tab labels short, parallel and in sentence case: one or two words each, the same part of speech, so the row reads as one set of siblings. Name the panel each tab reveals, "History" rather than "Show history", and let the labels carry no terminal punctuation. Order the tabs the way the reader thinks about the subject rather than the way the data is stored, and put the panel a reader wants first at the start of the row so it is the one shown by default.

Do not use tabs to hide content a reader needs to see together. Tabs are for views that are genuinely alternatives, where reading one does not require reading another at the same time, so a comparison that only makes sense side by side belongs on one panel rather than split across two. Do not change a label's wording between screens for the same panel, because a reader who learnt that this card offers "Notes" should not meet "Comments" meaning the same panel elsewhere.

## Accessibility

Some of this is enforced by a gate on every pull request and every push to `main`, and the rest is argued and labelled as such. At `alpha`, accessibility is claimed only where it has been checked, with the gaps listed rather than left out. Nothing here has been through a review with a disabled user.

**Checked, by `pnpm run check:a11y`:**

- **No status colour, no colour literal, no ramp step.** The control draws only the neutral chrome roles, so it carries no `data-status`, reads no clinical vocabulary, and cannot mix the two axes. The gate reads every element and would fail the build on a colour drawn from either axis or on a raw colour value, and there is neither here.
- **No px type size, and a 44pt target floor.** Each tab's text is the `headline` semantic step rather than a pixel size, and each tab floors its target at `--opsin-target-minimum` in rem on the vertical axis, so a pressable region survives and grows with the reader's text size rather than pinning at a device pixel.

**Argued, and true of the implementation, but not yet measured:**

- **The tabs pattern is Base UI's, not a bespoke one.** Base UI's Tabs renders `role="tablist"`, each tab a `role="tab"` with `aria-selected` that `aria-controls` its `role="tabpanel"`, the list is one tab stop with a roving focus moved by the Arrow keys, and the panel is the next tab stop. Activation is manual: the Arrow keys move the highlight and Enter or Space commits the choice, which is the recommended pattern when a panel swap is not free.
- **The active state has three sighted carriers plus the semantic one.** The ink lift, the heavier label and the indicator bar all key off `aria-selected`, so no single one is load-bearing and the selection survives greyscale and a reader stylesheet that strips fills.
- **The focus ring is carried in the component's own classes.** Both the tabs and the active panel carry the ring rather than leaving it to the product stylesheet, so a project installed without that stylesheet does not lose it silently.

**Not checked at all, and listed rather than omitted:**

- Every contrast pair: the active tab's ink against the row, the tab-list rail, and the indicator bar against the ground behind it. `scripts/check-contrast.mts` has not been run for this component, which is why the report below is empty rather than reassuring.
- What the control draws under `forced-colors: active` and `prefers-contrast: more`, where the ink change and the indicator bar are both replaced by the platform's own pair. None of this has been put in front of a machine or a high contrast user.

## API reference

<PropsTable name="TabsProps" />

`value` and `onValueChange` make this a controlled component with no internal selection state: the caller stores the active value and passes it back, and a `value` that matches no item renders the row with no tab active and raises a development warning. `items` carries each tab's value, its visible label and the panel it reveals as one object, so a tab can never be rendered without its panel or a panel without its tab. `label` is optional because every tab has a visible label, but naming the list helps a screen-reader user who lands on it before its tabs.

## Related

<RelatedComponents name="tabs" />

**Easily confused with**

- [SegmentedControl](./segmented-control.mdx) sets a parameter of one view that stays on the surface, such as a chart's window. Tabs swap the panel for a different one. If choosing an option keeps the reader looking at the same thing, it is a segmented control.
- [TabBar](./tab-bar.mdx) moves the reader between whole sections of an app from a persistent bar, and each destination is its own tab stop because it is navigation. Tabs switch panels within one region and the list is a single tab stop.
- [Stepper](./stepper.mdx) moves through panels that are steps in a sequence, where progress and a next action matter. Tabs offer free movement between panels and say nothing about order.

**Used by**

- No pattern, recipe or screen composes it yet. It is a neutral primitive that a product drops into a card or a region of its own to fold two or three views of one subject behind their tabs.
