## How this is generated

Source file: `skills/opsinjs/evals/evals.json`. Script: `scripts/run-evals.mts`.
Command: `pnpm run evals`.

Each task in the source file is a question an agent asks in practice, the
address the answer has to live at, and the things that answer cannot omit or
claim. The script resolves each page — from `content/docs` on disk, or from the
served `.md` twins when it is given `--base` — checks every assertion, and
writes a dated result file. No score on this page is typed by a person, and a
task with no result renders as `<NoDataYet>` rather than as an optimistic blank.

What is being scored is the corpus, not a model: the script never contacts one.
A failing task means a page is missing, has moved, or has stopped saying the
thing it exists to say, which makes this a coverage probe for the docs-as-API
contract rather than a benchmark. The suite is deliberately small and
deliberately adversarial, and when a task starts failing the usual cause is that
a page became ambiguous.

### What a task looks like

A task pairs the question with assertions that can be checked mechanically. The
assertions are the interesting half:

```json
{
  "id": "normal-is-banned",
  "question": "How should I label a result that is inside the reference range?",
  "why": "Not \"normal\". The word carries a verdict opsinjs is not entitled to give, and a reader outside the range hears \"abnormal\" about themselves. The page has to carry both halves: the ban and the replacement wording, because a ban with no alternative is the thing writers route around.",
  "expect": {
    "page": "health/reference-ranges",
    "mustContain": [
      "normal",
      "is banned",
      "in the usual range",
      "describes the person, not the measurement"
    ],
    "alsoResolves": ["content/writing-status-and-alerts"]
  }
}
```

`mustContain` and `mustNotContain` are lowercase substring checks over the whole
page, not regular expressions and not judgements by another model. The
substrings are chosen because the page cannot be correct without them — a rule
it exists to state, a unit it exists to disambiguate — rather than because an
author happened to phrase it that way. `frontmatter` and `frontmatterAny` pin a
declared field, `catalogueId` and `catalogueStatus` check the catalogue row
instead of the prose, and `alsoResolves` asserts that the pages a good answer
would link to are actually there.

A needle also has to survive typography and serialisation, which is why so many
of them are JSX attributes rather than sentences. The runner matches plain
substrings against the page text, so a phrase lifted from running prose passes
or fails on where the author happened to break the line — the sentence saying a
component is implemented wraps on `TrendSparkline` and does not on `ResultCard`.
An attribute (`importPath="@/components/ui/result-card"`, `status="alpha"`), a
token name, a table cell or a fenced command is on one line by construction.
Prefer an attribute whose value is already a string, because those survive both
forms of the page: the `.md` twin serialises every JSX expression attribute,
so `unbuilt={false}` on disk arrives as `unbuilt="false"` over HTTP. A needle
written in the brace form then stops matching under `--base` — as a
`mustContain` it fails against a page that is correct, and as a `mustNotContain`
it passes while measuring nothing. Where the suite has to pin one of those, it
asserts both spellings.

**Refusal.** Does the assistant refuse to emit an import for a component that is
specified and not implemented? This is the highest-weighted family, because it
is the failure the whole scaffold exists to prevent.

**Tokens, not values.** Does generated markup contain a literal colour, radius or
duration? Checked by pattern over the diff.

**Axis discipline.** Does any single element carry both a category colour and a
status colour? Checked structurally.

**Threshold refusal.** Asked to classify a reading, does the assistant decline
and name who owns the decision? A number the prompt did not supply is a failure.

**Citation.** Does the assistant name the documentation page it used? An
uncited claim is not scored as wrong, but it is scored as conditional, because
it cannot be checked.

### Scoring

Three outcomes per task.

- **Pass** — every assertion held.
- **Conditional** — the substance was right and something checkable was missing,
  typically a citation. Conditional results are reported, not hidden inside the
  pass rate.
- **Fail** — an assertion was violated.

The headline figure is the weighted pass rate of the refusal family, because a
suite that scores well on style and badly on refusal describes an assistant that
writes beautiful imports of modules that do not exist.

### What this suite does not measure

It does not measure clinical correctness, and it cannot. Every assertion is
mechanical. An assistant can pass every task and still produce a screen that a
clinical reviewer would reject, and the safety argument continues to rest on
[the review checklist](../health/safety-review-checklist.mdx) rather than on a
score.

It also does not measure whether the *documentation* is right. It measures
whether the documentation is legible to a machine — which is a lower and more
achievable bar, and the one this pillar is responsible for.

### Reproducing a run

```bash
pnpm run evals
```

The script needs a model endpoint configured in the environment; without one it
exits with a readable message rather than reporting zeros, because a zero and an
un-run suite are not the same fact and must never look the same on this page.

Results are written dated. A run is attached to a documentation version, so a
regression can be traced to the change that caused it — see
[Docs freshness](../project/docs-freshness.mdx).
